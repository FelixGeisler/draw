= 5. Building Block View

== 5.1 Whitebox: Overall System

....
F:\Project (npm workspaces)
├── client/          React + TypeScript + Vite SPA
└── server/          Express 5 + better-sqlite3 + Claude API proxy
....

The layering below is the one rule the whole server obeys: routes validate and
map status codes, services own the domain, and only `db.ts` opens SQLite. The
MCP adapter (ADR-19) enters through the same REST front door as the browser —
it is a second client, not a second back end.

    ├── gamificationService.ts  completion transaction, XP/levels/streaks, achievements

[cols="1,2,2",options="header"]
|===
|Block |Responsibility |Key invariant

|`drawService`
|Candidate selection + weighting
|Drawability is computed, never stored

|`gamificationService`
|Completion side-effects
|XP/level/streak always derived from `completions`; freeze tokens are an append-only earn log, consumption derived at read time (ADR-28)

|`statsService`
|Time aggregation, estimated-vs-tracked accuracy
|Running entries count up to _now_; date math in UTC; tasks without estimate or tracked time are excluded from accuracy, never counted as 0

|`activityService`
|Per-day history card derivation (skyline)
|Derived read-side from `time_entries` + `completions`, bucketed by *local* day; a worked-but-uncompleted day stays face-down forever

|`aiService`
|Claude API access
|Requests blocked without key (503) or above 180K input tokens (400)

|`svgSanitizer` + `cardArtService` + `cardArtStyle`
|Card art safety, cost and variety (ADR-22)
|Only allowlist-re-serialized SVG is ever stored or served; at most one generation *in flight* per task; style directives are a pure function of the task id; regenerate is the only path that replaces a row (generate-then-replace)
|===

                               GamificationHeader, TrophyDeck, ActivityHeatmap,
                               AchievementToast, MaterialsSection, AiSuggestionPanel
                               (breakdown, plan, generate-tasks panels)
....

All server state flows through TanStack Query; task mutations invalidate the
`tasks`/`gamification`/`stats`/`activity`/`goals` query keys (goal cards derive
their task counts from tasks; timer start/stop also touches `activity` — a
started task lays a card into today's skyline tower). There is no other state
management.

== 5.4 Data Model

....
categories 1─n tasks n─1 goals 1─n materials
                │ 1─n time_entries
                │ 1─n completions        achievements (unlocked keys)
                └─ self-reference: parent_id (breakdown tree, depth 1)
                                         settings (key/value)
....

Central semantics: completing a *recurring* task keeps it `open` and pushes
`due_date` forward; completing a normal task sets `status='done'`. Both insert a
`completions` row — the single source for XP, streaks, trophy deck, and history.
