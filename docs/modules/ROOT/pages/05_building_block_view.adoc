....
server/src/
├── index.ts                 entry point: loads .env, starts the server
├── server.ts                startServer() — binds 127.0.0.1:API_PORT (testable)
├── app.ts                   createApp() — Express app + router mounting (testable)
├── db.ts                    SQLite bootstrap, PRAGMA user_version migrations
├── schema.sql               Current full schema (fresh installs)
├── aiSchemas.ts             zod schemas for structured AI outputs
├── routes/                  HTTP layer (validation, status codes)
│   ├── tasks.ts             CRUD, subtask bulk-create, timer start, completion entry point
│   ├── categories.ts        CRUD (delete blocked while referenced)
│   ├── goals.ts             CRUD with task/material counts
│   ├── materials.ts         multer upload, download, delete (disk + row)
│   ├── timer.ts             current/stop; start lives on tasks route
│   ├── draw.ts              POST /api/draw, GET /api/draw/current (restore)
│   ├── stats.ts             GET /api/stats (UTC date-range handling)
│   ├── activity.ts          GET /api/activity (per-local-day history, ADR-21)
│   ├── gamification.ts      GET /api/gamification
│   ├── settings.ts          key-value settings
│   └── ai.ts                status, estimate, breakdown, plan-goal, generate-tasks
└── services/                Domain logic
    ├── drawService.ts       drawable predicate + weight formula + roulette selection + current draw
    ├── statsService.ts      SQL aggregations, leverage insights, weekly grade, estimation accuracy
    ├── activityService.ts   per-day card derivation for the history skyline (pure core + SQL fetch)
    ├── gamificationService.ts  completion transaction, XP/levels/streaks, achievements
    ├── aiService.ts         Anthropic client, material blocks, prompts, token guard
    └── aiPostprocess.ts     deterministic generate-tasks shaping (ADR-14): pure, SDK-/DB-free
....

[cols="1,2,2",options="header"]
|===
|Block |Responsibility |Key invariant

|`drawService`
|Candidate selection + weighting
|Drawability is computed, never stored

|`gamificationService`
|Completion side-effects
|XP/level/streak always derived from `completions`

|`statsService`
|Time aggregation, estimated-vs-tracked accuracy
|Running entries count up to _now_; date math in UTC; tasks without estimate or tracked time are excluded from accuracy, never counted as 0

|`activityService`
|Per-day history card derivation (skyline)
|Derived read-side from `time_entries` + `completions`, bucketed by *local* day; a worked-but-uncompleted day stays face-down forever

|`aiService`
|Claude API access
|Requests blocked without key (503) or above 180K input tokens (400)
|===

== 5.3 Whitebox: Client

....
client/src/
├── api/client.ts + types.ts   typed fetch wrapper, shared DTOs
├── hooks/                     TanStack Query wrappers (useTasks, useDraw, useTimer,
│                              useGamification, useGoals, useAi, useActivity)
├── pages/                     Draw (centerpiece, incl. the CSS-3D card flip), Capture,
│                              Tasks, Goals, Stats, History (skyline), Settings
├── lib/                       pure client logic (drawable classification, effort display,
│                              generate-tasks review model) — unit-tested without rendering
└── components/                TaskRow/Form/Badges, SubtaskEditor, TimerBar,
                               GamificationHeader, TrophyDeck, AchievementToast,
                               MaterialsSection, AiSuggestionPanel (breakdown, plan,
                               generate-tasks panels)
....

All server state flows through TanStack Query; task mutations invalidate the
`tasks`/`gamification`/`stats`/`activity`/`goals` query keys (goal cards derive
their task counts from tasks; timer start/stop also touches `activity` — a
started task lays a card into today's skyline tower). There is no other state
management.

== 5.4 Data Model

....
categories 1─n tasks n─1 goals 1─n materials
                │ 1─n time_entries
                │ 1─n completions        achievements (unlocked keys)
                └─ self-reference: parent_id (breakdown tree, depth 1)
                                         settings (key/value)
....

Central semantics: completing a *recurring* task keeps it `open` and pushes
`due_date` forward; completing a normal task sets `status='done'`. Both insert a
`completions` row — the single source for XP, streaks, trophy deck, and history.
