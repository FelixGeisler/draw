= 5. Building Block View

== 5.1 Whitebox: Overall System

....
F:\Project (npm workspaces)
├── client/          React + TypeScript + Vite SPA
└── server/          Express 5 + better-sqlite3 + Claude API proxy
....

The layering below is the one rule the whole server obeys: routes validate and
map status codes, services own the domain, and only `db.ts` opens SQLite. The
MCP adapter (ADR-19) enters through the same REST front door as the browser —
it is a second client, not a second back end.

|===
|Block |Responsibility |Key invariant

|`drawService`
|Candidate selection + weighting
|Drawability is computed, never stored; a `task_fixed_slots` row excludes its task from candidates and current-card restore

|`fixedSlots`
|Validate the frozen schedule-zone identifier policy, resolve local wall minutes, and atomically set/replace/clear one slot
|Gap minutes reject; folds choose the earlier instant; UTC years stay `0001`–`9999`; final fixed-slot plus recurrence state is forbidden

|`db` + `SafeDatabase`
|Own the live native SQLite handle and expose only copied `prepare().run/get/all` values plus wrapped transactions
|Ordinary production code cannot recover a native handle/path, run DDL/pragma/attachment/transaction SQL, or access protected projection/introspection names; wrappers resolve the current handle after restore

|`weekService` + private `weekWorker`
|Authenticate cursor v2 in the main process, admit one Week computation, and read one bounded coherent v23 page on a lazy read-only Worker Thread
|Routes receive no path/handle/key; at most 101 title-free identities and 100 prefix-bounded titles are processed; Worker Thread isolation does not contain native OOM or abort

|`backupService` + restore preflight
|Own staged SQLite handles and semantic live snapshot/checkpoint/close/reopen capabilities
|A bounded exact v1–v23 `sqlite_schema` inventory precedes integrity checks, migration, virtual-module access and source reads; imported SQL is never executed

|`gamificationService`
|Completion side-effects
|XP/level/streak always derived from `completions`; freeze tokens are an append-only earn log, consumption derived at read time (ADR-28)

|`statsService`
|Time aggregation, estimated-vs-tracked accuracy
|Running entries count up to _now_; date math in UTC; tasks without estimate or tracked time are excluded from accuracy, never counted as 0

|`activityService`
|Per-day history card derivation (History calendar)
|Derived read-side from `time_entries` + `completions`, bucketed by *local* day; a worked-but-uncompleted day stays face-down forever

|`shopService` + `packCatalog`
|Atomic pack purchase/replay, derived shop state and settings-owned collection, over pure catalog/probability calculations
|Classic is always-owned fallback and never pullable; each fresh opening is one immediate transaction and three server-supplied samples, while replay consumes no RNG and reapplies no fact

|`aiService`
|Claude API access
|Requests blocked without key (503) or above 180K input tokens (400)

|`svgSanitizer` + `cardArtService` + `cardArtStyle`
|Card art safety, cost and variety (ADR-22)
|Only allowlist-re-serialized SVG is ever stored or served; at most one generation *in flight* per task; style directives are a pure function of the task id; regenerate is the only path that replaces a row (generate-then-replace)
|===

=== Gold pack catalog boundary (#265)

`packCatalog.ts` owns one registry in this exact order: `classic` (Classic
weave); common `ember` (Ember lattice), `tide` (Tide glass), `midnight`
(Midnight stars), `parchment` (Aged parchment), `graphite` (Graphite weave);
rare `meadow` (Meadow braid), `royal` (Royal filigree), `sakura` (Sakura
glass), `circuit` (Neon circuit), `frost` (Frost lattice); ultra-rare `aurum`
(Aurum crest), `aurora` (Aurora silk), `obsidian` (Obsidian gold); and
secret-rare `prism` (Prism foil). Classic is the common fallback only, leaving
pullable tier sizes 5/5/3/1.

Its functions are side-effect-free and require explicit finite `[0,1)`
samples: trailing non-Secret outcomes increase the next Secret chance from
500 by 50 basis points to a 1500 cap; rarity selection reserves that Secret
chance and divides the remainder 45:32:18; a separate sample selects uniformly
within the chosen tier; duplicate Gold is 10/20/40/100; and bonus intervals are
Freeze 5%, Pouch 5%, Ticket 2%, none 88%, with a would-be Freeze resolving to
Pouch at the bank cap of 2. Invalid inputs throw rather than clamp or coerce.
`packCatalog.ts` still owns no RNG or persistence. #266 composes `Math.random`
at `createApp` into a per-app shop router and calls the pure functions with
exactly three samples only after replay and payment checks. `shopService.ts`
owns the current-handle `db.transaction(fn).immediate()` boundary: canonical
ref lookup, derived Gold/Ticket/Secret/Freeze reads, opening insert,
settings-owned grant, and charge/refund/Pouch effects commit or roll back as
one unit. It maps immutable opening facts separately from the fresh shop
snapshot; same-ref/same-payment replay returns the same opening without RNG or
repair. No client, schema, backup-format, or test endpoint participates.

All server state flows through TanStack Query. The independent `['shop']`
snapshot is replaced only by a successful pack response or refetched after an
authoritative producer/equip invalidation; the pack client never derives or
optimistically changes economy/collection state. A validated purchase response is
also snapshotted into one mount-local reveal session keyed by its opening ref/order;
that presentation never rereads mutable query data or persists reveal progress.
Task mutations invalidate the
`tasks`/`gamification`/`stats`/`activity`/`goals` query keys (goal cards derive
their task counts from tasks; timer start/stop also touches `activity` — a
started task lights up today's cell in the History calendar), plus `draw.current`,
which holds a pointer a task mutation can invalidate (ADR-13). There is no
other state management.

== 5.4 Data Model

....
categories 1─n tasks n─1 goals 1─n materials
                │ 0─1 task_fixed_slots
                │ 1─n time_entries
                │ 1─n completions        achievements (unlocked keys)
                └─ self-reference: parent_id (breakdown tree, depth 1)
 task_fixed_slots ─┐                    settings (key/value)
 time_entries ─────┴─> week_interval_access 1─1 week_interval_rtree
                              │
                              └─ readiness/generation: week_access_state
....

`task_fixed_slots` stores one optional planned interval as canonical UTC start/end
plus the exact accepted entry timezone. It is independent from `due_date` and
`time_entries`; its presence is exposed as `hasFixedSlot`/`fixedSlot` and excludes
the task from Draw for the row's whole lifetime.

Schema v23's `week_interval_access` is a disposable numeric companion for every
eligible fixed slot and tracked interval; `week_interval_rtree` indexes its
inclusive UTC-day bounds and contains one row with the same `index_id`.
`week_access_state` records source/built generations and readiness. The source
tables remain authoritative and titles/descriptions never enter the projection.
The Phase 2A Week worker now consumes it through the RTree-first bounded query;
the Week client remains planned (ADR-75).

Central semantics: completing a *recurring* task keeps it `open` and pushes
`due_date` forward — that date is the task's *next occurrence*, so the card is
out of the deck until it arrives (ADR-6 amendment, #205); completing a normal
task sets `status='done'`. Both insert a
`completions` row — the single source for XP, streaks, trophy deck, and history.

== 5.5 Daily digest boundary

`dailyOverviewService` owns the single overdue/today/tomorrow classifier used by
both `/today` and notifications. Its digest projection aggregates complete
counts in SQL and performs a separate ordered `LIMIT 5` title query from the
same eligible relation; Push code never calls the HTTP route or reimplements
eligibility. `digestEvaluator` owns saved-IANA-zone wall time, quiet hours,
window and remaining TTL. `digestScheduler` owns one production recursive tick,
permit-before-claim and the `(device_id,local_date)` claim. `PushService` retains
authority, DNS, transport, exact-fingerprint deletion and final synchronous
race checks, then reads the projection and constructs one closed v2 payload.
The worker owns fixed presentation and only `/today` or `/settings` click data.
Default/development app assembly injects disabled Push and creates no scheduler.
