= 7. Deployment View

Three deployment modes. On the owner's machine: *dev* — two processes, Vite
serving the client with an `/api` proxy — and *production* (#189,
xref:09_architecture_decisions.adoc[ADR-49]) — one process, one port, Express
serving the built client next to the API. For self-hosting: a *container* (#191,
xref:09_architecture_decisions.adoc[ADR-51]) — the same production process,
packaged multi-arch for a Raspberry Pi (linux/arm64) or a linux/amd64 host,
with data on a named volume.

=== Wiring an MCP client

The adapter is a stdio process that talks to the running instance over
`/api` (ADR-19), so the app must be up and the client just needs to know how
to launch it. *Claude Code* reads the committed
https://github.com/FelixGeisler/draw/blob/main/.mcp.json[`.mcp.json`]
automatically when the repo is opened — approve the `draw` server when
prompted. *Claude Desktop* needs the server declared in
`claude_desktop_config.json` with an absolute path to the checkout:

[source,json]
----
{
  "mcpServers": {
    "draw": {
      "command": "npm",
      "args": ["run", "-s", "mcp", "-w", "server", "--prefix", "/path/to/draw"]
    }
  }
}
----

On Windows the same entry goes through the shell —
`"command": "cmd"` with `"/c"` prepended to the argument list — because `npm`
is a `.cmd` shim there and cannot be spawned directly. Point `DRAW_API_URL` at
a non-default origin, and set `DRAW_PASSWORD` in the client's env when the
instance is gated (ADR-50); the committed `.mcp.json` never carries a secret.

== 7.2 Production — `npm run build` + `npm start`

`npm run build` bundles the client to `client/dist` (vite) and type-checks the
server; `npm start` runs `tsx server/src/prod.ts` — the same Express app as
dev, plus `client/dist` served statically with an SPA fallback, on the single
`API_PORT`. There is no separate client process and no proxy; the server is
deliberately not compiled to JS (ADR-49). The MCP adapter is unchanged — it
talks to the same `/api` surface on the same port.

With `DRAW_PASSWORD` set (#190, xref:09_architecture_decisions.adoc[ADR-50]),
everything except `GET /api/health` and the login route requires a credential:
browsers get a server-rendered login page and a 30-day signed session cookie,
the MCP adapter sends the same secret as an `x-draw-password` header (it reads
`DRAW_PASSWORD` from its own env — the committed `.mcp.json` carries no
secret). Unset, the gate does not exist. Draw itself speaks plain HTTP; TLS is
terminated in front of it — see <<_7_4_tls_tailscale_serve_in_front_of_the_container_207,7.4>>
(#207, xref:09_architecture_decisions.adoc[ADR-55]).

With `BACKUP_INTERVAL_HOURS` set (#194,
xref:09_architecture_decisions.adoc[ADR-52]), the production entry starts an
in-process timer that writes a backup archive into `DATA_DIR/backups/` on that
schedule and prunes to the newest `BACKUP_RETENTION` (default 7). No cron — the
headless Pi keeps backing itself up with the process it already runs. Restore is
the existing `POST /api/backup/import` (section 8.9); the archives are ordinary
Draw backups. Unset/0 (the default) starts nothing.

== 7.3 Container — Raspberry Pi self-host (#191)

The 1.0.0 self-hosted deployment (#191,
xref:09_architecture_decisions.adoc[ADR-51]) packages the *production* process
above into a multi-arch image. A multi-stage build compiles the native
`better-sqlite3` binary for the target architecture (`linux/arm64` for the Pi,
`linux/amd64` for a desktop/server), builds the client with vite, prunes dev
dependencies, and ships a slim glibc runtime that runs the same tsx entry
(`node --import tsx src/prod.ts`) as an unprivileged `node` user. Build both
arches with buildx:

[source,console]
----
docker buildx build --platform linux/amd64,linux/arm64 -t draw:latest .
----

Config is by environment, identical to production mode: `HOST=0.0.0.0` (baked
in — the container listens on all interfaces so the port mapping is reachable),
`API_PORT` (default 3001), and the LAN opt-ins `DRAW_PASSWORD` /`TRUST_PROXY`
(xref:09_architecture_decisions.adoc[ADR-50] — set a password on a real
network). All persistent state lives under `DATA_DIR=/data` on a *named volume*,
so tasks, materials, and the database survive `docker compose down`, container
recreation, and image upgrades. The container `HEALTHCHECK` polls
`GET /api/health` (above the password gate) with node's global `fetch`.

Registry publishing is automated by the tag-triggered release pipeline (#192,
xref:09_architecture_decisions.adoc[ADR-53]): every `v*` tag runs the full test

the package to *Public* once (or self-hosters `docker login ghcr.io` with a

the container — the `draw-data` volume carries the data across.
*Backup/restore:* unchanged from
xref:09_architecture_decisions.adoc[ADR-26] — export the zip from Settings, or
snapshot the `draw-data` volume.

== 7.4 TLS — Tailscale Serve in front of the container (#207)

The container above speaks plain HTTP, which is a dead end for two of the
1.0.0 goals: the shared `DRAW_PASSWORD` (ADR-50) crosses the LAN in clear, and
the installable PWA (#193, xref:09_architecture_decisions.adoc[ADR-54]) never
installs, because browsers only register a service worker in a *secure
context*. Neither a bare LAN IP nor an mDNS `.local` name qualifies — only
`localhost` and real TLS do.

Draw ships no reverse proxy. TLS is delegated to *Tailscale Serve* (#207,
xref:09_architecture_decisions.adoc[ADR-55]), which runs on the host, obtains a
publicly-trusted certificate for the node's `*.ts.net` name, and proxies to
`127.0.0.1:3001`. No certificate has to be installed on any client, and the
deployment stays reachable off-LAN.

The two config changes are a *pair*, and the second is unsound without the
first. The published port moves to `127.0.0.1:3001:3001`, so the container is
reachable only from the host — i.e. only through Tailscale. Only then is
`TRUST_PROXY` safe to set, because a LAN client can no longer reach Express
directly to forge an `X-Forwarded-For`. The value is `1` (one trusted hop),
*not* the `loopback` preset: a published port arrives at the container from the
Docker bridge gateway, so the peer address inside is never `127.0.0.1` and
`loopback` would trust nothing — leaving the login limiter keyed on the proxy
and one attacker able to lock out everyone.

Cookie scope follows the request rather than the config: `draw_session` gets
its `Secure` attribute from `req.secure`, which is honest precisely when
`trust proxy` is set. Plain-HTTP deployments keep working unchanged — a
hardcoded `Secure` would make the cookie unsettable there and lock the owner
out of their own server.

== 7.5 Updates over the air — check, tell, apply (#247)

Draw checks for its own updates but never applies them itself (#247,
xref:09_architecture_decisions.adoc[ADR-70]). Three separable parts:

*Check.* Once per `UPDATE_CHECK_INTERVAL_HOURS` (default 24; `0` disables the
timer) the server GETs the GitHub latest-release endpoint
(`UPDATE_CHECK_URL` overrides it), compares the tag against its own
`server/package.json` version — numeric semver fields, prereleases offered
only to prerelease runners — and caches the result in memory. The
`update_check_enabled` setting (Settings -> Updates, default on) gates every
call including the scheduled tick: off means zero outbound calls, the #235
rule. The first check runs ~60s after boot with jitter, never in the boot
path. A failed re-check (network, non-2xx, or a reachable feed answering
without a `tag_name`) retains the last successful sighting — one blip must
not un-light the banner until the next daily tick.

*Tell.* Settings -> Updates shows the running version, a "Check now" button
and — when a newer release is out — a banner with the release-notes link.
Forced checks are throttled server-side (one outbound GET per 30s; within
the window the cached status is served), so a hammered button cannot burn
GitHub's unauthenticated 60-req/hr budget.
The first sighting of a new version additionally sends one notification
through the existing `notify_url` door (#235), deduped in the
`update_last_notified_version` settings row so re-checks and restarts never
re-send. `GET /api/update` sits behind the password gate: the running
version is authed data, `/api/health` stays exactly `{ok, time}` (ADR-50).

*Apply.* One outbound POST to a user-configured trigger URL — Draw never
mounts `docker.sock` and never executes an update itself. The blessed target
is a Watchtower sidecar in HTTP-API mode, label-scoped to the draw container
with periodic polling off (the trigger is the only actor):

[source,yaml]
----
  watchtower:
    image: containrrr/watchtower
    restart: unless-stopped
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    environment:
      WATCHTOWER_HTTP_API_UPDATE: "true"          # update only when POSTed
      WATCHTOWER_HTTP_API_TOKEN: "<long random token>"
      WATCHTOWER_LABEL_ENABLE: "true"             # only labeled containers
    # draw service additionally gets:
    #   labels: [com.centurylinklabs.watchtower.enable=true]
    #   image: ghcr.io/felixgeisler/draw:latest   (image, not build:)
----

In Settings -> Updates, save `http://watchtower:8080/v1/update` plus the
token as the update trigger (write-only, presence flag on read, excluded
from `GET /api/settings` like `notify_url`). "Update now" then POSTs the
trigger with `Authorization: Bearer <token>` — the bearer never rides the
check request — answers `202`, and the client polls `GET /api/update` every
3s (up to 5 minutes) until the reported version changes, then reloads
through the #193 service-worker path and pays one "Updated to X" line. A
trigger that answers non-2xx (token typo'd, wrong URL) is remembered as
`lastApplyError` in the status and stops the poll with an error line instead
of a five-minute wait; a dropped or aborted socket is deliberately NOT a
failure — that is what a successful swap of the very container looks like.
No trigger configured: the apply endpoint answers `409` and Settings shows
this section instead of a button.

*Rollback:* pin the previous image tag in the compose file
(`image: ghcr.io/felixgeisler/draw:v1.2.3`), `docker compose up -d`, and —
if a migration ran in between — restore a backup from before the update
(xref:09_architecture_decisions.adoc[ADR-26]; the backup importer refuses
newer-versioned archives, so restoring an older backup into an older image
is the supported direction). Current images accept backups through schema
v18: older files migrate and undergo complete v18 schema/immutability
validation in staging before the live database moves; a missing or weakened
contract leaves the live deployment untouched. *Bare-npm path:* `git pull`, `npm ci`,
`npm run build`, restart `npm start` — the check and the banner work the
same; only the trigger button is container-specific.

=== 7.5.1 Pi-only `edge` polling runbook (#286)

This is the one explicit opt-in exception recorded by ADR-70, not a general
update mode. Only the designated operator may opt Tailscale host `raspberry` into the
operational `edge` channel with `docker-compose.pi-edge.yml`. The external,
digest-pinned Watchtower polls every 300 seconds; Draw still performs no
scheduled apply and never receives `docker.sock`. Base, stable, and local
Compose remain non-edge and polling-off by default, and ADR-70's manual
HTTP-API/trigger boundary remains unchanged everywhere else. `edge` is
continuous operational promotion from protected `main`, not GitHub Release
discovery. ADR-53 governs the detached immutable-SHA publication and promotion
evidence used by the preactivation and post-merge gates.

The opt-in must resolve to all of these values before it is used:

* Draw image `ghcr.io/felixgeisler/draw:edge` through `DRAW_TAG=edge`, with
  `AUTO_UPDATE=true` and `AUTO_UPDATE_INTERVAL_SECONDS=300`;
* only Draw labeled `com.centurylinklabs.watchtower.enable=true`; Watchtower
  has no enable label;
* Watchtower image
  `containrrr/watchtower:1.7.1@sha256:6dd50763bbd632a83cb154d5451700530d1e44200b268a4e9488fefdfcf2b038`;
* `WATCHTOWER_LABEL_ENABLE=true`, `WATCHTOWER_CLEANUP=true`,
  `WATCHTOWER_HTTP_API_PERIODIC_POLLS=true`, and
  `WATCHTOWER_POLL_INTERVAL=300`; and
* the existing non-secret settings `DOCKER_API_VERSION=1.43`,
  `WATCHTOWER_HTTP_API_UPDATE=true`,
  `WATCHTOWER_HTTP_API_TOKEN=$\{WATCHTOWER_TOKEN}`, `TZ`, ADR-52's backup
  settings, ADR-55's `127.0.0.1:3001:3001` and one-hop `TRUST_PROXY=1`, and
  ADR-51's `draw-data:/data` mapping (the deployed volume is
  `draw_draw-data`).

The Watchtower digest above is the verified top-level registry manifest-list
digest in that exact tag-and-digest pull reference. It is not a local Docker
image ID. Mounting `/var/run/docker.sock` gives Watchtower root-equivalent host
control. Polling may replace Draw without another prompt; changing the
Watchtower digest requires review; cleanup removes superseded local images,
not GHCR immutable tags. Draw never receives the socket. There is no automatic
rollback and no automatic backup restoration.

==== Registry access and secret boundary

Public, anonymous GHCR access is the active policy. Immediately before
activation, anonymously pull or inspect both the current immutable Draw tag and
`edge`; configure no registry credential while that succeeds. Every repository
inspector invocation must unset `OCI_REGISTRY_USERNAME` and
`OCI_REGISTRY_PASSWORD`. Every Docker inspection or pull gate must additionally
set `DOCKER_CONFIG` to a newly created temporary directory whose only
`config.json` is `{"auths":{}}`. That isolated config prevents Docker from
consulting a host-default login, credential store, or credential helper. It is
safe even when the operator has a host login: do not log out or alter that
login; remove only the temporary directory when the gate finishes. A visibility
or access failure stops activation.

Only if anonymous access has stopped working may the coordinator provision the
fallback: one dedicated package-read credential with no package write/delete
scope. `/home/raspberry/draw/watchtower-docker-config` is owned by the Pi
deployment account with mode `0700`; its sole `config.json` has mode `0600` and
is mounted read-only as `/config.json` in Watchtower. Do not use or depend on
the host-default Docker login/config. The coordinator owns initial provisioning,
redacted validation, and removal if activation is abandoned. After successful
handoff, the designated Pi deployment operator owns rotation, revalidation,
revocation, and removal. Failed initial or rotated access stops Watchtower
until read-only access is restored.

Never put a token, password, Docker auth/config content, secret-bearing command
or output, rendered Compose values, backup contents, or sensitive storage path
in Git, documentation, an issue/PR, logs, or evidence. Evidence records only
redacted pass/fail and the approved non-secret identifiers below.

==== Preactivation gates and backup

Do not mutate the Pi until every gate passes. #280 and PR #283 must be merged.
Renew the read-only `main` protection check: required `test` from GitHub Actions
app ID `15368`, force pushes disabled, and branch deletion disabled. Under
ADR-53, wait for successful protected-`main` `test`, detached immutable-SHA
publication, and promotion for the exact current `main` SHA. From a trusted
clean checkout, run the repository inspector with both credential variables
absent against both images:

[source,console]
----
env -u OCI_REGISTRY_USERNAME -u OCI_REGISTRY_PASSWORD node scripts/inspect-oci-image.mjs --image ghcr.io/felixgeisler/draw:sha-<current-main-full-40-sha> --expected-revision <current-main-full-40-sha>
env -u OCI_REGISTRY_USERNAME -u OCI_REGISTRY_PASSWORD node scripts/inspect-oci-image.mjs --image ghcr.io/felixgeisler/draw:edge --expected-revision <current-main-full-40-sha>
----

Both revisions must equal current `main`; both reported top-level OCI-index
digests must be exactly equal. Absence, invalidity, access failure, failed
workflow, revision mismatch, or digest mismatch stops activation.

Create a current verified activation backup immediately before activation:

. use the authenticated Draw export to create a fresh, complete ADR-26 export;
. copy it off-host as the deployment operator required by ADR-52;
. require a non-empty file, a passing ZIP integrity check (for example
  `unzip -t` without retaining its file listing), and identical SHA-256 on the
  Pi and off-host copies; and
. record only filename, UTC creation time, byte size, SHA-256, and the literal
  result `off-host copy verified`.

File presence, age, or an ADR-52 scheduled-backup log alone does not pass:
scheduled archives remain on ADR-51's volume, while off-host copying and restore
readiness are operator responsibilities. Restore is ADR-26 import of the
complete export. Keep tested off-host backups after handoff.

Before any change, record the currently running Draw image reference/digest,
the verified pre-merge immutable rollback reference, `draw_draw-data` mounted
at `/data`, and one preselected existing-data continuity check without copying
its content into evidence. Never run
`docker compose --env-file /home/raspberry/draw/.env -f /home/raspberry/draw/docker-compose.pi-edge.yml down -v`,
remove `draw_draw-data`, or recreate that volume.

`sha256:6dd50763bbd632a83cb154d5451700530d1e44200b268a4e9488fefdfcf2b038`,
and linux/arm64/v8 child manifest
`sha256:f14f090fcc8235449da45ccbb1aea3b424ed3b101bcbd3de56526909397c2369`.
Then, on the Pi, pull the exact tag-and-digest reference and inspect that same
