= 9. Architecture Decisions

Lightweight ADR list. New decisions are appended here via the normal issue/PR flow.

== ADR-1: better-sqlite3 over a JSON file store

*Context:* Local persistence for tasks, time entries, completions.
*Decision:* SQLite via better-sqlite3.
*Rationale:* Stats/leverage is aggregation ("minutes by impact in range") — trivial in
SQL, awkward in JSON; synchronous API suits Express handlers; prebuilt Windows
binaries; atomic writes protect time-tracking data. Fallback documented: `node:sqlite`
(Node ≥ 22.5) has a near-identical API.

== ADR-2: Drawability as derived predicate, not stored flag

*Context:* Tasks enter/leave the deck when effort, children, or settings change.
*Decision:* Compute `drawable` in SQL at query time.
*Rationale:* A stored flag needs synchronization on every mutation path; the
predicate is one WHERE clause and cannot drift.

== ADR-3: Server-side AI proxy instead of browser calls

*Context:* The Claude API key must not leak; browser calls would expose it.
*Decision:* All Anthropic traffic goes through Express (`/api/ai/*`).
*Rationale:* Key isolation in `.env`; server can assemble context from the DB
(task, goal, siblings, materials) and enforce the token guardrail centrally.

== ADR-4: Impact only for goal-linked tasks

*Context:* "Clean the kitchen" has no leverage toward anything measurable.
*Decision:* The star widget only appears when a task is linked to a goal; unlinked
tasks keep a neutral default of 3. Chores compete via urgency and staleness instead.
*Rationale:* Impact is defined as _leverage toward a goal's measured outcome_;
forcing users to rate chores would produce noise and erode the metric.
*Enforcement boundary (#65, #76):* The API is the single enforcement point.
Non-neutral impact (≠3) without a goal is rejected on `POST /api/tasks` and
`PATCH /api/tasks/:id`; out-of-range impact is a clean 400 on every path.
Two deliberate exceptions keep history and breakdowns honest: grandfathering —
goal *deletion* keeps the historical rating everywhere, and the edit form's
no-op resend of a stored value passes — and the subtask batch
(`POST /api/tasks/:id/subtasks`, MCP `create_subtasks`), which accepts
per-subtask impact even under a goal-less parent: subtasks inherit the
parent's goal, and a goal-less breakdown's ratings rank the siblings relative
to each other (the AI breakdown emits exactly those). A deliberate goal
*unlink* is different from deletion: the server resets impact to 3 on the
task and cascades the reset to its *open* subtasks — the ratings described
leverage toward the goal that was just removed — while done/archived subtasks
keep theirs as the historical stats record, mirroring the category cascade's
open-only rule.
*Single-create parity (#84):* `POST /api/tasks` with a `parentId` inherits the
parent's goal and category exactly like the batch endpoint — an explicit
divergent `goalId`/`categoryId` is rejected, the impact gate judges the
*inherited* goal, and an omitted impact defaults to the parent's rating (the
batch's `s.impact ?? parent.impact` fallback, not the root create's neutral
3). Before, that path ignored the parent's goal entirely, so a
child could carry its own goal under a goal-less parent; the parent edit
form's no-op `goalId` resend would then cascade over the child *without* the
unlink reset — a silent wipe that minted grandfathered ratings a third,
undocumented way. Goal deletion and the goal-less batch stay the only two
exceptions.

== ADR-5: Gamification derived from the completions log

*Context:* XP, levels, streaks, achievements must never contradict history.
*Decision:* One `completions` row per completion is the only stored fact; XP totals,
levels, and streaks are computed from it. Reopening a task deletes its latest
completion (no XP farming).
*Rationale:* Stored counters drift; a log can be re-aggregated and audited.

*Amendment (#263, schema v18):* XP is permanent. The exact aggregate is
completion XP + claimed-achievement XP + only `xp_ledger` rows whose reason is
`challenge`; every retained legacy shop reason is inert. Gold follows the same
log-over-counter rule, derived unclamped from `completions.gold_awarded`,
`achievements.claim_gold`, and `gold_ledger.amount`. No mutable balance exists.

== ADR-6: Recurring tasks stay open, due date advances

*Context:* Weekly chores must reappear without recreating tasks.
*Decision:* Completing a task with `recur_every_days` inserts a completion and sets
`due_date = today + interval`, keeping `status='open'`.
*Rationale:* The task re-enters the deck automatically as urgency ramps up; history
accumulates naturally in `completions`.

*Amendment (#205): the due date IS the next occurrence, and the card sleeps until it.*
As originally built, the advanced due date only lowered the card's urgency weight —
`due_date` was never part of the drawable predicate, so a chore came straight back out
of the deck seconds after being completed and kept coming back on every draw. That is
the low-leverage-work failure mode the app exists to prevent: the deck offers a card the
user just finished, which wastes draws and teaches distrust of the draw. The recurrence
schedule is now:

* On a task with `recur_every_days`, `due_date` is its *next occurrence*. The date the
  user entered is therefore the *first* occurrence (semantics (c) of the issue's open
  question), and the card is *not drawable before it* — a recurring chore due Thursday
  is not offered on Monday.
* Completing it sets `due_date = completion date + interval`, so the cycle stays
  *completion-anchored* ("every 4 days after I actually do it", the pre-existing
  behaviour), and the card sleeps again until that day.
* The gate applies *only* when `recur_every_days` is set. A non-recurring task with a
  future due date stays fully drawable — doing something before it is due is the point
  of the deck — and a recurring task with *no* due date has no schedule to wait for and
  stays always-drawable.

The sleep is *derived*, never stored (ADR-2/ADR-17): `isAwaitingNextOccurrence`
(`server/src/services/recurrence.ts`) is evaluated at read time by the candidate query,
by `isRestorable`, and by the client's `classifyTask`, so an occurrence arrives with no
write, exactly like a snooze wearing off. It is deliberately *not* implemented by
writing `deferred_until`: that column is the user's own "not now" (ADR-17), and
overloading it with a schedule would make "snoozed" mean two different things — in the
UI as well, where the card would wrongly read as sent away by the user. It classifies as
*scheduled* instead, alongside the availability window (ADR-20): the chip reads
`next <date>`, and an empty pool of only sleeping chores reports
`all_awaiting_next_occurrence` ("they come back on their own") rather than steering the
user into a breakdown with `all_too_big`.

Both the write and the read use the *user's local calendar day* (`localDate` in
`services/localDay.ts`), never UTC. A due date is a local calendar day the user typed,
and the same `completeTask()` call already attributes its completion to the local day
for streaks and the History calendar (ADR-21/ADR-28) — so recurrence answers "which day
was that?" exactly like the rest of the user-day logic, and the card wakes at the user's
own midnight. A UTC anchor was tried first and rejected in review (PR #206): east of UTC
it made one completion two different days depending on which subsystem asked, and a
daily chore finished at 00:30 local was dated to the very day it was done, returning to
the deck at 02:30 that same night — the #205 symptom surviving for late-night work.
The arithmetic itself is date-only string math (`addDays`): the original
`next.setDate(next.getDate() + n)` mixed the local wall clock with a `toISOString()`
format, so an interval spanning a DST transition shifted the instant by an hour and the
due date could land a day early (risk R3). Because both bugs are invisible on a UTC
machine, the server test suite pins `TZ=Europe/Berlin` (`server/vitest.config.ts`) —
otherwise the regression tests pass against the very arithmetic they reject.

== ADR-7: Whole documents to Claude, no RAG

*Context:* AI planning needs lecture PDFs and past exams as context.
*Decision:* Send user-selected materials whole as native PDF/text document blocks,
with prompt caching and a token/cost estimate gate. No embeddings, no vector store.
*Rationale:* For a personal corpus that fits in the context window, full documents
beat retrieval quality-wise and eliminate an entire infrastructure layer; cost is
controlled by explicit selection + estimate + cache.

== ADR-8: Structured outputs over free-form parsing

*Context:* AI suggestions must be machine-usable (title, effort, impact, phase).
*Decision:* `messages.parse()` with zod schemas (`output_config.format`).
*Rationale:* Schema-validated responses remove parsing failures; the SDK retries
on mismatch; impact constrained to a literal union 1–5.

== ADR-9: GitHub Pages from `docs/` on main, plain Jekyll [.line-through]#(superseded by ADR-10)#

*Context:* arc42 docs must be hosted with zero pipeline maintenance.
*Decision:* Markdown + minimal Jekyll theme in `docs/`, served by GitHub Pages'
built-in build; no Actions workflow, no static-site generator toolchain.
*Rationale:* Smallest possible moving part count; docs render both on
github.com and as a website.
*Status:* Superseded by ADR-10 — the owner chose a dedicated documentation SSG.

== ADR-10: Antora as the documentation site generator

*Context:* The Jekyll setup (ADR-9) rendered flat pages without navigation;
the owner wants a proper documentation site generator for the architecture docs.
*Decision:* Antora with the default UI. Content is an Antora component at
`docs/` (AsciiDoc pages under `modules/ROOT/pages`, nav in `nav.adoc`), built via
`npm run docs:build` from `antora-playbook.yml`, deployed to GitHub Pages by the
`Docs` GitHub Actions workflow (`build_type: workflow`) on pushes to `main`.
*Rationale:* AsciiDoc is arc42's native format; Antora provides a navigation
sidebar, cross-reference validation at build time (broken xrefs fail the build),
and a growth path to versioned docs. Trade-off accepted: docs no longer render
directly on github.com and the deployment needs one Actions workflow.
The default UI bundle is vendored at `docs-ui/ui-bundle.zip` (built from the
official source) because the upstream GitLab CI artifact URLs 404 — builds have
no network dependency.

== ADR-11: Claude API key configurable at runtime, stored plaintext in SQLite

*Context:* Requiring users to edit `server/.env` and restart the server to enable
AI assistance is exactly the setup friction the app exists to remove.
*Decision:* The key is stored in the existing `settings` table and managed only
through dedicated endpoints (`PUT`/`DELETE /api/ai/key`). `aiService` resolves the
key per request — DB value first, `ANTHROPIC_API_KEY` env var as fallback — so a
key set in the Settings UI takes effect immediately. No endpoint ever returns the
key: `GET`/`PATCH /api/settings` exclude the row, `GET /api/ai/status` reports only
`configured`, `model`, and the key's source (`database`/`environment`).
*Rationale:* Zero-restart configuration with the smallest surface. Plaintext at
rest is a conscious trade-off: this is a local single-user app with no auth
(section 2); encrypting with a locally stored secret would add complexity without
a meaningful security boundary. Out of scope: key validation, encryption at rest.

== ADR-12: Completing a task closes its own running timer

*Context:* Completion (`completeTask()`) never touched `time_entries`, so a
running timer kept accruing minutes against a task that was already done until
the user pressed Stop or started another timer.
*Decision:* Inside the completion transaction, the completed task's open time
entry (if any) is closed with `ended_at` = completion time. The check is per
`task_id`: a running timer that belongs to a *different* task is left
untouched. This applies equally on the recurring path (ADR-6): the task stays
open with an advanced due date, but the work session that just earned XP is
over, so its entry is finished — the next occurrence starts its own timer.
Reopening a task (ADR-5) does *not* reopen the auto-closed time entry: the
tracked minutes were really worked, only the completion is undone.
*Rationale:* A completion is the strongest possible signal that the work
session ended; leaving the entry open silently corrupts the leverage stats the
app is built around. Closing only the task's own entry keeps the common
"complete a quick task while a long timer runs elsewhere" flow intact.

== ADR-13: Current draw persisted server-side

*Context:* The drawn card lived only in DrawPage component state, so a page
reload lost it — inconsistent with the timer, which restores from the server.
Worse, the drawn-card XP bonus trusted a client `wasDrawn` flag, which was
gone after a reload too.
*Decision:* `POST /api/draw` stores the picked task id as
`current_draw_task_id` in the `settings` table (single-user app — one current
draw). The next draw overwrites it (an empty draw clears it), completing the
drawn task clears it, any task delete clears it once the pointed-to row no
longer exists (covering the drawn subtask cascade-deleted with its parent),
and `GET /api/draw/current` exposes it for restore. That endpoint
re-validates drawability with the same predicate as the
deck (ADR-2: open leaf, estimated, within `max_draw_effort`) and lazily clears
a pointer that went stale sideways — task edited too big, completed elsewhere,
turned into a container. The DrawPage restores the revealed card on mount
without the shuffle animation, mirroring the TimerBar. The completion bonus is
now derived server-side (current draw, or `last_drawn_at` within 6h as the
generous fallback); the client `wasDrawn` flag was removed.
*Rationale:* A settings row rather than a tasks column because the current
draw is app-level session state, not a task fact; lazy validation at restore
instead of eager clearing on every task mutation keeps the write paths simple
(one line each on complete/delete) and cannot drift — the same reasoning as
ADR-2. The delete path is the one deliberate exception: `tasks.id` has no
`AUTOINCREMENT`, so a freed id can be re-bound to the next captured task
before any restore validation runs — deletes therefore clear the pointer
eagerly whenever its row is gone, not only on an exact id match. Deriving the
bonus server-side removes a client-trust quirk and makes the bonus
reload-proof.
*Amendment (#88):* the DrawPage no longer offers "Draw again" — the draw is a
commitment, and the persisted pointer makes it reload-proof. A revealed card
is resolved (completed, snoozed/blocked, deleted), never re-rolled; only the
next draw after resolution overwrites the pointer. Editing the card out of
the deck also counts as resolution: the lazy restore validation clears the
stale pointer, so a reload after an edit-out lands on the idle deck — the
sanctioned "this card was a mistake" escape hatch, not a re-roll.

== ADR-14: AI proposes full task lists; checkbox review remains the sole write path

*Context:* `/api/ai/generate-tasks` transcribes goal materials (e.g. a
40-exercise past exam with points and time estimates per item) into a complete
task list. At that scale, AI auto-accept becomes tempting and silent rewrites
of the material's own numbers become invisible.
*Decision:* The endpoint returns a proposal only — no AI path ever writes to
`tasks` (extends ADR-3/ADR-8); the client's review-before-accept panel stays
the single write path. The proposal is shaped by two deterministic server-side
post-processing rules (pure functions in `aiPostprocess.ts`): (1) when at
least half the items carry points printed in the material, impact is the
item's point-rank quintile (top fifth → 5★ … bottom → 1★, ties share a
rating), with per-item fallback to the model's suggestion flagged as
`impactSource: "model"`; (2) items longer than `max_draw_effort` are split
into even parts that preserve the stated total ("split, don't clamp") — the
`Math.min` effort clamp used by breakdown/plan-goal is explicitly banned on
this path because it would silently rewrite the source material's time data.
Time is not folded into impact: draw weight is already `impact²/effort`, so it
would double-count effort.
*Rationale:* Points are the material's own measure of leverage toward the
graded outcome (ADR-4), so they beat a model guess whenever present — and a
deterministic mapping is auditable during review, where every rationale cites
its source row. Keeping the user's checkbox as the only write path preserves
the app's trust boundary no matter how many tasks the AI proposes at once.

== ADR-15: Estimation accuracy attributes tracked time per completion cycle

*Context:* The "Estimates vs. reality" block (stats) compared a task's single
per-cycle effort estimate against ALL of its lifetime time entries. Recurring
tasks (`recur_every_days`) complete over and over, so every finished cycle
inflated their ratio — and the summary/byCategory aggregates — a bit more.
Recurring chores are exactly where users track time repeatedly.
*Decision:* Tracked time is attributed per completion cycle: each completion
owns the entries in the window `(previous completion, this completion]`, and
every in-range completion's window counts — a task's tracked minutes are the
sum over its tracked in-range cycles, compared against one per-cycle estimate
each (the block's `estimatedMinutes` scales to cycles × estimate). Cycles
without tracked minutes are skipped entirely — they neither hide the task nor
scale its estimate, because a checkbox-only completion says nothing about
estimation accuracy (#48). One-shot tasks have no previous completion, so all
their work still counts even when it started before the range; entries
tracked after the last in-range completion belong to the next,
not-yet-completed cycle and are excluded. The window logic lives in the pure
`trackedCyclesInRange()` (statsService) fed by plain per-task queries, keeping
it unit-testable like the draw weights. Range-filtered time totals
(`totalMinutes`, byCategory minutes, leverage) are untouched: every tracked
minute still counts there.
*Rationale:* Per-cycle attribution over excluding recurring tasks from the
block, because recurring work is where estimation feedback matters most;
every tracked in-range cycle over latest-cycle-only, because latest-only made
a task vanish when only an earlier in-range cycle was timed and silently
discarded tracked cycles when several were (#48); attribution in TypeScript
over correlated SQL subqueries so the boundary rules are testable without a
DB and readable next to `buildEstimation()`.

== ADR-16: Bulk accept commits one umbrella parent plus one transactional subtasks batch

*Context:* The plan-backward accept loop fires N sequential, non-atomic
`POST /api/tasks` calls. For the generate-tasks flow (ADR-14) with 40+
accepted rows that is unacceptable twice over: a mid-loop failure leaves a
half-imported list, and 40 new root tasks would flood every list view.
*Decision:* The review panel commits as *one umbrella parent* (created
unestimated, so it classifies as a container — never drawn while children are
open, ADR-2 — with remaining effort aggregated from the leaves) followed by
*one* `POST /api/tasks/:id/subtasks` batch, which is already transactional
and inherits category/goal from the parent. Each leaf carries a provenance
`description` ("Exercise 7 · 8 pts · ~45 min · exam.pdf") citing the
material's original numbers — the user's effort edits never rewrite it. If
the batch fails, the client deletes the just-created parent (cascade), so no
half-imported state survives. Exercises split into parts commit as flat
part-leaves under the same parent, keeping the tree exactly two levels deep.
*Rationale:* Reusing the two existing write endpoints avoids a third,
AI-shaped bulk-import path and keeps their invariants (validation, category
inheritance, one transaction per batch). The one non-atomic seam left —
parent created, batch failed — is closed with a compensating delete, which is
simpler than a new atomic endpoint and impossible to observe as a task list
(a bare parent with zero children exists only between the two calls). Deeper
nesting is banned because every list renders roots plus one child level:
level-3 leaves would be draw-eligible yet invisible everywhere. Since #35 the
API enforces the ban on both subtask-creation paths —
`POST /api/tasks/:id/subtasks` and `POST /api/tasks` with a `parentId` — by
rejecting a parent that is itself a subtask with 400, so API/MCP callers
cannot create the nesting the UI already forbids (the one-level
remaining-effort rollup and the one-level goal/category cascades rely on it).
Databases that acquired nesting before that guard are repaired at startup by
the v7 migration (#80, ADR-24), so the invariant holds for every database,
not only for post-guard writes. Reparenting (#100, `PATCH parentId`) enforces
the same invariant from both directions: the target must be a root task, and
the moved task must be childless — children of *any* status, since a
done/archived child is one status write away from being an open grandchild.
Those two rules are also what keeps `parent_id` acyclic now that it is no
longer INSERT-only (ADR-24): a childless mover can never become anyone's
ancestor. An adopted task joins the breakdown keeping its own stored
`sort_order` (ADR-43, `(sort_order, id)` order — backfilled to `id`, so it
still lands by roughly creation order and may be dragged into place after).
Split-in-place (#108) is the
sanctioned path for *deep* decomposition within this ban: a subtask above the
draw limit cannot be broken down further, so `POST /api/tasks/:id/split`
*replaces* it with two or more parts as siblings under the same parent — the
original ends `archived` in the same transaction, never deleted (its time
entries and completions survive; a running entry is closed at split time,
mirroring completion, ADR-12). Part estimates deliberately carry no
`<= max_draw_effort` cap — a part that is still too big is itself split
again. The tree stays exactly two levels everywhere; decomposition is
unlimited *by repetition, not by depth*. Recurring originals are rejected
(parts are one-shot rows — no part could carry the recurrence; the repair is
ADR-23's: drop the recurrence first), and the parts INSERT carries no
recurrence column, so a split can never mint the ADR-23 ban either.

*Amendment (#161): the umbrella is optional.* The container earns its keep for
a large import — 40 comparable leaves would flood the lists as roots (#28/#29)
and #30's fold hangs off it — but for a small hand-generated set it is
bureaucracy: a parent that appears out of nowhere. The generate-tasks review
panel now carries a "Group under one parent task" toggle, defaulting ON at
`>= 5` accepted leaves and OFF below (`defaultUmbrella`, pinned client-side),
always overridable before accepting. Toggle ON is unchanged — the umbrella
parent plus one transactional subtasks batch above. Toggle OFF creates each
leaf as a *root* task linked to the goal, through the SAME `POST /api/tasks`
core the plan-backward accept loop uses (looped per leaf, non-atomic like that
loop — roots have no parent to compensate for, and a mid-loop failure leaves
only valid roots, never a half-imported container), so the ADR-4 impact gate is
enforced identically: a goal-linked root may carry its reviewed per-task impact.
No server change was needed — both accept paths were already served by the two
existing write endpoints. The umbrella's default title also moved off the source
file onto the *goal* ("Machine Learning — generated plan"): the file name read as
an unrelated parent, the goal names the work. Impact itself became editable at
review in the same issue (the shared `StarPicker`, replacing the read-only star
text in every AI review panel) — ADR-14's contract is that the AI proposes and
the user reviews, and impact was the one field the model guesses that could not
be corrected; the impactSource "(model estimate)" annotation is dropped once the
user touches the picker.

*Amendment (#167): cross-parent moves of a childless task are a first-class
gesture.* The reparent matrix above always accepted a childless *subtask*
PATCHed to a new root — it requires a root target and a childless mover, never
that the mover currently BE a root. The client, however, had gated the whole
"Move under…" affordance on `parentId == null` (root-only), so moving a subtask
to a different parent needed two steps: promote to root, then nest. That gate
was cosmetic, not an invariant, and it made the common "wrong parent, fix it"
reorganization unintuitive. The client offer predicate (`offersMoveUnder`,
shared by the menu button and the drag-and-drop routing #101) now keys on
*childlessness* instead: any task with no subtasks — root or subtask — offers
the gesture, and a container (a task WITH subtasks) never does (it genuinely
cannot become a subtask, and the earlier root-only gate happened to *show* it
disabled — hiding it is both correct and cleaner). Consequences: a childless
subtask now nests under a different open root directly (drag onto the row, or
the "Move under…" menu); its own-parent drop stays blocked with
`ALREADY_UNDER_TARGET`, a subtask target with `TARGET_IS_SUBTASK` (one level
deep), and the reorder gap-zones (#157, ADR-43) still handle same-parent
ordering — gaps and rows are distinct drop spots, so the two gestures coexist
without collision. The moved subtask inherits the new parent's goal (and, while
open, category) through the same adoption write documented above; no server or
migration change was needed. The one-level-deep and childless-mover invariants
are unchanged — only the "subtasks cannot change parent" client restriction is
lifted.

== ADR-17: Snooze/block as retained timestamps, drawability stays derived

*Context:* Some tasks are temporarily undoable (waiting on someone, wrong
context); every redundant draw of such a card erodes trust in the deck. Cards
need a timed removal (snooze) and a manual-wake removal (block).
*Decision:* Two columns on `tasks` — `deferred_until` (nullable ISO timestamp)
and `blocked` (0/1) — extend the drawable predicate (ADR-2):
`blocked = 0 AND (deferred_until IS NULL OR deferred_until <= now)`. There is
no stored "snoozed" state: an expired snooze re-enters the pool with *no
write*, and `deferred_until` is deliberately *retained* after expiry as the
wake timestamp. `stalenessFactor` uses
`max(created_at | last_completed_at, deferred_until)` as its base date, so
snooze time never counts as "lying around" and a woken card returns without an
unfairly boosted weight. The client's "Wake" action PATCHes
`deferredUntil = now` (not `null`) plus `blocked = false`, giving manually
woken cards the same staleness treatment. Completing a task — including
recurring ones, which stay open (ADR-6) — and reopening a done task clear
both fields; on the recurring path the card is nonetheless out of the deck
afterwards, because its advanced due date is its next occurrence (ADR-6
amendment, #205) — a *derived* sleep, so no snooze state survives the
completion that a later cycle would inherit. The empty-pool fallback count
applies the same predicate, so a
pool of only snoozed/blocked cards reports `no_ready_tasks` (they come back on
their own) instead of steering the user into breakdown with `all_too_big`.
The restore validation for the persisted current draw (ADR-13, `isRestorable`)
rejects snoozed/blocked cards, so snoozing the drawn card also drops it from
reload-restore — and because a snooze wears off on its own, the PATCH route
clears the pointer *eagerly* (the wear-off would otherwise slip past ADR-13's
lazy validation and resurrect a card the user explicitly sent away). A
`dueDate`/`recurEveryDays` edit joins that eager clear since #205: scheduling
the drawn card into a future occurrence takes it out of the deck with the same
wear-off shape. The 💤/⛔
badges and the client's `classifyTask` group `snoozed` (precedence container →
snoozed → needs-estimate → too-big → ready) are derived the same way; client
and server predicates are pinned by shared test vectors
(`shared/drawableVectors.ts`) run in both suites.
*Rationale:* Retaining the expired timestamp gives a correct staleness base
for free — one comparison instead of an extra "woken at" column and expiry
writes that could drift (the ADR-2 argument). A separate `blocked` flag
instead of a sentinel far-future date keeps "indefinite" semantically honest
and trivially queryable.

== ADR-18: Sequential subtask mode as one parent column, hold-back stays derived

*Context:* Many breakdowns are inherently ordered (outline → draft →
proofread) — drawing step 3 before step 1 makes the card useless — while
others are independent chores. The AI breakdown already emits subtasks in
execution order, which the draw ignored.
*Decision:* One column on the parent — `subtask_order_mode`
(`'parallel'` default | `'sequential'`) — and *no* per-subtask state. For a
sequential parent only the first open subtask in creation order
(`created_at ASC, id ASC` — the id tie-break keeps batch-inserted siblings
deterministic) enters the draw pool; later open siblings are *held back* by a
derived `NOT EXISTS(older open sibling under a sequential parent)` predicate
(ADR-2), mirrored as the query-time `heldBack` field, the client's `queued`
group (precedence container → snoozed → queued → needs-estimate → too-big →
ready; an explicit snooze outranks the derived queue position, keeping the
Wake affordance visible) and the ⏳ chip. Completing the exposed step frees
the next one with *no write*. A snoozed first subtask still gates its
siblings — "in order" means in order; the empty-pool reason stays honest:
held-back siblings never count toward `all_too_big` (they surface by
finishing the step in front, not by breakdown), while an oversized *exposed*
first step still does. `isRestorable` (ADR-13) rejects held-back cards
lazily — unlike a snooze wear-off there is no path where a held-back card
becomes restorable again without a user action that legitimately frees it,
so no eager pointer clear is needed — reparenting the drawn card into a
held-back position (#100) is the exception: like a snooze wear-off, the card
would become restorable again the moment the step in front completes, so the
reparent PATCH clears the pointer eagerly. Manual ordering stays out of scope
(creation order only, no `position` column); reparenting (#100) keeps that
rule — a task adopted into a sequential breakdown queues by its original
`created_at` like every other sibling, so a task older than the existing
steps enters *ahead* of them and may jump the queue. One predicate, no
stored positions; explicit sibling ordering remains a possible follow-up if
queue-jumping proves wrong in practice. Split-in-place (#108) leans on the
same mechanism as a deliberate trick: the parts of a split subtask adopt the
original's `created_at` *verbatim*, so they sort into the original's queue
slot — splitting step 2 of 5 must not make its parts run after steps 3–5 —
while their new, higher ids keep the parts themselves in array order via the
id tie-break. In-slot placement is exact whenever sibling timestamps differ
(breakdowns grown over time, and any sibling created after the original).
*Known approximation:* batch-created siblings share one `created_at` string
and are ordered purely by id, and there is no `(created_at, id)` value
between `(T, id5)` and `(T, id6)` for a new row with a higher id — exact
placement inside such a group is impossible without mutating sibling rows,
so parts land at the *end* of the same-timestamp group, still ahead of every
later-timestamp sibling. Accepted and documented; if it bites in practice,
the explicit `position` column above is the named escalation. Adopting
`created_at` also inherits the original's staleness base (up to ×2) —
deliberate, consistent with ADR-17's wake semantics: the work has genuinely
been lying around since then. The "Do in order" toggle
travels with the breakdown batch (`orderMode` on `POST /:id/subtasks`,
persisted on the parent in the same transaction) and as a plain
`subtaskOrderMode` PATCH; the AI breakdown returns an `orderMatters` boolean
that only pre-sets the toggle — the user has the last word. Client and
server predicates stay pinned by the shared vectors
(`shared/drawableVectors.ts`).
*Rationale:* A per-parent mode captures the actual property ("this breakdown
is a sequence") with one write and zero synchronization; per-subtask
dependency edges would be bookkeeping for a capability (arbitrary DAGs) the
product explicitly does not want. Deriving hold-back keeps every mutation
path (complete, reopen, delete, re-parent, toggle) automatically correct —
the ADR-2 argument once more.

*Amendment (#157, ADR-43):* the "creation order only, no `position` column"
scope above is superseded — the named follow-up landed. Sibling order is now
STORED in `tasks.sort_order` and read as `(sort_order, id)`; `heldBackSql` and
the child listing key off it, and subtasks are drag-reorderable
(`POST /:id/reorder`). Backfill = `id`, so the queue reads identically to the
`(created_at, id)` era on migration day. The wear-off pointer clear this ADR
describes for a reparent into a held-back slot now also fires on a reorder that
strands the current draw. Roots stay out of scope (root order is creation
order — no queue over roots). See ADR-43.

== ADR-19: MCP adapter speaks HTTP to the local API; the client's approval flow replaces staged review

*Context:* Issue #36 exposes Draw's domain operations to MCP clients (Claude
Code, Claude Desktop). The MCP process could have opened the SQLite file
directly — WAL makes a second better-sqlite3 process technically safe — but
the domain invariants live in the Express layer, not in importable services:
the complete-with-open-subtasks 409 and the XP/achievements/recurrence path,
the single-running-timer rule, the draw's `last_drawn_at` stamp and
achievement check. A direct-DB adapter would have to duplicate all of that
(and run `migrate()` a second time). Separately, unlike the in-app AI, an MCP
client has its own per-tool-call approval conversation.
*Decision:* The MCP server (`server/src/mcp.ts`, stdio transport,
`@modelcontextprotocol/sdk`) is a thin adapter: every tool call maps to an
HTTP request against the running local API (`DRAW_API_URL`, default
`http://127.0.0.1:3001`), so the >30-minute drawability rule, impact
semantics, timer invariant, and gamification hold *identically by
construction* — it is literally the same code path the web UI uses. The tool
vocabulary lives in an SDK-free catalog (`server/src/tools/catalog.ts`, no
MCP and no Anthropic imports) so #31 can bind the same contracts to staged
executors; this surface binds live HTTP executors because the MCP client's
tool-approval conversation IS the review surface — every write is shown to
and approved by the user in the client, so staged changesets would review
twice. Destructive operations are omitted entirely (no delete tools; key
management is never exposed); read tools carry `readOnlyHint: true`,
`draw_card` deliberately does not (it stamps `last_drawn_at` and can unlock
achievements), and nothing is marked destructive. Read-heavy state ships as
resources: `draw://deck` (backed by the new side-effect-free
`GET /api/draw/pool`, reusing the ADR-2 candidate query), `draw://gamification`,
and `draw://materials/\{id}`. No `ANTHROPIC_API_KEY` is needed anywhere — the
intelligence is the MCP client's. The `update_task` pause/wake binding follows
this same boundary: MCP passes `deferredUntil` and `blocked` through one HTTP
PATCH without its own clock, normalization, or pause state; ADR-17 remains the
authoritative source for timed/indefinite pause, automatic expiry, retained wake
timestamps, `blocked` precedence, and the manual-resume pair.
*Rationale:* Trade-off accepted: the dev server must be running —
`ECONNREFUSED` maps to an actionable tool error naming `npm run dev`. In
exchange, no invariant is duplicated, no second migration runner exists, and
the drawability predicate keeps its single home (ADR-2). Direct writes
without staging are safe precisely because the approval conversation moved
into the MCP client; the in-app AI keeps checkbox review (ADR-14) because the
web UI has no per-call gate. stdout stays a pure JSON-RPC channel (logs on
stderr), and loopback-only remains untouched (section 2) — the MCP server is
a local process talking to a local API.

== ADR-20: Availability windows on the local wall clock, filtered in TypeScript

*Context:* Some tasks are only doable at certain times — calling the doctor's
office works Mon–Fri 08:00–12:00 — but the deck held such cards around the
clock, and drawing them at 21:00 wasted the draw (the recurring cousin of the
one-off problem ADR-17 solves). Time semantics in the repo are mixed: due-date
urgency parses local wall clock, stats arithmetic is UTC.
*Decision:* One optional window per task: `window_days` (JSON array of JS
`getDay()` integers, 0 = Sunday) plus `window_start`/`window_end` (`"HH:MM"`),
all three set or all three NULL (API-enforced all-or-none; `windowDays: null`
clears). Semantics are deliberately **local wall clock** — the app is a local
single-user tool, so "Mon–Fri 08:00–12:00" means the user's own clock,
consistent with due-date urgency. Corollary: the check lives in
**TypeScript**, never SQL — SQLite's `strftime('%w','now')`/`time('now')`
evaluate in UTC and would shift the window by the user's offset. The shared
candidate query (ADR-2) selects the three columns and one exported pure
predicate (`isWithinWindow`) post-filters the rows for both `drawTask()` and
`drawPool()`; the same predicate guards `isRestorable` (ADR-13, lazy pointer
clear like an expired snooze in reverse) and is mirrored in the client as the
`scheduled` classify group (precedence container → snoozed → queued →
scheduled → needs-estimate → too-big → ready; explicit snooze and queue
position outrank the schedule). Both sides are pinned by shared vectors
(`shared/drawableVectors.ts`) — window vectors are expressed as *offsets*
relative to "now" and materialized per run, because fixed weekdays would make
the suites timezone-dependent. Boundaries are `[start, end)` — start
inclusive, end exclusive — with `"24:00"` allowed as end-of-day, so
`00:00–24:00` is a full day and future back-to-back windows cannot overlap.
`end <= start` is rejected (400): with a weekday set, a midnight-crossing
window is ambiguous (does Mon 22:00–02:00 need Tuesday selected?); resolving
that only pays off with multi-window support, the designated follow-up — a
night window is approximated as `22:00–24:00`. Weights are untouched: the
window is hard pool membership, an overdue windowed card keeps its ×5 urgency
inside the window and does not exist outside it. The empty-pool dispatch
gains `all_outside_window`, reported whenever the SQL query produced
candidates and only the window filter emptied the pool — those cards return
on their own, so the "break something down" hint would mislead; a card that
is oversized *and* out-of-window still counts toward `all_too_big`, because
waiting will not fix it. The window gates the draw only: manual timer start
and completion work at any time.
*Rationale:* A derived, wall-clock predicate keeps every mutation path
automatically correct (the ADR-2 argument), needs no scheduler or background
job to "reopen" cards, and no write when a window opens or closes. The
TypeScript placement trades one SQL-side filter for immunity against the
UTC/local mismatch that already bit the repo elsewhere (`isDueSoon` vs.
`urgencyFactor`).

== ADR-21: Activity history derived read-side, bucketed by local day

*Context:* The gamification layer only showed *today* (trophy pile, #40) — at
midnight the pile evaporates. The house-of-cards skyline (#53) needs a
permanent, browsable per-day record of started and completed tasks, including
the "abandonment trace": a task worked on but not finished that day stays
face-down on that day forever.
*Decision:* No new tables, columns, or write paths — `GET /api/activity`
derives everything read-side from `time_entries` and `completions` (the ADR-5
argument extended to history). The card set for local day D is *tasks with a
time entry started on D* UNION *tasks completed on D*; the union keeps
timer-less completions (PATCH status to done) visible. `completed` on a card
means "a completion exists on that same local day", so an entry-only day stays
face-down permanently and a later completion earns only that later day an
upright card. Days bucket by **local** day, not UTC: the skyline is a
human-facing record like streaks (`date(..., 'localtime')`), unlike the
deliberately UTC-bucketed `/api/stats` ranges — which is also why activity is
its own endpoint instead of a stats extension. Bucketing lives in one pure
function (`localDayOf`, offset injectable for tests); SQL only pre-filters on
a UTC window widened by a day per side. Tracked minutes reuse the stats
`MINUTES_EXPR` (running entries count up to now); midnight-spanning entries
attribute to their start day; per-day `totals` ride along for day-level
consumers (born for the #54 heatmap; the merged Stats page's activity view
keeps consuming them — the skyline through #155/ADR-41, the History
contribution calendar since #174/ADR-45).
Accepted limitation: deleting a task cascades its entries/completions away and
with them its history — we do not add write-path tracking to preserve it.
*Rationale:* Deriving keeps history incapable of contradicting its sources
(no counters to drift, reopen/undo just works), and local-day bucketing puts a
23:30 task on that evening's tower — the emotional ledger the feature exists
for.

*Amendment (#174):* the read model and local-day bucketing described here are
unchanged; only the UI consuming them changed — the house-of-cards skyline
became the History contribution calendar (ADR-45).

== ADR-22: Card art as sanitized, model-written SVG — cached once per task

*Context:* The drawn card is the app's emotional centerpiece, but its back
face was a static CSS gradient. Unique, subtly themed artwork per card makes
drawing feel like a real card game and rewards the reveal. Two constraints
shape the design: the Claude API generates text, not raster images, and model
output must never reach the user's DOM as live markup.
*Decision:* The artwork is SVG markup written by Claude through the existing
structured-output pipeline (`cardArtSchema`, its own `CARD_ART_SYSTEM_PROMPT`
— neither planning nor transcription directives apply to art — 6K
`max_tokens`, same `MODEL`), themed from task title + category name and color
(+ goal title when linked) on the dark app palette so all cards read as one
deck. Security is two *independent* layers. First, allowlist sanitization
server-side (`svgSanitizer.ts`, pure module) **before storage**: the untrusted
string is tokenized and a new document is re-serialized from scratch — only
allowlisted elements (shapes, gradients, filter primitives) and allowlisted,
value-validated attributes are emitted; `<script>`/`<foreignObject>`/`<image>`
subtrees, `on*` handlers, non-fragment `href`/`xlink:href` (`javascript:`,
`data:`, external URLs), non-`url(#id)` CSS references, text nodes, comments,
CDATA and DOCTYPE/entity declarations are all dropped, so nothing that was not
deliberately emitted can survive. Second, the client renders the stored SVG
exclusively as `<img src="data:image/svg+xml,...">` — an image context never
executes scripts — and `dangerouslySetInnerHTML` of model output stays banned
repo-wide. Generation happens at most once per task: `card_art (task_id
PRIMARY KEY REFERENCES tasks(id) ON DELETE CASCADE, svg, created_at)` caches
the *sanitized* markup (schema v6); concurrent first views race benignly —
first writer wins. Failed sanitization is a 502 and is *not* cached, so a
later view retries instead of pinning a broken background. The reveal never
waits: the card flips instantly with the default gradient, `useCardArt` fires
only once revealed, and the art fades in over the gradient behind a legibility
scrim whenever it arrives. Every failure — including 503 `ai_not_configured`
without a key — resolves silently to "no art".
*Rationale:* SVG-as-text keeps the feature inside the one approved AI channel
(`aiService.ts`, ADR on structured outputs) with no new provider, dependency
or raster pipeline. Sanitize-before-store means the database only ever holds
markup that is safe to serve forever, independent of future render paths; the
img-data-URI render makes the browser enforce the same guarantee a second
time. The once-per-task cache bounds cost (one generation per card, ever) and
keeps a card's identity stable — the same task always reveals the same art.

*Amendment (#113 — variety and regenerate):* One fixed recipe in the system
prompt ("the single accent", one open-ended abstract-themes list) made every
generation converge on the same image — user verdict: "All look the same …
not really adding any benefit". The look now arrives per request as
deterministic style directives (`cardArtStyle.ts`, pure): a named archetype
(layered geometric, organic curves, constellation, gradient mesh, brush
strokes, prismatic shards, contour lines), a palette *harmony* built from the
category color (analogous/complementary/split-complementary) replacing the
single-accent rule, and density + focal-placement composition directives —
each selected by a salted FNV-1a hash of the task id, so the same task always
gets the same style (cache coherence; a regenerate re-rolls the execution, not
the identity) while different tasks spread across genuinely different
recipes. The pinned id→style mapping is append-only: reordering existing
entries would silently change existing cards' character. Focal placements all
bias upward because the TCG frame (#115) will present the art through a
portrait window; the system prompt keeps only the hard rules (no text, no
external references, `viewBox="0 0 300 420"`, dark base, scrim legibility) and
now states the portrait bias. `CARD_ART_MAX_TOKENS` rose 6K→8K for the dense
archetypes; the sanitizer's 64 KB input guard was reviewed in the same change
and stays (still ~2× a maximal generation). The regenerate action deferred in
#27 exists now: `POST /api/tasks/:id/card-art/regenerate` is the ONLY path
that replaces a `card_art` row, strictly generate-then-replace — any
generation or sanitization failure throws before the write, so the old art
always survives. At most one generation is in flight per task across both
endpoints (`cardArtService` coalesces concurrent callers onto one promise);
the GET keeps its at-most-once semantics — a cache hit never regenerates.
Client-side the ↻ button overlays the drawn card's corner — deliberately on
the 2D `.draw-scene`, NOT inside the 3D flip faces, whose
`backface-visibility` context Chromium does not hit-test reliably (caught in
live verification: a button inside the face was visually present but
unclickable). It renders only when art exists (degraded mode shows nothing,
keeping the silent-failure contract) and swaps the query cache from the
mutation response.

== ADR-23: Recurring subtasks are banned under sequential parents

*Context:* A recurring task never closes on completion — `completeTask`
advances its due date and keeps it open (ADR-6). ADR-18's hold-back predicate
frees a sequential sibling only when every older sibling stops being open. In
combination (issue #66, flagged in PR #63): a recurring step inside a
sequential breakdown gates every later sibling *forever* — as the first step
it deadlocks the whole queue from day one, and in any later position the same
trap merely waits until the steps in front close. Conceptually the
combination is confused: a sequential breakdown is a one-shot pipeline
(outline → draft → proofread) that finishes, while a recurring chore never
does — "position in the pipeline" has no meaning across recurrence cycles.
The alternatives were considered and rejected. (a) "a completed-this-cycle
recurring step counts as done for queue purposes" breaks the queue's own
promise: pool eligibility has never depended on due dates (they only weight
urgency), so the recurring step itself would stay drawable *next to* the
sibling it just released, and the derived predicate would need completion
history — which the client mirror (`classifyTask`) does not have, breaking
the ADR-2 parity pinned by `shared/drawableVectors.ts`. (c) "cycle completion
releases the queue until the next due date" makes hold-back time-dependent:
when the next cycle comes due mid-pipeline, already-released siblings would
be re-gated with no user action — cards oscillating in and out of the deck.
*Decision:* The combination is *rejected with 400* on every path that could
create it, in the routes where all domain invariants live: creating a subtask
with `recurEveryDays` under a `sequential` parent (`POST /api/tasks` with
`parentId`; the batch endpoint's INSERT carries no recurrence at all), adding
a recurrence to an existing subtask of a sequential parent (`PATCH`),
reparenting a recurring task into a sequential breakdown (`PATCH parentId`,
#100 — judged on the effective recurrence, so clearing the recurrence in the
same PATCH legalizes the move), and
flipping a parent to `sequential` — via `PATCH subtaskOrderMode` or the
breakdown batch's `orderMode` — while *any* subtask carries a recurrence
(any status: done and archived rows can be revived by a plain status write).
Only *transitions* are rejected: a pre-ban database keeps working — no-op
resends of a stored value pass (the edit form emits them, mirroring the
ADR-4 grandfathering), an already-sequential parent accepts its own mode
again, and the repair paths (clear the recurrence, flip to parallel) stay
open. No migration rewrites user data. The UI guards the same transitions:
the edit form hides the ↻ recurrence field on steps of a sequential parent,
and the order-mode flip button plus both breakdown editors' "Do in order"
toggles disable with the reason when a recurring subtask exists (server 400
surfaced inline as backstop). Recurring subtasks under *parallel* parents
stay legal — a never-completing routine container ("morning routine") is a
coherent use. Classification is untouched: `heldBack` stays purely
structural, so `shared/drawableVectors.ts` and both classify mirrors need no
change.
*Rationale:* A validation invariant names the modeling error instead of
bending the queue semantics around it — the same shape as ADR-16's
one-level-breakdown ban. Every alternative would have complicated the one
derived predicate ADR-2/ADR-18 keep deliberately simple, split server and
client eligibility semantics, and still left "what does order mean next
cycle?" unanswered.

== ADR-24: Legacy nested breakdowns are repaired by a startup migration, not grandfathered

*Context:* The #35 guard (ADR-16) stops *new* nesting, but databases that
acquired nested subtasks through the pre-guard API/MCP window stayed
pathological (#80, verified on a seeded 3-level tree): the grandchild is
draw-eligible yet invisible in every list, the root's remaining-effort rollup
contradicts its displayed children, the grandchild leaks past the sequential
hold-back queue while its visible siblings are held back, a root goal edit
cascades one level and leaves the grandchild's `goal_id` stale, and
completing the middle task 409s with no visible open subtask anywhere — an
undiagnosable dead end. Elsewhere legacy rows are tolerated (ADR-4 impact,
ADR-23 recurring-sequential), but those rows stay *operable*; a nested row
breaks derived state and had no user-reachable repair (at the time no
re-parent edit existed in any UI or API — #100 added one later, after every
stored database had already been repaired by this migration).
*Decision:* The v6 → v7 migration (`server/src/db.ts`) re-parents every task
whose parent is itself a subtask to its root ancestor — the exact flattening
the guard's 400 message tells callers to perform — one level per pass until
the tree is two levels deep everywhere (arbitrary legacy depth; terminates
because ancestor chains in the migrated data are acyclic and finite — every
pre-v7 database was written by code that only ever set `parent_id` at INSERT
referencing an existing row. Since #100 `parent_id` is also rewritten by the
reparent PATCH, but the guarantee carries over: a reparent target must be a
root and the moved task must be childless, so the moved node never becomes
anyone's ancestor and no cycle can be minted. The pass count is bounded by
the initial nested-row count anyway, so a corrupt cyclic chain
aborts the boot with a diagnosable error instead of hanging it). Re-parented
rows then join their new breakdown under the same cascade rules a parent
edit applies (routes/tasks.ts): `goal_id` follows the root unconditionally,
`category_id` only while open — done/archived rows keep the category they
were finished under (#44). The whole step runs in one transaction, and fresh
databases never enter it (schema.sql cannot express nesting the guard would
reject). Two side effects of the flattening are deliberate, not oversights.
First, hoisting a recurring row under a `sequential` root *mints* the
ADR-23-banned combination — the migration must not run the #66 guard (it
would fail the boot on exactly the legacy data the repair exists for), so
the flattened tree may contain a recurring step under a sequential root.
That state gets the same tolerated-but-repairable treatment ADR-23 grants
pre-ban rows: the row is visible and operable (no-op resends of the stored
recurrence pass), both user repairs stay open (drop the recurrence, or flip
the root to parallel), and the transition guards prevent re-creating it once
repaired — pinned by `server/test/integration/migration-v6-recurring.test.ts`.
Second, under a goal-less root the cascade leaves re-parented rows with
`goal_id` NULL and their stored impact untouched — deliberate grandfathering,
not route parity: a *deliberate* goal wipe resets impact to the neutral 3 (a
parent unlink cascades the reset to open subtasks since #76, and a #100
reparent into a goal-less root resets the moved task the same way), but the
migration moves rows the user never asked to move, so it keeps the
historical rating the way goal deletion keeps one, and the ADR-4 no-op
tolerance keeps such rows editable.
*Rationale:* Repair over grandfathering because every listed pathology is a
*silent* corruption of derived state (ADR-2's core promise) rather than a
stale-but-honest stored value, and the flattened result is exactly what the
user would have gotten had the guard existed all along. A read-side
tolerance (recursive rollups, deep cascades, recursive hold-back) would have
rebuilt the complexity ADR-16 banned to serve rows that should never have
existed.

== ADR-25: Draw weights are damped by the square root of the pool-sibling count

*Context:* A #29 import commits ~40 comparable fresh leaves under one
umbrella, each a full-weight pool candidate. Issue #30 mandated measuring
before touching the formula. The deterministic simulation
(`server/scripts/sim-issue30.ts`; deck pinned in `scripts/deckFixtures.ts`,
guarded by `test/unit/draw-weights.test.ts`) put such an import at 58% of
the probability mass on day 0 against a healthy 12-task organic deck — and
rising (63% after a week, 74% after a month), because the fresh leaves climb
the staleness ramp while the older organic tasks already sit at its ×2 cap.
Leaner-but-normal decks fared worse (67% without the deck's overdue chore,
72% against 6 organic tasks, 70% with a second 25-leaf import running in
parallel). Waiting doesn't heal it, and the existing escape hatches don't
either: the Draw page chips filter *into* the exam, not out of it, and
sequential mode (#23) fixes the flood outright (0.6% share) but #29 commits
default-parallel — deliberately, since exam exercises are independent.
*Decision:* `drawService.poolWeights()` — the single home both `drawTask()`
and `drawPool()` use — multiplies each candidate's weight by `1/sqrt(k)`,
where k is the number of same-parent siblings *in the candidate pool*, not
open siblings: held-back sequential steps (ADR-18), snoozed (ADR-17) and
out-of-window (ADR-20) siblings don't flood the deck, so they must not
dampen the one card representing them. k = 1 — every parentless task, only
child, or sequential front card — is exactly ×1, and `weight()` itself is
untouched. A 40-leaf import competes like √40 ≈ 6 cards (measured 18%
share), and the damping decays smoothly as leaves complete (20 left → 13%,
5 left → 6%) instead of the cliff a per-parent quota would create.
*Rationale:* sqrt is the mildest standard damping that keeps aggregate group
mass monotone in group size — a bigger breakdown still surfaces more often
in total (the exam *is* important; its best leaf still draws at ~1% per
draw), but sublinearly, so it can no longer starve chores and other goals:
distinct organic cards seen in a 10-draw session recover from 3.6 to 6.3 of
12, and a mid-weight organic card's chance to surface within 5 draws from
7% to ~13% (pre-import: 16%). Per-goal quotas and changes to the
urgency/staleness/cooldown factors were explicitly out of scope (#30).

== ADR-26: Backups are one zip — VACUUM INTO snapshot + material files; import swaps files with the DB rename as commit point

*Context:* All user data lives in `DATA_DIR`: the WAL-mode SQLite database
and the uploaded goal materials under `files/` (#61). Hand-copying `app.db`
while the server runs silently drops every commit still sitting in
`app.db-wal`, and a DB-only backup would restore `materials.stored_name`
rows that point at nothing. Restore is destructive by nature, and the app
has exactly one live `better-sqlite3` handle opened at module scope.
*Decision:* `backupService.ts` exports one archive: an `app.db` snapshot
taken with `VACUUM INTO` (the safe online-copy path under WAL — never a raw
file copy), every file under `files/`, and a `manifest.json` (app marker,
timestamp, `user_version`, row counts) that lets import reject foreign zips
up front. The `anthropic_api_key` settings row is deleted from the
*snapshot* only (ADR-11: it is stored plaintext, and backups get copied
around); the live DB keeps it. Import validates everything against staged
temp copies first — readable zip, our manifest, `integrity_check`,
`1 <= user_version <= CURRENT_VERSION`, required tables present, zip-slip
guard on `files/` entries — and only then swaps: checkpoint + close, delete
stale `-wal`/`-shm` (a leftover WAL would be replayed into the restored
database — the torn-DB hazard), *copy* `app.db` to `app.db.bak` (copy, not
rename: the live path never disappears, so a crash cannot boot into a fresh
empty DB), swap `files/` (previous kept as `files.bak`), and last the
staged snapshot is renamed onto `app.db` — a single same-volume rename, the
atomic commit point. The whole swap is one synchronous block:
better-sqlite3 is synchronous, so no request can interleave with a
half-swapped state.
*Rationale:* one archive keeps backups self-contained (acceptance was
export → wipe → import → byte-identical material files); validating on
staged copies means every rejection is a 400 with live data untouched; and
ordering the swap around a final atomic rename means a crash at any step
boots either the complete old state or the complete new state. `adm-zip`
handles both zip directions synchronously, fitting the no-framework
guardrails; `multer` (already a dependency) receives the upload.

*Amendment (#263, schema v18):* import accepts versions through v18 and rejects
anything newer. A v17-or-older archive is migrated in staging _before_ swap;
the staging handle must then prove the complete v18 runtime contract, including
both Gold owner columns, exact table CHECK/unique/AUTOINCREMENT definitions,
all six immutable trigger definitions and behavior, and
`idx_xp_ledger_reason`. Missing or weakened contracts are rejected while live
data remains untouched. Reopen after swap sees an already migrated, validated
file. Non-empty opening rows and `sqlite_sequence` survive round trips.

*Accepted limitation (#103):* `adm-zip` inflates each entry fully in memory,
so peak RSS during export/import scales with the largest entry — the DB
snapshot, plus one material at a time. Accepted, not fixed: this is a local
single-user app whose database is measured in megabytes, the alternative is
a streaming zip layer (a new dependency and an async rewrite of a
deliberately synchronous, non-interleavable swap), and the failure mode is a
loud OOM on a machine that is not serving anyone else. Revisit if materials
ever grow to gigabyte scale.
*Amendment (#103) — the interrupted and contended paths:* (a) Temp artifacts
(`backup-uploads/*`, `backup-import-*`, `backup-export-*`) are cleaned up in
a `finally` on every path, but a hard kill skips those and nothing else ever
collects them — each orphan being a whole snapshot or zip. `createApp()`
sweeps them by name prefix at boot, the one moment none of them can belong to
a live request; the uploads directory is emptied, never removed (multer
creates it once, at module load). (b) Temp stems are `<ms>-<counter>`, not
`Date.now()` alone: two exports in the same millisecond collided on one path,
and `VACUUM INTO` refuses an existing file, so the second died as a raw 500.
(c) The single-process assumption above is now verified instead of assumed:
SQLite deletes `-wal`/`-shm` when the last connection closes, so if they
survive our `close()` another connection is still attached — the import
aborts with a 409 before the first destructive step rather than deleting a
WAL that connection is still writing into and swapping a different file
underneath it.

== ADR-27: Estimation coaching is read-only advice — hints never mutate, weights stay on stated estimates

*Context:* The estimation block (ADR-15) measures per-category
estimated-vs-tracked bias but stops short of coaching: nothing said *which
kind* of work the user habitually misjudges, and nothing helped at the moment
that matters most — while typing a new estimate (#55). The obvious stronger
designs — pre-filling the corrected value, or letting the draw weigh tasks by
bias-adjusted "effective effort" — both make the system silently disagree
with the user's stated plan.
*Decision:* Coaching is strictly read-only, in two surfaces. The Stats page
renders a plain-language per-category statement ("Uni: tracked 1.4× estimated
over 6 tasks — pad your Uni estimates") and TaskForm shows a dim, passive
hint under the effort field ("history suggests ~45 min") once the entered
estimate diverges more than 25% from the category's all-history ratio. Both
gate on a minimum sample of 3 qualifying tasks; below it nothing renders, not
even a placeholder. The hint never rewrites the field, never blocks submit,
and the submitted `effortMinutes` is exactly what the user typed. Draw
weights keep using stated estimates — an explicit non-goal fence. The
all-history numbers come from a dedicated lightweight endpoint
(`GET /api/stats/estimation-bias`) that reuses the estimation block's
qualifying rules and per-cycle attribution (ADR-15, #48) with open-ended
bounds, rather than stretching the range-scoped `/api/stats` payload;
thresholds and wording live client-side in the pure
`client/src/lib/estimationCoach.ts`. The server returns every category with
its `taskCount` — showing or hiding is a display decision.
*Rationale:* Passive advice over auto-correction because the estimate is the
user's commitment, the same principle that keeps the draw un-rerollable
(#88): tooling may inform the plan, never quietly rewrite it — and a
pre-filled "corrected" estimate would poison the very tracked-vs-estimated
feedback loop it learns from. Weights stay on stated estimates because
bias-adjusting them would move cards between the ready/too-big piles based on
invisible arithmetic, contradicting ADR-2's promise that drawability is
explainable from what the user can see. A dedicated endpoint over reusing the
stats query because TaskForm mounts on four surfaces and needs one small,
stably-cacheable all-history array — not a week-scoped Stats object whose
range semantics the hint would have to fight.

== ADR-28: Streak rest days and freeze tokens — the streak stays derived, only earned freezes are state

*Context:* The streak broke on any local day without a completion, including
days off the user planned on purpose (#58). Punishing a deliberate Saturday
teaches users to stop trusting the flame — but the fix must not violate
ADR-2/ADR-5: no stored streak counter, ever, and `GET /api/gamification`
must stay side-effect free.
*Decision:* Three parts. (a) *Rest weekdays* are a plain setting
(`streak_rest_weekdays`, JSON array in JS `getDay` convention, same as
`tasks.window_days`; `PATCH /api/settings` rejects all 7 — at least one
weekday must stay required). A rest weekday without a completion neither
breaks nor extends the run; one *with* a completion counts +1 like any other
day, so resting is never better than completing. (b) *Freeze tokens* are
genuine state, but only the EARN side: `streak_freezes` is an append-only
log of earned events (v8 migration), one row per 7-real-day milestone with
the milestone's local day under a UNIQUE constraint — earning is idempotent
per milestone, so complete → reopen (`undoLatestCompletion`) → complete
again cannot farm tokens; the bank caps at 2 banked. *Consumption is
never stored:* every read re-runs a deterministic fold (the pure
`computeStreak()` in `streak.ts`) that replays the calendar FORWARD from
the earliest completion/earn day with the bank as a plain counter: an earn
adds a token (clamped to the cap inside the fold, so re-aggregation under a
changed rest setting can never resurrect a token past it), a missed
non-rest day inside a run consumes one banked token (earns bank only after
their own day is classified, so a token covers strictly later days — never
the day it was earned on or earlier), and a miss the bank cannot cover is a
break: the run dies and the bank expires with it, so a dead run's tokens
never shield a later streak and letting a streak die can never increase the
balance (a broken gap consumes nothing — it expires, Duolingo-style).
Today-in-progress still neither breaks nor consumes, and the replay is
bounded by the earliest recorded fact, so even 6 configured rest weekdays
terminate. The first cut walked BACKWARD, assigning each missed day the
oldest unconsumed token earned strictly before it (issue #58's suggested
reading), but the PR #98 review proved that shape wrong twice: the
assignment flipped between reads — a new miss could steal the token that
covered an older, already-frozen day and retroactively break the run there
despite a feasible cover — and consumption inside runs the walk never
reached evaporated, resurrecting dead runs' tokens past the cap. The
counter-based forward replay is assignment-free (any feasible cover banks
the same count, so coverage is maximal) and prefix-stable: a new miss can
only affect days after the previous read, never rewrite committed
history. (c) The streak number counts REAL completion days only — rest
and frozen days keep the run alive but never increment it — and the API
exposes `todayKind`/`frozenDays`/`restDays`/`freezesBanked` so the client
renders four honest flame states instead of presenting covered days as
completed. `streak_7`/`streak_30` keep testing `currentStreak() >= N`,
which now means N completed days possibly spanning more calendar days;
their copy says so, and already-unlocked rows stay (append-only table).
*Rationale:* The earn events are facts (like `completions` rows) — they
happened and survive an undo; a stored "banked" counter or consumed-rows
would be writable from a GET path or need provably idempotent writes, the
exact drift ADR-5 exists to prevent. Deriving consumption keeps reads pure,
re-aggregatable, and auditable, and the append-only log plus UNIQUE
milestone day is the entire anti-farming story — no trigger, no counter,
no reconciliation job.

*Amendment (#263):* historical shop freezes remain replay facts: only
`xp_ledger.reason='buy:freeze'` timestamps are converted by the existing local
calendar-day function and merged with milestone days. No other XP-ledger reason
and no `pack_openings.effective_bonus` participates before #266; the ordered
cap-2 fold, consumption, rest-day and expiry semantics are unchanged.

== ADR-29: Focus mode is a derived view — timer plus current draw decide, nothing is persisted

*Context:* Focus mode (#56) flips the drawn card into a fullscreen countdown
with the timer already running. It must survive reloads the way the drawn
card (ADR-13) and the TimerBar already do, and it must not invent tracking:
focus sessions are ordinary `time_entries`.
*Decision:* The client never stores "in focus". The view is a pure function
(`client/src/lib/focusView.ts`) of two facts the server already persists —
the current draw (ADR-13) and the running timer (6.4) — plus one
session-local "exited" flag for Escape: timer on the drawn card and not
exited → fullscreen; timer missing or on another task → plain revealed
card; no draw → idle deck. A reload re-derives: mid-focus it lands back in
the overlay, after a Stop it lands on the revealed card, and after an
Escape it re-enters focus. The Escape flag deliberately does NOT go to
sessionStorage: while the timer runs on the drawn card, "working on this
card" is the truthful state — Escape is a transient peek at the rest of the
app, and a persisted flag would be exactly the derived-state drift ADR-2
bans, going stale the moment the timer changes from a second tab. The
countdown is sized to `effortMinutes` but display only: crossing zero flips
to a visibly distinct overtime count-up and never stops the timer or
completes the task (estimates are guesses — ADR-27 — and punishing an
overrun teaches padding); a missing estimate degrades to a plain count-up.
The in-face actions ARE the existing DrawPage actions, not copies: ✓ Done
is the same completion PATCH (entry closed server-side, ADR-12, drawn bonus
from the persisted draw), ■ Stop the same `POST /api/timer/stop` (the
persisted draw is untouched, the card stays restorable). No new endpoints,
columns, or tracking paths — focus sessions flow into the #22 estimates-vs-
tracked stats as plain entries, overtime simply reads as a ratio > 1.
*Rationale:* A persisted focus flag would duplicate what timer + draw
already say and could contradict them (a dead overlay counting down for a
stopped timer). Deriving keeps the invariant surface unchanged — one
running entry, one persisted draw — and the whole feature stays client-only.
*Amendment (#110):* The same principle extends to the standing revealed
card itself: the DrawPage derives it continuously from the persisted
current draw (`resolveDrawnCard`, `client/src/lib/drawnCard.ts`) instead of
a mount-time snapshot, so completing, snoozing, or deleting the drawn task
on ANY surface — TimerBar, Tasks page, MCP, a second tab — dismisses the
card on the next refetch of the current-draw query: mutation invalidation
in-app, window focus or the 60s interval where no invalidation fires
(cross-tab/MCP latency of up to a minute is accepted). The draw animation
still reveals off the mutation response (written through to the query
cache on success), celebration stays with the acting surface (confetti
fires only for the page's own ✓ Done), and #88's sanctioned escape is the
one session-local hold: a card edited out of the deck forfeits its pointer
(cleared lazily, as before) but stays on screen with the resolve hint
until resolved on-page — an edit must not become a hidden re-roll.

*Amendment (#118):* Two consequences of deriving that were intended but
undocumented. (1) The pointer's restore validation (`isRestorable`) is
evaluated at GET time against `new Date()`, so forfeits are TIME-based, not
only action-based: an availability window closing (ADR-20) or a sequential
sibling change that holds the card back (ADR-18) invalidates the pointer
with nobody touching anything, and the standing card then evaporates on the
next refetch — mid-session, unprompted. Intended: a card the deck would no
longer deal is not a commitment the user can honour right now, and the
alternative (freezing a card the rules have retired) is the stored-state
drift ADR-2 bans. (2) The 60s cadence is the FOCUSED-tab cadence: React
Query pauses `refetchInterval` while the tab is in the background
(`refetchIntervalInBackground` stays off), so a card resolved from MCP or a
second tab is dismissed on the hidden tab's next window focus rather than
within the minute — the accepted latency above is a foreground promise.
The one hold releases the same way: while it stands, the pointer is already
forfeit and cannot report the held card's fate, so the page watches the
tasks list instead (`heldCardResolved`, gated on the hold, same 60s
cadence) and drops the card once it is gone or no longer open — a card
completed or deleted elsewhere used to stick until a reload, with every
on-page resolution 404ing. A resolution that races the watch and 404s is
read as the same dismissal arriving by the other door, not as an error.

== ADR-30: The warm-up draw is a deterministic deal — cooldown as exclusion, XP capped below the drawn ×1.5

*Context:* The main draw is a gamble: it can serve a 30-minute card when
even ten minutes feels impossible. The warm-up (#57) is the "I can't start"
escape hatch — one secondary click on the IDLE Draw page deals the
objectively smallest eligible card. It must not become a re-roll (#88), a
fishing rod for comfortable cards, or the XP meta.
*Decision:* (a) `warmupDraw()` reuses `queryCandidates()` — the exact
eligibility pool of the weighted draw — but picks deterministically:
minimum `effort_minutes`, tie-broken by most stale using the same
`stalenessAnchor` the weight formula uses (creation, last completion for
recurring tasks, bumped by a snooze wake — one definition of "stale",
shared by construction), final tie-break lowest id. Impact, urgency, and
the staleness weight are deliberately bypassed: the point is the smallest
card, not a clever one. (b) The draw cooldown applies as EXCLUSION, not the
regular ×0.15 dampening — a dampener is meaningless for a deterministic
pick, and exclusion prevents deal → discard → deal-the-same-card churn; an
exclusion-emptied pool answers `cooling_down`. (c) The deal is the same
commitment as a draw: `last_drawn_at` stamped, persisted as the current
draw (ADR-13, focus mode included), resolvable only via complete, snooze/
block, or delete — and the route rejects a deal while a valid current draw
exists, so the warm-up only ever exists on the idle deck (#88). A marker
(internal settings key next to the pointer: task id, dealt-at, bonus-window
minutes) is cleared everywhere the pointer is cleared and overwritten by
every regular draw, so it can never describe a card that is not the current
draw. (d) One deal per `warmup_every_hours` (public setting, default 8),
consumed irrevocably AT DEAL TIME — discarding the card does not refund the
allowance. The setting takes non-negative integers, and *0 is a documented
off-switch* (#103): "always available" is a coherent choice — (c) still
refuses to deal while a card stands, so an unlimited allowance loosens the
pacing, never the commitment. Negatives and non-numeric values are rejected
rather than silently doing the same thing (a negative disabled the limit
while reading like one; a non-numeric string fell back to 8 unannounced).
(e) XP: a warm-up completion NEVER earns the drawn ×1.5 (it was
handed out, not gambled — the `last_drawn_at` stamp of the deal is also
excluded from the 6-hour drawn heuristic by exact-timestamp match): inside
its window (`max(effort at deal time, 15)` minutes) ×1.25, late ×1.0.
Completing any OTHER task within 30 minutes of a warm-up completion earns
momentum ×1.25, combining with the drawn bonus but capped at ×1.5 total.
Momentum never applies to a warm-up completion itself. Momentum is derived
from `completions.was_warmup` rows at completion time, never stored —
reopening the warm-up deletes its completion and disarms momentum
automatically (ADR-2/ADR-5). (f) Display derivations agree with the XP:
everywhere a completion is surfaced as "drawn" — the trophy pile's rarity
and "(drawn)" label (#62), the History calendar — drawn-ness reads
`was_drawn AND NOT was_warmup` at query time. The completion row keeps both
raw facts (the card WAS the persisted current draw, and it got there by
deal), so a warm-up impact-5 completion mints no foil, exactly as it earns
no ×1.5.
*Rationale:* The invariant the multipliers encode: no completion ever
exceeds ×1.5, and a warm-up caps at ×1.25 — strictly below the gamble — so
the escape hatch can never out-earn playing the deck. Exclusion-not-
dampening and deal-time consumption close the two farming loops a
deterministic pick would otherwise open (re-dealing the same card, and
discard-until-happy). Reusing the pool predicate and the staleness anchor
keeps one definition of "eligible" and "stale"; reusing the current-draw
machinery keeps one commitment lifecycle — the warm-up adds a marker and a
rate limit, not a second draw system.

(PR #117's discovery); horizontal scrolling would clip the #47 lift

hides trophies on a reward shelf.
*Rationale:* Presentation-only derivation keeps every invariant that
already holds: the #47 lift stays transform + z-index with no layout shift
(art/scrim/sheen are absolutely positioned overlays), rarity stays a
render-time function, and no new state can drift. The one deliberate
duplication-removal: the drawn card's effort chip and star badges are
absorbed by ATK and the star row (one datum, one place); the focus overlay
(#56) adopts exactly the type-line pill and nothing else — its job is the
clock, not the frame. Follow-ups noted in their issues: the skyline
mini-cards (#53) and the daily hand (#59) adopt the frame when built.
*Amendment (#147):* the daily hand was since removed (ADR-39) — that

*Amendment (#174):* the skyline was itself replaced by the History

== ADR-32: Parent-task lifecycle follows the subtasks — derived effort, auto-complete at a symbolic 1 XP, reopen on new subtasks

*Context:* Explicit user feedback (#111): a broken-down task's estimate
should just be its subtasks' estimates, finishing the last subtask should
finish the task, and adding new ones should reopen it. Before this decision
all three were violated: `remainingEffortMinutes` fell back to the parent's
own stored estimate the moment the last subtask closed (and the parent
re-entered the draw pool as if it were a leaf), the parent then had to be
completed manually — earning XP from its own `effort_minutes ?? 10` on top
of the effort-XP the subtasks had already paid — and creating or adopting a
subtask under a done parent reopened nothing (#104 item 1).
*Decision:* One lifecycle package, three rules. *(1) The subtasks own the
estimate:* a parent with >= 1 NON-ARCHIVED subtask never uses its own stored
`effort_minutes` for display or drawability — not even when all subtasks are
done. `remainingEffortMinutes` sums OPEN subtasks (NULL when none are open
or none estimated); the pool predicate, `isRestorable`, the client's
`classifyTask` (new derived `hasNonArchivedChildren` field, pinned by the
shared drawable vectors) and the goal rollup all exclude such parents. The
stored estimate is IGNORED, NOT NULLED: nulling would lose the sizing
history and strand the parent-revives-as-leaf path (PR #102 — children all
moved away or archived leave zero non-archived subtasks and the stored value
becomes meaningful again; ADR-2: derive at read time, keep stored fields as
source data). *(2) Auto-complete:* after every write that changes a
subtask's status (complete, archive, reopen, un-archive) or deletes one (the
trash button sits on every subtask row, and deleting the last open step next
to a done sibling is an everyday finisher — deleting a parent's ONLY subtask
instead leaves zero children and revives it as a leaf, not as done), a
parent that is open, non-recurring and ALL-DONE — >= 1 done subtask, zero
open, archived ignored on both sides — completes through `completeTask()` in the same
transaction: a genuine completion row (ADR-5 derivations, achievements
including `monster_slayer` at its natural moment, timer close, ADR-13
pointer hygiene all flow normally), with an explicit effort override of 0 —
the subtasks already earned the effort-XP — and `wasDrawn` false (under rule
1 a parent with children is never in the deck); the override also forces the
warm-up branch off (ADR-30): a dealt card that was broken down still owns
the marker when its symbolic completion runs, and a `was_warmup = 1` row
would lie in the log and arm the ×1.25 momentum window off a completion the
user never made on the dealt card. The existing `xp < 1` floor
lifts it to a symbolic *1 XP*, keeping every completion row >= 1 for the
trophy pile and today displays. It COUNTS toward the daily goal and the
streak like any completion — it is one honest row, and excluding it would
need a new stored distinction (rejected for simplicity and honesty). The
estimation block (ADR-15) usually never sees the symbolic cycle — the
attributed window has no tracked minutes (checkbox-only cycles are skipped)
or an unestimated parent fails the positive-estimate rule — but a parent
with BOTH pre-breakdown tracked time and a positive stored estimate DOES
enter the block on auto-completion, exactly as the same row would have on
manual completion before this decision; the data point is real and
deliberately kept. Manual
completion of a parent with >= 1 non-archived subtask awards the same
zero-effort XP (legacy all-done-open rows resolve this way); a parent whose
subtasks are ALL archived is a leaf again and completes on its own estimate.
A split-in-place (#108) can never trigger the predicate — the archived
original is replaced by open parts in the same transaction. Sequential mode
(ADR-18) needs no extra bookkeeping: the hold-back is derived, so the last
freed step's completion is an ordinary trigger. *Recurring parents are
EXCLUDED:* their completion advances the due date and keeps the task open
(ADR-6), but the subtasks would stay done — every later occurrence an empty
shell — and auto-reopening subtasks on recurrence is undefined territory. A
recurring parent whose breakdown is all done simply stays open (rule 1 keeps
it out of the deck and its estimate inert); manual completion remains
available and follows ADR-6 unchanged, at the zero-effort XP. *(3) Reopen:*
every path that puts an OPEN child under a DONE parent reopens it — subtask
creation (single and batch), adoption via reparent (resolving #104 item 1
for done roots; archived-root adoption stays open in #104), reopening a done
subtask (symmetry with rule 2), and un-archiving one. Reopening sets status
open, clears `completed_at` and snooze/block (ADR-17), and deletes the
parent's latest completion row via `undoLatestCompletion` (ADR-5 no-farming
— exactly the auto-completion being undone; a harmless no-op on legacy done
parents without one). Adopting a DONE task under a done root reopens
nothing — no open child appeared. Reparenting AWAY is not a trigger: an old
parent left with only done children resolves like a legacy row, on its next
subtask status change or by manual completion. The subtask-completion
response carries the parent's result as `parentCompletion` (XP,
achievements, level-up) so the client and MCP surface the cascade without a
second request.
*Rationale:* The parent's row is bookkeeping for the breakdown once
subtasks exist — the work, the estimates and the XP live in the leaves, so
every derived surface (effort, drawability, completion, reopening) follows
the leaves too, and no stored counter or flag is introduced anywhere
(ADR-2/ADR-5). Zero-effort-plus-floor was chosen over bypassing the floor
(a true 0-XP row would break the "every trophy carries >= 1 XP" uniformity)
and over any estimate-derived award (double-earning is the exact bug being
fixed). No migration: legacy all-done-open parents are not retro-completed —
they resolve on their next subtask status change or via manual completion.

and the ×1.5 XP bonus keep agreeing on what counts as drawn), richer
gradient — because two competing iridescent tiers would be noise. The 4★
silver tier is KEPT: the user rejected the frame furniture, not the #62/#107
reward ladder, silver is monochrome and quiet next to holo, and dropping it
would silently strip an earned reward. On the standing drawn card the drift
runs slowly and always; in the pile the sweep remains lift-gated (a shelf
of 20 shimmering cards would be a casino, one celebrated card is not).
(d) Kept from ADR-31, verbatim: the cache-only batch pile art endpoint
(`GET /api/card-art?taskIds=…`), the pile flex-wrap overflow behavior, the
degraded-grace contract, and the derived payload fields (`trackedMinutes`
on draw payloads, `goalId` on todayCompletions) — now unused by the UI but
part of the API surface for MCP and future consumers.
*Rationale:* The draw-a-card metaphor needs the card to feel like a reward,
not a character sheet: the art carries the reward, the chips carry the
information, and the shimmer marks exactly the behavior the app pays the XP
bonus for (drawn high-leverage work). Deriving holo from the same facts as
the old foil keeps rarity a pure render-time function (ADR-2/ADR-5 spirit)
— nothing stored, nothing to migrate; the rename is a class name and a
gradient. Deleting the frame component instead of hiding it keeps one card
language in the codebase, and the surviving pieces live where they are used
(pill in TaskBadges, ink+art helpers in `lib/cardVisuals`).


== ADR-34: The daily hand is dealt once per local day, has no redeal, and lives in one settings row

*Amendment (#147):* The daily hand was REMOVED — see ADR-39. This ADR stays
as the record of how the feature worked, and of the no-redeal reasoning in
(b), which outlived the feature (it is restated as the commitment invariant
in section 8.2).

*Context:* Drawing one card at a time answers "just start", but not the
morning question "what does my day look like?" (#59). A hand of 3–5 cards
dealt as today's plan answers it — and forces the redeal question. The issue's
original draft DECIDED it one way ("one free redeal per day, then the hand
stands"); this ADR OVERRULES that decision on the re-roll/ADR-5 grounds in (b),
and the owner has since amended the issue to match. It is not a question the
issue left open — it is a decision the implementation reversed.
*Decision:* (a) *Dealing.* One hand per SERVER-LOCAL day (the streak's day
convention, `services/localDay.ts`), effort-budgeted rather than fixed-size:
`daily_hand_budget_minutes` (public setting, default 90) with a hard cap of
5 cards. Eligibility is not a new predicate but literally the draw's own
candidate query (`queryCandidates`, exported for this): snooze/block
(ADR-17), sequential hold-back (#23), availability windows (#33) and the
leaf rule (#111) land in the hand for free and cannot drift. Selection is
weighted sampling WITHOUT replacement using the existing `poolWeights`
(impact²/effort × urgency × staleness × ADR-25 sibling damping), a card
being samplable only while its effort fits the REMAINING budget; the
weights are recomputed each round over the still-affordable set, which is
ADR-25's rule read faithfully (a sibling that cannot fit cannot flood the
deal, so it must not dampen). Random, not top-N by weight: a top-N hand
would be the same five cards every morning — a to-do list, not a deal.
Dealing has NO side effects on the cards: no `last_drawn_at` stamp, no
current draw, no achievement. Empty deals reuse the draw's honest reasons
(`no_ready_tasks` / `all_too_big` / `all_outside_window`) plus
`budget_too_small` — eligible cards exist, none fits the day.
(b) *No redeal.* The issue's original draft decided on one free redeal per
day; this ADR overrules it. #88
removed "Draw again" because re-rolling is fishing for a comfortable card;
a hand redeal is that same re-roll, five cards at a time. The issue's own
argument only establishes that a redeal cannot be PRICED — XP is derived
from the completions log (ADR-5), so charging it would mean fabricating or
deleting completion facts, a lie in the ledger — which is an argument
against pricing it, not for granting it free. The warm-up settles the shape
of the tension (ADR-30): its allowance is consumed at deal time and never
refunded, precisely so the deal cannot be fished for a better card; a
once-per-day redeal is an allowance whose only purpose is to fish. The hand
therefore only ever SHRINKS, and the escape from a card you do not want is
the single draw's sanctioned one: resolve it (complete, snooze/block, edit,
delete). This costs the user nothing, which is what makes it defensible —
the freestyle draw below the strip is untouched and always available, so
the hand is today's plan, never the only way to get a card. Playing a card
while another is revealed is impossible for the same reason: `409`, exactly
like the warm-up deal.
The hand does permit CHERRY-PICKING within itself, and that is accepted. The
3–5 cards are dealt face-up and `POST /api/hand/play` takes any `taskId` in the
list, so a user can read the whole hand and play the most comfortable card at
zero cost, without snoozing anything. This is bounded by construction and
strictly WEAKER than the loop #88 already sanctions: the set is
weighted-sampled ONCE, is closed, and can only SHRINK — nothing appends to
`taskIds` outside `dealHand`, and `POST /api/hand/deal` answers `409` even on an
emptied hand — so the most a user can do is choose among a fixed few, whereas
the freestyle snooze-and-redraw escape can resample the whole deck without
bound. Picking within a dealt hand IS the "plan my day" overview the feature
exists to give; forbidding it would defeat the purpose. It is acceptable.
(c) *Playing.* `POST /api/hand/play` makes the card the current draw with a
real draw's side effects (ADR-13 pointer, `last_drawn_at`, `drew`
achievement) — so reload-restore, the ×1.5 drawn bonus, the 5★ holo and the
snooze/edit/delete actions are the EXISTING ones, with no second code path.
A played card is gambled (it was sampled out of the weighted pool), unlike
the warm-up's handout, so it keeps the bonus and the shimmer.
(d) *Persistence: no table.* The hand is one settings row (`daily_hand`,
JSON `{date, taskIds, budgetMinutes}`) — ADR-13's pattern widened from one
pointer to a
list, and internal session state excluded from `/api/settings` like the
current draw and the warm-up marker. The budget is stored WITH the deal, not
re-read from `daily_hand_budget_minutes` on every GET: the minutes a hand was
dealt against are a historical FACT of that deal, not derived state, so a later
PATCH of the setting must not rewrite a standing hand's header. This is the
mirror of ADR-2, not a breach of it — ADR-2 forbids storing state that CAN be
re-derived; the dealt budget cannot be. It is a pointer list validated on
read, not a record: `GET /api/hand` re-validates every member with the same
`isRestorable` the current draw uses (shared `taskWithDeckState` row shape)
and prunes failures permanently. Three removals are EAGER because lazy
validation provably cannot catch them in time: `completeTask()` (a
recurring task stays open, ADR-6, and would sail straight through
`isRestorable`), the snooze/block/reparent PATCH (a snooze wears off with
no GET in between, and the once-valid card would resurrect in the hand the
user sent it away from — ADR-17), and delete (`tasks.id` has no
AUTOINCREMENT, so a freed id can be re-bound to a newcomer — the
`clearDanglingDraw` reasoning). A row from an earlier day is not a hand: the
ritual resets at local midnight, unplayed cards return to the deck, no
carryover, no penalty.
(e) *Migration v10 adds no schema* — it seeds `daily_hand_budget_minutes`
on existing databases so the Draw page's budget input is not empty on
exactly the databases that predate the feature.
(f) *UI.* A strip above the draw scene (the morning entry point), sharing
the page so the played card and the freestyle draw stay on ONE current-draw
pointer and cannot diverge. Faces follow ADR-33 in miniature: full-bleed
cached art (cache-only batch read, never a generation) under a scrim,
subtle chips, holo on 5★ goal-linked cards. The card IS the play control —
no per-card action row duplicating what the revealed card already offers —
and the budget input lives beside the deal button rather than in Settings,
because that is the one place the number is read.
*Rationale:* The hand is a commitment or it is nothing: a plan you can
re-roll until you like it is precisely the choice paralysis the app exists
to remove, and it would quietly undo #88 one feature later. Reusing the
draw's query, weights, restore-validation and current-draw pointer keeps
the feature honest by construction rather than by discipline — there is no
second eligibility path to keep in sync, and no second way to hold a card.
Keeping the hand in settings-kv follows ADR-2/ADR-13: it is session state
derived from the tasks it points at, so it needs validation on read, not a
table with its own truth to defend.


== ADR-35: A goal PDF uploads once to the Anthropic Files API; its file_id is a cache, not identity

*Context:* Every AI call embedded each selected PDF as a fresh base64
`document` block, re-sending the whole payload on every request (section 11
R5, #92). Prompt caching (ADR-11's `cache_control` breakpoint) discounts the
*token cost* of that prefix on a repeat call but not the *bandwidth*: the
base64 still travels the wire each time, and a re-read of the file can produce
a different byte string that quietly breaks the cache prefix anyway. The
Anthropic Files API is the documented fix — upload a file once, reference it by
`file_id` thereafter — but it introduces a piece of state this app does not
own: the id names a file living in the Anthropic account behind the *current*
API key.

*Decision:* (a) *Upload lazily, once, on first AI use.* A new nullable
`materials.anthropic_file_id` column (migration v11, no default, no backfill)
caches the id. It is filled the first time a material reaches an AI call, not
when the user uploads the material: most materials never reach an AI call, and
at upload time there may be no key at all (degraded mode is a fresh install's
default state). `.txt`/`.md` materials stay inline as text blocks — they are
cheap and inlining keeps the assembled prompt debuggable; the win is PDFs.
(b) *The id is a CACHE of remote state, never identity.* It is valid only
under the key that created it, so it can go stale for reasons this app cannot
observe: the key was swapped for another account's, a backup was restored on a
different machine (#61 — the archive carries the material rows AND the PDFs,
but Anthropic-side state cannot travel with them), or the file expired
server-side. The PDF under `files/` remains the source of truth and can always
rebuild the request. Nothing treats a stored id as proof the file exists.
(c) *Self-heal transparently.* If Anthropic rejects a request that referenced
a cached id (a 404, or a file-mentioning 400), the ids for that call are
dropped and the blocks are rebuilt from disk exactly once — the rebuild
re-uploads, so a second rejection is a real failure and surfaces rather than
loops. One 400 class is excluded from the file-mentioning slack (#138): a
capability rejection ("... not supported ...") is the API refusing the request
*shape*, not reporting a dead id — re-uploading cannot fix it, so it must
surface instead of invalidating a live id and burning an upload. This is the
whole cache-coherence policy, isolated in
`withFileIdRetry` so it can be pinned by a test without a key. On a key change
(`PUT`/`DELETE /api/ai/key`) every cached id is cleared eagerly, because the
old key's ids can never be valid again.
(d) *Never break a feature on the upgrade path.* If an upload fails (no key,
quota, outage, the beta being withdrawn) the call falls back to the base64
block it used before #92. The Files API can cost bandwidth, never function.
(e) *Token counting substitutes the bytes — corrected by #138.* This ADR
originally claimed `count_tokens` resolves the referenced file server-side.
That claim was false: the real endpoint rejects `{type: "file"}` sources
outright (`400 — "File sources are not supported in the token counting
endpoint"`, observed live), and because the mocked SDK accepted them CI stayed
green while every material-backed call died at the estimate gate. The guard
now counts a *base64 substitute* read from the local PDF for each file-source
block — the exact content the id references, so the count is exact and the
`MAX_INPUT_TOKENS` guard gates the same thing — while the paid call keeps the
`file_id`. Counting therefore still pays the base64 bandwidth; only the paid
call sheds it. The mocked `count_tokens` now rejects file sources exactly like
the live endpoint, so a regression re-fails in CI instead of only in
production.
(f) *Beta surface.* The `{type: "file", file_id}` document source exists only
in the SDK's beta namespace (the GA `DocumentBlockParam` source is
base64/text/content/url — verified against the installed `@anthropic-ai/sdk`),
so the four AI calls move to `client.beta.messages.*` and send the
`files-api-2025-04-14` header — but only when a request actually references an
id, so material-less calls (card art, a task with none) keep their exact
pre-#92 shape.

*Rationale:* Modelling the id as a cache rather than a stored fact is what
makes the change safe against the one thing that would otherwise corrupt it —
a dangling id surviving a backup restore onto another account (#61). Because
the file on disk is always the fallback and the retry always re-uploads, no
state this app cannot observe can wedge an AI feature: the worst a stale or
missing id can do is cost one extra upload. Degraded mode is byte-for-byte
unchanged — the uploader is null without a key, so assembly produces exactly
the base64 blocks it did before, and the 503 still comes from the same guard.

== ADR-36: Every structured AI call streams — amends ADR-8

*Context:* ADR-8's structured outputs rode the SDK's non-streaming
`messages.parse()`. The first-ever real API calls (#91) exposed a guard the
mocks could never trip: the SDK refuses any non-streaming request whose
`max_tokens` implies a possible run of more than ten minutes ("Streaming is
required for operations that may take longer than 10 minutes"). Three of the
four AI calls stayed under it (16K default, 8K card art) — generate-tasks'
deliberately raised 32K cap (#28, a 40-item transcription plus rationales)
tripped it, and the flagship exam-import feature answered a plain 500 on
every live call while CI stayed green (#133).

*Decision:* `runStructured` sends every structured call through
`messages.stream()` and reads the accumulated final message via
`finalMessage()` — all four callers, not just the one over the threshold.
Streaming here is transport, not behavior: the SDK's stream helper applies
the same beta parser to the accumulated message that `parse()` applied to the
buffered response, so `parsed_output` (zod-validated, ADR-8) is unchanged;
request-level SDK errors reject `finalMessage()` with the same typed error
classes the existing mapping handles; and the request shape — `cache_control`
breakpoints (ADR-11), the `files-api` beta header (ADR-35), the
`count_tokens` preflight — is untouched apart from stream mode, so prompt
caching and the token guard see nothing new. The SDK boundary in the
integration suites mocks `stream()`/`finalMessage()` accordingly, and the
request shape is pinned so a silent fall-back to `parse()` fails in CI.

*Rationale:* Streaming only the 32K call would leave a tripwire armed: the
guard is a function of `max_tokens`, so the next cap raise (a bigger deck, a
denser card) would re-break a feature in the exact way mocks cannot catch —
live only. Streaming everywhere removes the failure class for the cost of
nothing: no request field changes, no parse semantics change, and the paid
calls were already long-running (card art measured ~39s live). What streaming
does NOT buy here is incremental UI — the server still hands the client one
complete JSON result; per-token delivery to the browser stays out of scope
until a feature needs it. The live 32K path itself still cannot run in CI (no
key); its re-verification is a #91 checklist item.

== ADR-37: The assistant stages a draft changeset; apply is one transaction through the route cores

*Context:* Issue #31's conversational assistant gives the model free-form,
multi-turn control ("import this exam, make the first 10 due this week").
ADR-19 settled the tool vocabulary (`server/src/tools/catalog.ts`) and why the
MCP surface may write live — the MCP client's per-call approval conversation
IS its review. The in-app chat has no such gate, and forty mid-loop confirm
dialogs would be worse than none. ADR-14's contract stands: the AI proposes,
checkbox review remains the sole write path.

*Decision:* (a) The agent's WRITE tools never touch the database during the
loop. `create_task`/`create_subtasks` — the catalog's own definitions, with
`parentId` widened to draft references — validate against an in-memory draft
changeset (`services/agentStaging.ts`, pure) and return synthetic
`draft-N` ids the model can chain into breakdowns. READ tools (`list_tasks`,
`list_goals`, `list_categories`, `get_settings`, `get_stats`) execute live
through `executeTool` against an in-process `ApiClient`
(`tools/inProcessApi.ts`): a lazy private loopback listener on the app's own
Express instance, so the derived read payloads and every invariant hold by
construction (the ADR-19 argument) — with or without a public listener
(supertest). `draw_card`, the timer tools, `complete_task` and `update_task`
are absent from this surface: the draw is a commitment device (ADR-13/ADR-30,
+#88+ removed re-rolls) and a chat assistant that draws on request would be a
re-roll machine; update/complete staging (before→after diffs) is the issue's
declared out-of-scope.
(b) `POST /api/ai/agent/apply` carries the REVIEWED operations in the body —
included rows plus the user's title/effort edits, exactly what the review
card shows (ADR-14: the review is authoritative, so its state must travel;
`{sessionId, acceptedDraftIds}` alone could not carry an edit). Apply runs in
ONE `db.transaction` and calls the same creation cores the task routes run —
extracted honestly to `services/taskWrites.ts` (`createTaskWrite`,
`createSubtasksWrite`), so the ADR-4 impact gate, ADR-16 one-level rule,
ADR-23 recurring×sequential ban and the #111 lifecycle hooks have exactly one
home; better-sqlite3 nests the cores' inner transactions as savepoints, and
any rejected row rolls back the whole changeset. Draft parents resolve to
real ids in list order. Oversized subtask efforts are split, never clamped
(#28's `evenSplit` policy) — at stage time so the review shows the real rows,
and again at apply because the reviewer can edit efforts; a `create_task`
staged WITH a `parentId` is a leaf too and takes the same stage-time split
into sibling parts (ADR-16 leaves it no breakdown to fix itself with).
(c) The loop itself (`services/agentLoop.ts`, pure; transport injected by
`agentService.ts`) is a manual while-`stop_reason=tool_use` loop over
`beta.messages.stream()` + `finalMessage()` — the ADR-36 seam the whole suite
already pins — NOT the SDK's beta `toolRunner`: the per-iteration `usage` the
issue's budgets need is exactly what the runner abstracts away. Caps per user
message: 8 iterations and a cost ceiling summed from per-iteration usage with
OUTPUT tokens priced at $25/MTok (the pre-existing estimate() prices input
only and would understate agent runs ~5×); an abort returns the partial
changeset plus a `stopped` reason, never an error. A model-side truncation
(`stop_reason` `max_tokens` with tool calls still pending) answers every
dangling `tool_use` with a synthetic error result instead of executing
possibly-cut-off arguments — the session history stays API-legal (the next
send would otherwise be rejected) and the model's context stays honest.
Materials enter as document blocks in the first user message via
`materialBlocks()` (ADR-7/ADR-35, `count_tokens` guard with the #138 base64
substitution, file-id retry); the system prompt is static and carries a
cache breakpoint, so material-less iterations reuse the tools+system prefix.
(d) Sessions live in an in-memory `Map` (single-user local app; the multi-MB
PDF blocks must not round-trip through the browser) — deliberately NOT
persisted, so `user_version` stays 11: a conversation is scratch state, and
the accepted limitation is that a `tsx watch` restart drops it (the client
surfaces the 404 as "start a new conversation"). Both endpoints answer 503
`ai_not_configured` without a key — apply included, although it never calls
the SDK: the whole surface is hidden in degraded mode, and a reachable apply
would be a write path no UI owns.
(e) Apply CONSUMES the changeset (+#143+, amending this ADR's original
"apply stays stateless and unaffected" wording — the live verification round
showed the same `{sessionId, operations}` POSTed twice returned 201 twice
and created every task again, reachable through a timeout-after-commit HTTP
retry or a double-click race). Each session carries a monotonically
increasing *changeset version*: every message turn returns it alongside the
ops, apply sends it back, and a successful apply clears the staged ops,
bumps the version and keeps the created mapping. A re-apply of a consumed
version answers `409` carrying the ORIGINAL `created` mapping, which the
client treats as success — an honest retry reconciles instead of
duplicating; a version-less re-apply (API-level caller) reconciles
best-effort when the session has nothing pending, and is refused (`409`, no
mapping) when a pending changeset and a consumed one coexist — ambiguous by
construction, and acting on it could consume the pending changeset without
applying it. The key is the VERSION,
never a deep-equal of operations: the apply body carries the REVIEWED ops
(title/effort edits, exclusions), which legitimately differ from the staged
ops of the very changeset they belong to. A NEW changeset staged later in
the same session gets the bumped version and applies normally. When the
session itself is gone (restart, eviction) apply still proceeds statelessly
— a retry that crosses a server restart cannot be detected: it answers
`201` and re-creates every task, and the client reports it as a fresh
success with no hint of duplication. Closing that window would take a
persisted idempotency ledger (a schema migration), which (d)'s
no-persistence stance deliberately declines — the accepted limitation
above, now scoped to exactly that case.

*Rationale:* One review table beats forty confirmations and preserves the
app's review-before-accept contract; staging in memory keeps the "never
writes mid-loop" property testable as a pure function (the suite never mocks
Anthropic — degraded 503s plus pure staging/loop coverage plus a mocked
stream seam, the #136 convention). Routing apply through the extracted cores
is the only way "same validation as the routes" stays true by construction
instead of by diligence. The live loop cannot run in CI (no key); its
verification on a real key is a follow-up checklist item like #91's.

== ADR-38: Goal resolution — `missed` is a user assertion, `resolved_at` is a stored event fact

*Context:* Issue #145: marking a goal achieved was a silent column write (the
goal vanished from the only listing the UI ran), and a goal whose outcome is
decided against the user — the grade is in and it is not the one the goal
named — had no honest state: `dropped` means "abandoned by choice", and was
not even reachable from the UI. The feature adds a `missed` status, a
celebration for achieved goals, and a Hall of Fame shelf that shows resolved
goals with their resolution date — a date no existing column carried.

*Decision:* (a) `missed` joins the status CHECK as a USER ASSERTION only: the
app never sets it — an overdue `target_date` keeps producing the red chip and
nothing else, because only the user knows whether the outcome is actually
decided (a grade can arrive before or after the date). (b) `resolved_at`
stores the moment a goal leaves `active`. This scopes ADR-2's "derive, don't
store": the ban covers DERIVABLE state (counters, progress, drawability),
and a resolution instant is not derivable — there is no transition log to
replay, the same standing as `tasks.completed_at` and
`achievements.unlocked_at`. It is maintained exclusively in the PATCH
handler: set once on the transition out of `active`, kept verbatim across
no-op resends (ADR-4 tolerance) and `achieved`&#8596;`missed` corrections,
cleared on reactivation — and never client-supplied. Pre-v12 resolved rows
keep `NULL` ("date unknown", the v11 `anthropic_file_id` honesty) rather
than a backfilled guess. (c) All transitions stay legal; validation is enum
membership only, turning the former CHECK-constraint 500 into a clean 400.
Reactivation from the shelf requires `achieved/missed → active`, and a
single-user app with one writer has no invariant for a state machine to
protect. (d) The migration rebuilds the goals table (SQLite cannot alter a
CHECK) with `foreign_keys` toggled OFF outside the transaction: ON, the
implicit delete of `DROP TABLE goals` fires `tasks.goal_id`'s SET NULL and
`materials`' CASCADE — the rebuild would "succeed" having silently unlinked
every task and deleted every attachment; `foreign_key_check` afterwards
proves the rebuilt table dangles nothing. (e) The shelf and every listing
derive purely from `status` + `resolved_at`; `trackedMinutes14d` is
deliberately absent from the shelf — a rolling window decays to zero after
resolution and would misrepresent history (the victory overlay may show it:
it fires at resolution time, labeled as the final 14 days).

*Rationale:* A `missed` goal is a recorded defeat, not a deleted one — the
distinction from `dropped` is the whole feature, so collapsing them was
rejected. Auto-fail on the target date was rejected because the date is a
plan, not a verdict. Storing the event fact beats deriving nothing: the
alternative — a goal-transition log — is heavier than the one column and
would still store the same instants. The FK-off rebuild is the standard
SQLite recipe; the migration-v12 test pins the exact failure the pragma
prevents, because it is the kind that ships green and loses data.

== ADR-39: The daily hand is removed — one card face-up, never a day preview

*Context:* ADR-34's hand answered the morning question "what does my day
look like?" (#59) with 3–5 cards dealt face-up. Living with it showed the
question itself was the trap: the app's core psychology is to HIDE the
mountain of effort and move from one small doable card to the next — one
card face-up is a commitment you can start; five cards face-up is a to-do
list, and a to-do list is the overwhelm machine this app was built to
replace. The hand's one unique contribution — an "enough for today" finish
line — was already covered by the daily goal (`daily_goal_completions`),
which counts completions without ever previewing tasks (#147).

*Decision:* Remove the feature entirely: the `/api/hand` routes and
`handService`, the HandStrip and its hooks, the `daily_hand_budget_minutes`
public setting and the `daily_hand` session row. Migration v13 is v10's
mirror and equally pure data — it deletes the two settings rows on existing
databases; v9/v10 stay verbatim as replayed history (a pre-v10 file still
seeds the budget row, then v13 deletes it — the chain test pins exactly
that). The single draw, the warm-up (ADR-30), focus mode and the trophy
pile are untouched, and the commitment invariant (section 8.2) survives the
feature that helped articulate it.

*Rationale:* Philosophy-first, the #88 precedent: re-draw was removed
because a feature that contradicts the product's one job is debt, not
value, no matter how well it is built — and the hand was well built (no
redeal, shared predicate, shrink-only). What #88 could not fix by
tightening rules, this removes at the root: even a commitment-shaped
day preview still SHOWS the day, and showing the day is the harm. Nothing
of the user's is lost — the hand was validated pointers into tasks, dealt
fresh each morning — and no capability is lost that the daily goal does not
already provide.

== ADR-40: Capture merges into Tasks — one capture-first task page

*Context:* Capture and Tasks were two partial views of the same task list
(#151), and the split had real seams: Capture's "too big" group said
_"split them"_ but the split control lived on the other page; the Draw
page's empty-pool helper linked "Break something down" to `/capture`,
where breakdown did not exist; adding an estimate had two different UIs
(Capture's inline input, Tasks' row-edit form) for the same PATCH; and the
Tasks page could not create a task at all — its empty state walked the
user to Capture. ADR-39's "hide the mountain" doctrine is about the DRAW
page, not these planning surfaces: Capture already listed every open task,
so consolidation exposes nothing new.

*Decision:* One page at `/tasks`, capture-FIRST: the shared `TaskForm`
pinned on top with the rapid-entry ritual intact (autoFocus, title-only
Enter submit, fields reset, focus retained for the next thought), then a
"not deck-ready" *triage strip*, then the category tree with full row
actions and drag-and-drop. The strip lists only the ACTIONABLE eligibility
groups: needs-estimate rows carry the inline Enter-to-save estimate input,
too-big rows are full `TaskRow`s whose Break down / Split work in place —
and the #30 sibling folding applies inside the strip. The passive groups
(ready, queued, scheduled) dissolve: `TaskBadges` already wears those
states per row. `classifyTask`/`groupSiblings` stay the single predicate
source (`lib/drawable.ts`); the server is untouched. The Capture nav entry
is removed; `/capture` survives as a client-side redirect to `/tasks`
(muscle memory, old links).

*Rationale:* One home per concern — the page that names a problem must own
the control that fixes it. A triage row deliberately renders in BOTH the
strip and its category group: the strip is a worklist over the list, not a
second tree — which is also why strip rows live outside the DnD context
and are neither drag sources nor drop targets. Actionable-only triage
keeps the strip an emptying queue rather than a re-grown Capture page: a
group whose rows offer nothing to do is a to-do list about the to-do list,
and ADR-39's lesson applies — surfaces that only display state feed the
overwhelm this app exists to replace.

== ADR-41: History merges into Stats — one summarized progress page, the per-task estimation table is removed

*Context:* Stats and History were two zoom levels of the same record
(#155): the 26-week activity heatmap on /stats and the day-tower skyline
on /history both rendered `GET /api/activity` via the same `useActivity`
hook. Meanwhile the Stats page itself sprawled — the "Estimates vs.
reality" block rendered an unbounded per-task table (~3 bars per completed
task in range), which grows into exactly the wall of past effort the
product philosophy avoids putting on screen.

*Decision:* One page at `/stats`, in this order: header + week/month range
chips, summary tiles + leverage banners, where-your-time-went bars,
estimation SUMMARY (accuracy ratio, tendency copy, totals line, and the
per-category rows with their coaching statements), the skyline, the
achievement collection. The skyline moves whole — extracted into
`components/Skyline.tsx` with every behavior intact (8-week windows +
"Load earlier" to the ten-year cap, windowed virtualization, local-day
bucketing, lift interactions, rarity sheens). The ActivityHeatmap is
DELETED as a redundant zoom of the skyline's data (with `lib/heatmap.ts`,
its only consumer gone). The estimation per-task table is deleted, and the
server stops computing/shipping `estimation.tasks` — `summary` and
`byCategory` stay, as does the separate all-history
`/api/stats/estimation-bias` endpoint (ADR-27). The History nav entry is
removed; `/history` survives as a client-side redirect to `/stats`
(the ADR-40 `/capture` precedent).

*Rationale:* One progress surface, summarized. Two views of one endpoint
at different zooms is duplicated UI, not added insight — and of the two,
the skyline is the richer artifact (per-card detail, rarity, face-down
permanence) so it is the one that stays. Trimming `estimation.tasks` on
the server rather than merely hiding the table follows the guardrail that
unconsumed payload is dead code: coaching is deliberately per-category
(ADR-27) because "your Study estimates run 2× low" is actionable while a
scrollable ledger of individually mis-estimated tasks is only
retrospection. The redirect keeps muscle memory and old links working at
zero maintenance cost.

*Amendment (#174):* the extracted `Skyline.tsx` was itself later replaced by

instead of card towers (ADR-45).

== ADR-42: Achievement chains — the draws log, claim-for-XP as a second stored XP source, and the 5-tier ladder

*Context:* Achievements were eleven one-off unlocks with a client-only
rarity tier (ADR-5 stored just `unlocked_at`; #124 layered presentation on
top). #156 turns them into multi-level CHAINS with visible progress and a
click-to-claim XP payout, which needs three things the old model did not
have: a count of how many cards have been DRAWN (nothing logged draws —
`last_drawn_at` is a single overwritten timestamp, not a history), a place
to record a claim, and a rarity ladder both the server and client agree on
(the server now pays XP by tier).

*Decision:*

* *Draws log (new `draws` table).* An append-only event log,
`draws(id, task_id, drawn_at, was_warmup)`, written by `drawTask()` and the
warm-up deal — exactly the ADR-5 log-over-counters shape of `completions`
and `streak_freezes`. `task_id` is `ON DELETE SET NULL`, never CASCADE: a
draw HAPPENED even if the task is later deleted, so its history must survive
the row it pointed at. `was_warmup` separates gambled draws from handed-out
warm-up deals (ADR-30); the draws achievement chain counts non-warmup rows
ONLY. No backfill — pre-log draws are honestly unknown, so a chain progress
bar simply starts at 0 on an existing database.

* *Claim-for-XP amends ADR-5 with a SECOND stored XP source.*
`achievements` gains `claimed_at` and `claim_xp`. An unlocked achievement
can be claimed ONCE ever (idempotent by the primary key + a guarded
`claimed_at IS NULL` UPDATE) for rarity-scaled XP, and
`totalXp() = SUM(completions.xp_awarded) + COALESCE(SUM(achievements.claim_xp), 0)`.
This deliberately widens ADR-5's "XP is the completions log": a claim is
still an honest, idempotent event fact, so there is still no stored `xp`
counter to drift — the total is derived from two logs instead of one.
Schema v18 (#263) adds nullable `claim_gold` as Gold owned by the same
achievement row, with no backfill and no producer in this cutover; it does not
change claim-for-XP behavior. Permanent XP subsequently narrows ledger
participation to challenge rows (ADR-5 amendment).
`POST /api/achievements/:key/claim` returns `200 {xpAwarded, levelUp}`,
`400` for an unknown or not-yet-unlocked key, `409` for a repeat. `claim_xp`
is stamped from the SERVER tier table at claim time — the client is never
the XP authority.

* *The 5-tier ladder moves to `shared/`.* Rarity was a client-only lookup;
now the server reads it to price claims, so the tier per key lives in
`shared/achievementTiers.ts` (common 25 / rare 50 / super-rare 100 /
ultra-rare 250 / secret-rare 500 XP), imported by both sides — the same
drift-guard as `shared/achievementKeys.ts`. The old tiers migrate:
epic → super-rare, legendary → ultra-rare. `client/lib/achievementRarity.ts`
becomes a thin lookup over the shared table. The chains and their progress
share ONE table (`CHAIN_SPECS`) that drives both the unlock condition and
the progress bar, so a full bar is always a real unlock.

* *One new visual treatment, deliberately.* The two shipped sheens
(holo/silver, the "glint, not casino" doctrine) cover four tiers. Secret
Rare — reserved for the extreme chain ends (10k draws, 2500 completions, a
100-day streak, level 50, 25 goals) — gets ONE new treatment: a
dark/negative card frame + drifting holo + a distinct luminous violet
border. Not a casual new gradient; recorded here as the single exception.
Motion stays gated behind `prefers-reduced-motion: no-preference`, so the
frame and sheen paint but never move under reduced motion. `trophyRarity`
(task trophies) keeps its own separate 3-tier vocabulary — untouched.

*Rationale:* Progress and claims are exactly the anti-procrastination loop
the product wants (a visible next rung, a small reward for reaching one),
and both are expressible as logs, so they stay within ADR-2/ADR-5's
"derive, never store a counter" spirit — the draws table and the claim
columns are event facts, not running totals. Sharing the tier table is
forced by the claim: the moment the server pays XP by rarity, a client-only
table would be a silent second source of truth. The chain keys shipped
initially on the emoji-glyph art fallback (`achievementArt`) — deliberately
not a blocker, since the degraded-grace face already handles a missing art
row (ADR-33 e) — and committed per-chain SVGs followed in #163, so every
key now carries hand-designed art.

== ADR-43: Stored sibling positions — a REAL `sort_order` column, midpoint reorders, roots excluded

*Context:* Sibling order was never stored. Subtasks sorted by
`(created_at, id)` everywhere — the child listing, the sequential hold-back
queue (ADR-18, where order is the whole semantics: the front step is what the
draw exposes), the split-in-place placement (ADR-18 amendment) — so the DnD
that could nest and promote (ADR-42 is unrelated; this is #101 → #157) could
not REORDER a breakdown. `classifyDrop` knew only nest/promote/inert, and
ADR-18 itself named explicit sibling ordering as the escalation if
queue-jumping ever proved wrong. #157 is that escalation.

*Decision:*

* *One REAL column, `tasks.sort_order` (migration v15).* Sibling order is now
`(sort_order, id)` everywhere the old `(created_at, id)` sort ran: the child
listing (`routes/tasks.ts`), the hold-back predicate (`heldBackSql`, the
semantic consumer), split-part placement, and — because MCP `list_tasks`
proxies `GET /api/tasks` — the MCP subtask order too. The backfill is
`sort_order = id`: `id` is the monotone creation key the pre-#157 order
already tie-broke on, so for organically-created rows `(created_at, id)` order
equals `id` order and NOTHING moves on migration day. New inserts are stamped
`sort_order = id` by an AFTER INSERT trigger (`WHEN NEW.sort_order = 0`), so a
fresh root/sibling lands after existing ones; split-in-place parts set
`sort_order` explicitly (spread between the archived original's slot and the
next sibling) to land in the original's exact place, so the trigger's guard
skips them. No legitimate position is ever 0.

* *REAL, not integer, so a reorder is a single-row midpoint write.*
`POST /api/tasks/:id/reorder { beforeId }` sets the moved task's `sort_order`
to the midpoint of its two new neighbors (`beforeId` null = one gap past the
last sibling) and touches nothing else. Only when REAL precision leaves no
value strictly between the neighbors — repeated bisection of one gap, rare in
a single-user app — does the parent's whole breakdown renormalize to integer
gaps (`siblingOrder.ts`). Guards: `beforeId` must share `:id`'s parent
(cross-parent is a reparent — the nest PATCH, ADR-16 — not a reorder), 404
unknown, 400 for a root (`:id` with no parent) or a before-self.

* *Roots are NOT reorderable — documented exclusion.* Root order stays
creation order (the list renders roots newest-first; there is no queue over
roots, so no order semantics to arrange). The column exists on root rows
(backfilled like any other) but no read sorts roots by it, and the endpoint
400s a root `:id`.

* *Sequential-queue interaction reuses the ADR-18 wear-off guard.* A reorder
under a `sequential` parent changes which step is exposed vs held back, so if
the move strands the persisted current draw — the moved card, OR a sibling it
jumped in front of, pushed into a held-back slot — the pointer is cleared
EAGERLY, exactly as the reparent path does (ADR-13/ADR-18): a held-back card
would become restorable again the instant the step in front completes, with no
GET between. Reparent (adoption into a sequential breakdown) is unchanged: the
adopted task keeps its own `sort_order`, so it still enters by roughly creation
order and may jump the queue — but #157 adds the remedy, dragging it into
place afterward.

*Rationale:* Sibling position is USER STATE, not derivable state — there is no
predicate or log it could be computed from, so storing it stays WITHIN ADR-2
(which bans stored DERIVABLES, e.g. XP/streak counters, not stored facts). It
stands exactly with `resolved_at` (ADR-38): an event/decision the user made,
recorded once, kept until changed. The REAL midpoint scheme is the standard
fractional-index trick — it buys O(1) reorders against O(n) renumbering, and
the renormalize path bounds the precision cost that a purely-fractional scheme
would otherwise accrue. Deriving hold-back from the stored order (rather than
storing a second "is exposed" flag) keeps every mutation path automatically
correct, the ADR-2 argument once more.

== ADR-44: User-customizable achievement display metadata — a side table, display-only, unlock/claim untouched

*Context:* Achievements are server-defined (`ACHIEVEMENTS` in
`gamificationService`) with no user overrides — the title, description and
whether a card shows at all were fixed copy. #177 asked for two linked things:
a NAME-ONLY card face with the description revealed on hover/focus, and a
per-card edit affordance to rename an achievement, rewrite its description, and
hide it. That is display personalization layered on top of a fixed achievement
set — it must not touch the unlock/claim/XP machinery (#156, ADR-42) or the
shared key contract (#124).

*Decision:*

* *One new table, `achievement_customizations` (migration v16).*
`(key TEXT PRIMARY KEY, title TEXT, description TEXT, hidden INTEGER NOT NULL
DEFAULT 0)`. Keyed by achievement KEY, NOT a foreign key to the `achievements`
table — that table only rows UNLOCKED keys, and a customization must apply to a
still-LOCKED key too (pre-rename or pre-hide a card before earning it). NULL
`title`/`description` mean "use the server default"; the row exists only while
some override is set — an all-default result (a reset) DELETES it, so
`customized` is a simple truth about the row's presence.

* *`gamificationState()` COALESCEs the overrides.* It reads the side table into
a Map (the JS `ACHIEVEMENTS` array still owns order/emoji) and, per card,
ships `title`/`description` = `COALESCE(custom, default)` plus `hidden` (bool)
and a `customized` flag (any override set — gates the card's "Reset to
default"). The shipped key SET and ORDER are unchanged, so the "ships exactly
the shared key set" pin (#124) still holds.

* *`PATCH /api/achievements/:key { title?, description?, hidden? }` — an
upsert, DISTINCT from `POST /:key/claim`.* An absent field is left as-is;
`title`/`description` = null (or a whitespace-only string, normalized) CLEARS
that override; `hidden` toggles the curation flag. The key is validated against
`ACHIEVEMENT_KEYS` (400 otherwise). "Reset to default" is the same PATCH with
both texts null and `hidden` false. It returns the updated COALESCE'd
achievement.

* *Client: name-only face, hover/focus description, inline editor.* The card
face shows the name only; the description reveals on hover/focus as a
focus-reachable overlay (the ✎ button carries `aria-describedby` to it), and an
✎ button opens an inline editor (name, description, Hide toggle, Save/Cancel,
Reset to default) driven by a new `useUpdateAchievement` mutation that
invalidates `['gamification']`. Hidden cards move OUT of the main grid into a
collapsed "Hidden (N)" section on the Stats page — still editable, claimable,
and un-hideable there. Every title/description consumer, the unlock TOAST
included, reads the same `/api/gamification` payload, so custom values propagate
with no extra wiring.

*Rationale:* The overrides are DISPLAY ONLY — `checkAchievements`,
`claimAchievement`, `totalXp`, the rarity ladder (ADR-42) and the shared key
list are all untouched, so a hidden achievement still unlocks and is still
claimable (in the Hidden section). A chosen label/visibility is USER STATE, not
derivable state — there is no predicate or log it could be computed from — so
storing it stays WITHIN ADR-2 (which bans stored DERIVABLES, not stored facts):
it stands with `resolved_at` (ADR-38) and `sort_order` (ADR-43). Hiding is
display CURATION, never deletion: the card, its unlock and its claim all remain.
A side table keyed by achievement key (rather than columns on `achievements`)
lets a locked key carry an override and keeps the append-only unlock table a
pure event log. Backup/restore rides along for free (ADR-26): the table is part
of the whole-file `VACUUM INTO` snapshot, and `reopenDatabase()` re-migrates on
import, so a restored older backup gains the empty table on the way forward.

== ADR-45: History becomes a contribution calendar — same endpoint, a heatmap in place of the skyline

*Context:* ADR-21's activity history first rendered as the house-of-cards
skyline (#53): one tower of cards per local day. At any sustained cadence the
towers stood one or two cards tall, the per-card TCG detail was unreadable at
that size, and the floating card details clipped at the scroll edges. The
record underneath — `GET /api/activity`, dense per-local-day cards and totals —
carried far more than the towers could show.

*Decision:* Replace the skyline with a GitHub-style contribution calendar
(#174) WITHOUT touching the data model. Unchanged: the `/api/activity` contract,
the read-side derivation (`activityService.buildActivityDays`), local-day
bucketing (ADR-21), and the `(wasDrawn, impact)` rarity derivation (#62). New on
the client is `components/HistoryCalendar.tsx` over a pure, unit-tested
`lib/historyCalendar.ts` (the buildActivityDays split, kept DOM- and clock-free).
One tile per local day in Monday-first week columns, shaded by an intensity
level (0–4, blending tracked minutes with completion count); a day's rarest
completion shows as a corner gem (holo/silver) rather than the holo/silver
sheen; the per-day detail — which tasks, completed vs. worked-but-unfinished,
XP, rarity — reveals on hover / keyboard focus / tap as a floating overlay
(a `role="status"` live region) anchored to the active tile. "Load earlier"
widens the window in 26-week steps to the same ten-year `MAX_RANGE_DAYS` cap.
`Skyline.tsx/.css` and their E2E spec are deleted.

*Amendment (#182):* The detail was first a box docked in the calendar footer —
"a panel, not a floating tooltip" — chosen to sidestep the skyline's edge
clipping. But because it sat in normal flow with no reserved height, its
content-driven height (one idle line vs. one row per card) changed the section
height as the pointer swept across cells, shoving the Achievements grid below it
up and down: the page jumped. It is now a FLOATING, out-of-flow overlay
(`position: absolute`) anchored to the active tile, mounted OUTSIDE the
`overflow-x: auto` scroll box with `.cal-section { position: relative }` as its
containing block. Out of flow, it reserves no space, so nothing below reflows;
outside the scroll box (plus a viewport clamp with edge-flip above/below the
tile), it still cannot clip. The `role="status"` live region, focus handling and
tap-to-pin are unchanged, and the fade stays behind `prefers-reduced-motion` —
this corrects the original "docked panel, not a floating tooltip" rationale
while keeping its no-clipping and accessibility guarantees.

*Rationale:* The calendar reads a year at a glance where the tower metaphor
never scaled past a few weeks and buried the record it sat on. Because the
endpoint and derivation are untouched, this is a pure client re-render — no
migration, no server change, and the local-day and rarity invariants carry over

verbatim. The floating, out-of-flow detail overlay (#182, see amendment) is a
strictly more robust successor to the skyline's floating card details — anchored
to the active tile yet clip-free and reflow-free, and it doubles as an
accessible live region. Supersedes the skyline as the Stats activity view
established by ADR-41.


== ADR-46: Hall of Fame — always-visible, name-only spotlight showcase, supersedes the #168 cabinet

*Context:* The Hall of Fame (#145/ADR-38, redesigned as a lit trophy cabinet in
#168) sat behind a collapse toggle and defaulted closed, so the resolved goals
were hidden until a click; each achieved goal hung on a brass plaque crowded
with `Achieved <date>`, `✓ N/M tasks`, and a target-delta chip. Twice the user
rejected it: the trophies should greet them the moment the Goals page opens, not
hide, and the wall of metadata cheapened the reward at rest.

*Decision:* #181 rebuilds the shelf as a spotlight showcase, a pure client
re-render over the unchanged ADR-38 model. (a) ALWAYS visible: the collapse
toggle and its `useState` are gone; a plain static `🏆 Hall of Fame` heading
sits above a case that renders unconditionally. The two `useGoals("achieved")`
/ `useGoals("missed")` queries therefore run on every Goals-page load rather
than only while a panel is open — intended — and the pending guard stays (render
nothing until BOTH have answered) so there is no empty-case flash. (b) Name only
at rest: each achieved goal is a gold cup (the #124/#168 `goal-trophy.svg`)
standing in its own CSS spotlight — a blurred trapezoidal beam from the top of
the case, a warm floor pool, and a tight dark contact shadow so it reads as
standing — with its name below in letter-spaced small-caps dim gold. The brass
plaque and its whole meta block (date, task count, delta chip) are deleted.
(c) Hover/focus intensifies the light and fades in a quiet `Achieved <date>`
caption + Reactivate / Delete strip, absolutely positioned into space the cup
reserves up front, so revealing NEVER reflows the case; `:focus-within` keeps
the actions keyboard-reachable, never hover-only. (d) Missed goals stay quiet
rows below the case, name only at rest, `missed <date>` + actions revealed on
hover/focus in place (the row reserves the strip, an opacity-only toggle, so it
never reflows either). (e) All MOTION — the spotlight intensify, the fades, the
one-hair cup lift — is gated behind `prefers-reduced-motion: no-preference` (the
#62/#123 pattern); the hover end-states still apply instantly under reduced
motion, so the information is always reachable, nothing just animates.

*Rationale:* An always-lit case that greets the user answers the twice-repeated
ask head-on, and the name-only rest state lets each trophy read as a reward
rather than a report — the metadata is one hover or Tab away, not a permanent
placard. The reserved-footprint reveal keeps the drama free of layout jank, and
the reduced-motion gate honours the motion preference without hiding the
controls behind it. Nothing in the data model or the query contract changes:
`resolved_at` (ADR-38) still supplies the hover date, and `targetDelta` survives
in `lib/goalShelf` as a shared helper — only the shelf dropped its delta chip;
the victory overlay still renders one. This supersedes the #168 trophy-cabinet
presentation (brass plaques, glass shelves, collapse toggle) as the Hall of Fame
treatment.


== ADR-47: Achievement chains collapse to a single evolving current-tier card — client-side grouping, claim advances

*Context:* Chains (#156, ADR-42) model a running metric as several keyed levels
— draws `first_draw → draw_10 → … → draw_10000`, and the same shape for
completions, streak, level, goals and tracked hours. The Stats "Achievements"
grid (`AchievementsGrid`) rendered one card per KEY, flat, so every tier of a
chain showed at once: five draw cards, five completion cards, twenty-six tiles
for six chains plus three one-offs. The shelf read as a wall of near-duplicate
locked cards rather than a set of goals, and the user's own framing was to show
only the level they are on: "only display lvl 1 ... if it's done you can get the
exp and it turns into lvl 2 etc." (#183).

*Decision:* Collapse each chain to ONE evolving card = its *current tier*,
client-side, with no server/claim/XP/schema change (the `/api/gamification`
payload still ships all tiers).

* *Shared chain map.* `shared/achievementChains.ts` — a dependency-free sibling
of `shared/achievementKeys.ts` / `shared/achievementTiers.ts` — maps each
CHAINED key to `{ chainId, order }`. It is a pure projection of the server's
`CHAIN_SPECS` (`gamificationService.ts`): `chainId` = the shared `metric`,
`order` = the `target`. The client cannot import `gamificationService` (it pulls
in `db.js`/better-sqlite3), hence the hop; a server drift-guard
(`server/test/unit/achievement-chains-map.test.ts`) pins the map equal to the
projection, the same anti-drift treatment the key and tier lists get. Keys with
no entry are the one-offs (monster_slayer, deck_clearer, early_bird).

* *Current-tier selector.* `lib/achievementChains.collapseAchievementChains`
groups the payload by `chainId` (one-offs each their own slot, first-appearance
order preserved) and picks, per chain, the CURRENT tier: the first tier
(ascending `order`) whose `claimedAt` is null, or the last (maxed) tier once
every level is claimed. `AchievementCard` is unchanged — it already derives
art/rarity/progress/claim state from whatever key it is handed.

* *Claim advances with no extra code.* `useClaimAchievement` already invalidates
`['gamification']`; on refetch the just-claimed tier carries `claimedAt`, the
selector skips it, and the next level becomes current — the card evolves in
place. A wholly-unearned chain shows level 1 face-down (with its progress bar);
a fully-claimed chain shows the maxed tier as a claimed card, so the chain never
vanishes.

* *Defaults.* The heading `\{collected}/\{total}` reflects the COLLAPSED view
(one per chain + one-offs, not the raw 26 tiers); a chain counts as collected
once ANY tier of it has unlocked — monotonic, so claiming can never lower the
count. Hide (#177) and the ✎ editor act on the currently-shown tier's key
(unchanged behaviour per visible card): a hidden current tier moves to the
"Hidden (N)" section as before.

*Rationale:* This is a pure client re-render (ADR-5): unlock, claim, XP, rarity
(ADR-42), the shared key set, and `CHAIN_SPECS` are all untouched, so the grid
becomes a ladder-of-goals view without moving any authority off the server. The
grouping is DERIVED from the payload each render (ADR-2's derived-over-stored
spirit) rather than a stored "current level" counter — claiming a tier is the
only state change, and the advance falls out of the existing refetch. Putting
the chain map in `shared/` with a drift-guard keeps the client's notion of a
chain from silently diverging from the server's `CHAIN_SPECS`, exactly as the
key/tier mirrors do. The one deliberate cost is that a specific non-current tier
is no longer addressable in the grid (its card is only in the DOM while it is
current) — acceptable, since the point of the change is that a chain presents as
one moving target, not a shelf of every rung at once.

== ADR-48: The leverage grade, coaching insights, and `leverage_master` badge are removed — do not grade the user for the algorithm's choice

*Context:* The Stats page carried an A–F "leverage grade" tile and a set of
rule-based "coaching insights", both computed from `highShare` — the share of a
week's tracked minutes spent on 4–5★ tasks (≥60% = A). A matching one-off
achievement, `leverage_master`, unlocked the same "grade A" week. All three
scored the USER on which tasks got the time.

But the user does not choose the next task — the *draw does*. The weighted-random
selection is already biased by impact² and deadline urgency (ADR-25 weight
formula), so the mix of impact levels a week lands on is largely the algorithm's
output, not a decision to grade. The grade also pinned at F for anyone doing
non-goal work (impact stars exist only on goal-linked tasks, ADR-4), punishing a
frame the product itself imposes. Per the user: "the grade is not useful. Because
it's not the user deciding what task to do next. It's the algorithm."

*Decision:* Remove the grade, the coaching insights, and the badge outright.

* *Server.* `statsService.ts` drops `weeklyGrade`, `leverageInsights`, and the
`highShare`/`lowShare` intermediates from the `Stats` payload — the aggregation
now ships only the descriptive breakdowns (minutes by impact, category, goal) and
the estimation block. `get_stats` (MCP catalog) is reworded to stop naming a
"weekly leverage grade". `gamificationService` drops the `leverage_master`
definition and its weekly SQL condition.

* *Shared key set.* `leverage_master` leaves `shared/achievementKeys.ts` and
`shared/achievementTiers.ts`, taking the shipped set from 27 keys to *26*
(23 chained + 3 one-offs: `monster_slayer`, `deck_clearer`, `early_bird`). The
`\{collected}/\{total}` heading and the #183 chain-collapse (ADR-47) are derived
from the payload, so the count follows automatically; `leverage_master` was a
one-off (never in `CHAIN_SPECS`), so the chain map and its drift-guard are
untouched.

* *Client.* The grade tile, its `GRADE_COLORS`, the insights banners, and the
`lowImpactDominant` red-bar treatment of the by-impact chart leave `StatsPage`;
the impact bars stay, now neutrally coloured (dim for 1–2★, accent for 3–5★). The
`leverage_master` art import and `leverage_master.svg` asset are deleted.

*Rationale:* This is descriptive-over-prescriptive: Draw still shows where the
time went — the by-impact breakdown is intact — it just stops assigning the user
a mark for it. XP accounting is unaffected (ADR-5/ADR-42): a never-unlocked key
had no rows in the append-only `achievements` table, so
`SUM(completions.xp_awarded) + SUM(achievements.claim_xp)` never referenced it and
no reader breaks on its absence. Impact input and the draw weighting are
deliberately KEPT (the user chose to keep impact goal-only) — only the act of
grading the user is retired. This supersedes the leverage-grade tile and the
"leverage banners" of the Stats page composition described in ADR-41.

== ADR-49: Production mode — tsx as the production runtime, single-port Express serving `client/dist`, HOST as an env opt-in

*Context:* Until #189 Draw only ran as `npm run dev` (tsx watch + Vite with an
`/api` proxy); `npm run build -w server` was `tsc --noEmit` and nothing served
`client/dist`. The 1.0.0 self-hosted deployment (Raspberry Pi container, #191,
reached from desktop and phone) needs a production mode: one process, one port,
no dev tooling in the request path.

*Decision:* Production is `npm run build` (vite bundles the client, tsc
type-checks the server) followed by `npm start` → `tsx src/prod.ts`. The server
is NOT compiled to JS — tsx stays the runtime in production, promoted from
devDependency to a runtime dependency. `prod.ts` is a separate entry next to
`index.ts` (dev): it defaults `NODE_ENV` to production, refuses to boot without
`client/dist/index.html`, and passes `clientDir` to `createApp()`, which then
mounts `express.static` plus an SPA-fallback middleware AFTER every `/api`
router. The production entry — and only it — resolves the listener host from
the `HOST` env var (`resolveHost()` in `src/config.ts`, default `127.0.0.1`);
the dev entry stays pinned to loopback.

*Rationale:*

* *tsx over emitted JS.* `server/src` imports sibling workspace code from the
repo-root `shared/` directory, so tsc's emitted tree would nest as
`dist/server/src/…` + `dist/shared/…` — breaking every module-relative anchor
(`db.ts` finds `schema.sql` and defaults the data dir next to itself) and
adding an asset-copy step, all to avoid a runtime the project already runs
everywhere else: dev is tsx watch and the MCP adapter (`npm run mcp`) has
always been plain tsx in normal use. One runtime for every mode means no
build-drift class of bugs and no second module-resolution regime; the cost is
one more runtime dependency and a sub-second esbuild transpile at boot (fine on
a Pi). Revisit if boot time or memory on the Pi ever matters.
* *A separate entry, not a NODE_ENV switch in `index.ts`.* npm scripts cannot
set env vars portably on Windows without a helper dependency (`cross-env`);
`tsx src/prod.ts` needs no env plumbing and states its intent in the script
name. Dev behavior is untouched by construction — `index.ts` never mounts the
static middleware.
* *Single port.* The client is static files; a second listener (or a reverse
proxy) would be pure operational surface. Mounting static + fallback after
the `/api` routers keeps the API in charge of its namespace: an unknown
`/api` path is answered by a JSON 404 (the API surface speaks JSON, including
its misses) and never reaches the SPA fallback. The fallback itself answers
only GET/HEAD requests for extension-less paths — a missing asset (a stale
hash after a redeploy) must 404, not arrive as `text/html`. Express 5
(path-to-regexp v8) dropped bare `"*"` routes, so the fallback is a plain
middleware, not `app.get("*")`.
* *HOST opt-in.* Loopback-only stops being an invariant (section 2) and
becomes the default posture: a stock install stays unreachable from the LAN,
and the container explicitly sets `HOST=0.0.0.0`. Restricting `HOST` to the
production entry keeps the opt-in deliberate — an ambient `HOST` export in a
shell profile must not silently move the auth-less dev API off loopback (the
same ambient-injection class that keeps `PORT` ignored). Draw still has no
auth — that gap is #190's password gate, a release requirement for 1.0.0.

== ADR-50: Optional LAN password gate — one env shared secret, HMAC-signed session cookie, header for MCP; a deliberate amendment of the "no auth" guardrail

*Context:* The "no auth" guardrail (section 2) was calibrated to a
loopback-only app. ADR-49 made LAN exposure a supported configuration
(`HOST=0.0.0.0` for the 1.0.0 container, #191), and behind that listener sit
the user's entire task history *and the Anthropic API key* — stored in the
settings DB and readable via `GET /api/settings` and the Settings UI. Anyone
on the network could take both. 1.0.0 needs opt-in access protection that
leaves the localhost experience untouched (#190).

*Decision:* A single shared secret from the `DRAW_PASSWORD` env var switches
the gate on; unset (the default) means no auth anywhere — byte-for-byte the
pre-#190 behavior. When set, `createApp()` mounts a blanket middleware behind
exactly two openings: `GET /api/health` and `POST /api/auth/login`. Every
other request needs one of two equivalent credentials:

* *Session cookie* (browsers): the server-rendered login page
  (`loginPage.ts` — the React client is untouched) POSTs the password; a
  correct one sets `draw_session`, an `HttpOnly`/`SameSite=Lax` cookie
  holding an HMAC-SHA256-signed expiry token. *Session lifetime: 30 days*
  (`SESSION_TTL_MS`), after which the next request lands on the login page
  again. The signing key is derived from the password itself
  (`scryptSync(password, fixed salt)`).
* *Shared-secret header* (`x-draw-password`, non-browser clients): the MCP
  adapter sends it when its own env carries `DRAW_PASSWORD` — both processes
  read the same `server/.env`, and the committed `.mcp.json` stays
  secret-free.

All password comparisons are constant-time (`timingSafeEqual` over SHA-256
digests). Failed presentations — login body or header, which would otherwise
be an unthrottled side channel — are rate-limited per client IP: 5 failures
per 15 minutes, then 429 with `Retry-After`. Two refinements make that
per-IP guarantee real (both from the #190 security review):

* *The limiter keys on the de-proxied client.* The key is `req.ip`. Behind
  the recommended reverse proxy every request's socket peer is the proxy, so
  `req.ip` would collapse to one shared bucket (one attacker could then
  429-lock the owner out) unless Express's `trust proxy` is set — hence the
  `TRUST_PROXY` env var (production entry only; accepts a preset like
  `loopback`, a hop count, or a subnet list).
* *The HEADER path exempts loopback; the login FORM never does.* A header
  request whose de-proxied `req.ip` is loopback is the host itself — the
  in-process assistant (ADR-37) or a same-host MCP adapter, presenting the
  *real* secret — so it is inside the trust boundary and skips the limiter
  entirely (it neither trips it nor resets another client's tally: finding B).
  The login form gets no such exemption: no trusted client ever POSTs to it,
  so a loopback carve-out there would have no legitimate user and would hand a
  misconfigured same-host proxy (`TRUST_PROXY` unset → every `req.ip`
  loopback) unlimited brute-force against the shared password. The form is
  therefore always throttled, keyed on `req.ip`.
* *A present-but-invalid or expired cookie is aging, not attacking.* Only the
  header path records failures; a lapsed or tampered cookie is never counted,
  so an owner whose session expired can never be throttled out.

Unauthenticated `/api` requests get a JSON 401; page views get the login page
with a 401 status. Like `HOST`, only the production entry consumes
`DRAW_PASSWORD` and `TRUST_PROXY`.

*Rationale:*

* *Amending the guardrail, minimally.* "No auth" stays true in spirit: no
user accounts, no roles, no OAuth, no secret in the database. One shared
secret is the smallest mechanism that closes the LAN gap ADR-49 opened, and
off-by-default keeps every existing setup identical. The constraint row in
section 2 now names this exception.
* *Env, never the settings DB.* The DB is the thing the password protects —
storing the secret there would be a bootstrapping paradox and would expose it
through the very settings API it guards.
* *`node:crypto` over a session dependency.* A stateless signed-expiry token
needs no store and no `express-session`/`cookie-parser` (the one cookie is
parsed by hand) — in line with the dependency-security policy and the ~6
runtime-deps guardrail. Deriving the signing key from the password means
sessions survive restarts, rotating the password revokes every cookie, and
forging a token requires the password itself — which already *is* the
credential, so there is no second secret to manage.
* *`/api/health` stays open.* Playwright's `webServer` pre-flight and the
container healthcheck (#191) poll it before anyone can log in; it leaks only
liveness and the server clock.
* *Prod-entry-only, like `HOST` (the ambient-injection class).* `npm run dev`
serves the client through Vite, which the gate could never cover — an
exported `DRAW_PASSWORD` in a dev shell would half-lock dev (API 401s, no
login page) while protecting nothing loopback doesn't already.
* *Threat model — what this protects and what it does not.* It protects the
API key and task data against *casual LAN access* (roommates, guest-Wi-Fi
devices, IoT). On its own it does **not** protect against an on-path attacker:
a plain-HTTP deployment sends password and cookie in cleartext. TLS remains out
of scope for the Express app itself — it is terminated in front of `API_PORT`.
Since #207 that is no longer left to the reader: ADR-55 makes *Tailscale Serve*
the documented path and ships the compose recipe, and the cookie's `Secure`
attribute is derived from `req.secure` rather than being permanently off as it
was when this ADR was written — so a TLS-fronted deployment now gets it
automatically while the plain-HTTP paths described here are unchanged.
**Anyone deploying behind such a proxy must set `TRUST_PROXY`** (`loopback` for
a same-host proxy on bare metal, `1` for the container behind Tailscale — see
ADR-55 for why the preset is wrong there): leaving it unset makes every request
look like it came from the proxy,
so the rate limiter can no longer tell clients apart — it degrades to a single
shared bucket, i.e. effectively off. Prefer `loopback` or a hop count over
`true`: trusting *every* forwarded hop lets a LAN client spoof
`X-Forwarded-For` to forge its rate-limit key. Residual owner-lockout risk:
clients that genuinely share one source IP (several devices behind one NAT)
share a bucket, so one bad actor there can throttle the others for up to 15
minutes — accepted for a single-secret LAN tool; the fixed window was kept
over a progressive per-attempt delay for its simplicity. Where loopback trust
holds and where it doesn't: it is safe in both *supported* deployments —
direct LAN (no proxy, so `req.ip` is the real, unforgeable socket peer) and a
reverse proxy *with `TRUST_PROXY` set* (so `req.ip` is the de-proxied client).
It degrades only in the misconfiguration the docs already warn against — a
same-host proxy with `TRUST_PROXY` unset — and even then the exposure is
narrow: every `req.ip` reads as loopback, so the HEADER path's loopback
exemption makes non-browser (`x-draw-password`) brute-force unthrottled, while
the browser login FORM stays throttled regardless of proxy config (it has no
loopback exemption). Setting `TRUST_PROXY` closes even that gap. The in-memory
limiter resets on restart, which is acceptable because restarting is an owner
action, not an attacker's.

== ADR-51: Multi-arch container image — the 1.0.0 self-hosted deployment, a deliberate amendment of the "no Docker" guardrail

*Context:* The 1.0.0 target deployment is a self-hosted container on a
Raspberry Pi (linux/arm64), also runnable on linux/amd64 (#191). Nothing about
the app was containerized before — the guardrails (section 2) said "no Docker"
outright, calibrated to a run-it-on-your-PC tool. Two facts shape the build:
the production runtime is tsx, not compiled JS (ADR-49 — `npm run build -w
server` is `tsc --noEmit`, so there is no server `dist`), and `better-sqlite3`
is a native module that needs an architecture-matched binary.

*Decision:* Ship a multi-stage `Dockerfile` plus a sample `docker-compose.yml`
and a `.dockerignore`, building with `docker buildx` for `linux/amd64` and
`linux/arm64`. The specifics:

* *tsx is the runtime in the container too.* The image ships node 22 + tsx +
`server/src/**` + `shared/**` (the server imports it at runtime, e.g.
`gamificationService.ts` → `../../../shared/…`) + `client/dist` + a pruned
`node_modules`, and runs the ADR-49
entry directly as one process: `node --import tsx src/prod.ts` (equivalent to
`npm start`, but a single node process so tini can signal it — no npm/tsx
wrapper layer). There is deliberately no compiled server artifact to build or
copy; the same runtime serves every mode (dev, MCP, prod, container), which is
exactly ADR-49's "one runtime, no build-drift" argument carried into packaging.
* *Multi-stage, native-per-arch.* A full `node:22-bookworm` *builder* runs `npm
ci` (so `better-sqlite3` installs a prebuilt binary or compiles from source
with the toolchain present), builds the client with vite, then `npm prune
--omit=dev`. A slim `node:22-bookworm-slim` *runtime* copies the pruned
`node_modules` (carrying the compiled `.node`), the sources, and `client/dist`.
Under buildx the builder runs *as the target architecture* (native amd64, arm64
via QEMU emulation), so the binary it produces matches the runtime stage — no
cross-compilation, no per-arch branching in the Dockerfile.
* *glibc, not musl.* Runtime is Debian slim, not alpine: `better-sqlite3` has
no musl prebuild, so alpine would force a from-source musl build for no benefit.
The builder and runtime share the same glibc ABI, so the compiled binary loads.
* *Single port, non-root.* The container serves the client and the API on one
port (`API_PORT`, default 3001), `HOST=0.0.0.0` baked in as the whole point of
the container (ADR-49's opt-in becomes the container's default posture), and
runs as the base image's unprivileged `node` user (uid 1000) — nothing needs
root. `tini` is PID 1 for prompt SIGTERM shutdown and zombie reaping.
* *Data on a named volume.* All persistent state lives under `DATA_DIR=/data`
(the SQLite `app.db` in WAL mode plus `files/` goal materials, ADR-26), mounted
from a named volume so it survives container recreation and image upgrades. The
mount point is pre-owned by `node` in the image so a fresh volume inherits that
ownership. Backups are unchanged: export the zip (ADR-26), or snapshot the
volume.
* *Healthcheck on `/api/health`.* The container `HEALTHCHECK` (and the compose
one) polls `GET /api/health` with node's global `fetch` (no curl/wget in the
slim image). That route sits *above* the password gate (ADR-50) precisely so
the probe stays green with `DRAW_PASSWORD` set.

*Rationale:*

* *Amending the guardrail, deliberately.* "No Docker" was a proxy for "no
production-deployment complexity" while Draw was a local-only tool. Shipping
1.0.0 as a Pi container is an explicit owner decision (2026-07-25); it is the
*one* sanctioned container, not a general embrace of orchestration —
Kubernetes/Helm, HTTPS termination, and registry/release automation stay out
(the last is #192). Section 2 now names this exception, exactly as ADR-50 named
the "no auth" one.
* *Pairs with the password gate.* The container binds non-loopback by
construction, so a LAN deployment should set `DRAW_PASSWORD` (ADR-50) — behind
that listener sit the task history and the Anthropic API key. The sample
compose carries `DRAW_PASSWORD` and `TRUST_PROXY` as commented opt-ins so a
deployer finds them.
* *Verification.* The container build itself is not exercised in CI (the ubuntu
runner has no guaranteed Docker/buildx, and building under QEMU is slow); it is
verified manually and by the release workflow (#192). What CI *does* pin is the
wiring the container depends on: a contract test asserts the Dockerfile/compose
reference the real `/api/health` route, the `src/prod.ts` entry, the client
build step, the volume, and the non-root user (so a rename breaks the test, not
a Pi deploy), and a runtime test boots the container's exact `node --import tsx
src/prod.ts` invocation as a real process with `CLIENT_DIR`/`HOST`/`DATA_DIR`
set and hits `/api/health` and `/`.

== ADR-52: Scheduled automatic backups — an in-process timer writing to DATA_DIR/backups/, retention by count, restore is import

*Context:* Manual backup export/import exists (ADR-26): `GET /api/backup/export`
streams one zip, `POST /api/backup/import` replaces everything. But nothing runs
it on a schedule. The 1.0.0 self-hosted deployment (a headless Raspberry Pi,
#191, #194) needs backups that *just happen* — with no one to click Export and,
on a minimal appliance image, no guarantee of a system cron either.

*Decision:* An in-process timer, off by default. `BACKUP_INTERVAL_HOURS`
(unset/0 = disabled) is the period; `BACKUP_RETENTION` (default 7) is how many
archives to keep. When the interval is set, the production entry starts the
timer alongside `startServer`; each tick reuses `createBackupArchive()`
unchanged and moves the result into `DATA_DIR/backups/` under a timestamped name
(`draw-backup-<ISO-to-the-second>Z.zip`, colons swapped for dashes so it is a
legal filename everywhere and sorts chronologically), then prunes to the newest
`BACKUP_RETENTION`. Restore adds *no new code*: a scheduled archive is an
ordinary export, restored through the existing `POST /api/backup/import`.

*Rationale:*

* *In the server process, not cron.* The Pi image may ship no cron, and the
server is the one thing guaranteed to be running. `unref`'d so it never keeps
the process alive on its own, and returned as a stoppable handle so shutdown and
tests do not leak a timer.
* *Started next to `startServer`, never inside `createApp()`.* `createApp()`
runs once per integration test; a live `setInterval` there would leak into every
test and keep the runner alive. So the timer is a production-entry concern like
`HOST` and `DRAW_PASSWORD` — and, like them, off unless deliberately configured,
so dev and every test are byte-for-byte unchanged. The tick
(`runScheduledBackup`) and the scheduling loop (`startBackupScheduler`) are
separate and each directly callable, so tests drive one backup without a real
timer and exercise the interval math with fake timers and an injected tick.
* *`DATA_DIR/backups/` is a sibling of `files/`, not under it — the recursion
guard.* `createBackupArchive()` globs `files/` and the DB only, never `DATA_DIR`
itself, so an archive can never contain `backups/`: no archive-inside-archive
growth where each backup swallows all the previous ones. This is an invariant of
where the directory lives, pinned by a test that asserts a produced archive
holds no `backups/` entry.
* *Retention by count, pruned by filename.* The timestamped names sort
lexically == chronologically, so "keep the newest N" is a pure string sort with
no `mtime` read — deterministic and unit-testable with synthetic inputs. Only
names the scheduler itself produces are ever pruned, so a file an operator drops
into `backups/` is never deleted. The just-written archive is passed to the
prune as *protected* and is never a deletion candidate — lexical order normally
puts it last, but the `-N` same-second dedup suffix (`-` sorts before `.`) and a
backward clock step on the RTC-less Pi can both make it sort as the oldest, and
excluding it outright is robust to both (the cost is keeping at most one extra
archive in those rare cases). `BACKUP_RETENTION` itself is never below 1: a
blank, zero, negative, or otherwise out-of-range value falls back to the default
(7) rather than being honored, since keeping zero archives would delete the one
the run just wrote. The interval is likewise capped (596h): `setInterval`'s
delay is a signed 32-bit millisecond int, so a larger value would silently wrap
to a 1ms runaway loop — an over-large `BACKUP_INTERVAL_HOURS` is clamped to the
cap with a stderr warning.
* *A failed backup never crashes the server.* The tick catches and logs
(filename on success, the error on failure) and the schedule continues — a full
disk must not take the app down. Off-device targets (S3, rsync) and a Settings
UI are out of scope (#194): copying `DATA_DIR/backups/` off the box is a
deployment concern, deliberately left to the operator.

== ADR-53: Tag releases, bounded OCI inspection, and detached immutable-SHA publication

*Context:* ADR-51 shipped the container image (#191) but explicitly left
"registry/release automation" out — the image was built locally and had *never
been built by CI at all*. 1.0.0 needs a repeatable way to cut a release: run the
tests, publish a pullable image, and record a Release, with no manual packaging.
The release path must remain isolated from `ci.yml` (PRs + `main`) and `docs.yml`
(Pages), and ordinary pushes/PRs must never produce semver/`latest` tags or a
GitHub Release. #277 adds one narrower exception after those original claims:
a successful protected-`main` push may, in a detached workflow, publish only its
immutable full-commit-SHA tag. It creates no release or mutable channel.

*Decision:* A new `.github/workflows/release.yml` triggered on `push` tags
matching `v*` (and a `workflow_dispatch` dry run). Two jobs:

* *`test` — the gate.* Reproduces `ci.yml` verbatim (type checks + `npm test` +
Playwright E2E). The release aborts here on any failure, so a red commit can
never publish an image or a Release.
* *`publish` — `needs: test`.* QEMU + Buildx build the `Dockerfile` for
`linux/amd64,linux/arm64` and push to `ghcr.io/felixgeisler/draw`.
`docker/metadata-action` derives the tags: `+{{version}}+` from the git tag
always, and `latest` *only* for a final release (a tag with no `-` suffix), so a
pre-release like `v1.0.0-rc.1` publishes `1.0.0-rc.1` without moving `latest`.
Then `gh release create --generate-notes` cuts the GitHub Release, flagging any
`-` (pre-release) tag `--prerelease`. This tag-triggered workflow remains the
exclusive automated producer of semver/`latest` tags and GitHub Releases.

A separate `.github/workflows/edge.yml` is routed by completion of the workflow
display name `CI`, but that name is not authorization. Its `publication`
job can run only when all five event facts agree: conclusion is `success`, the
reported event is `push`, the head branch is `main`, the head repository's full
name equals the current repository, and the reported workflow path is exactly
`.github/workflows/ci.yml`. It checks out exactly that run's `head_sha`, never
the edge-workflow revision or current branch tip. Because it is a
`workflow_run` consumer rather than a PR job, immutable-SHA publication remains
detached from required pull-request checks. A distinct `promotion` job needs
successful publication, repeats those five predicates independently, and
reconciles the mutable `edge` tag to verified freshly fetched current `main`.

The specifics that matter:

* *Built-in token, least privilege, no PAT.* The workflow default is
`permissions: contents: read`; the two write scopes (`packages: write` for the
GHCR push, `contents: write` for the Release) are granted *only on the `publish`
job*, so the `test` gate — which runs `npm ci` (arbitrary transitive install
scripts) and Playwright — never holds a token that can publish. Third-party
`docker/*` actions in that credential-bearing job are pinned to full commit SHAs
(with a `# vN` comment) so a moved tag cannot inject code beside the token;
first-party `actions/*` keep major tags, as in `ci.yml`. `docker/login-action`
and `gh` authenticate with `GITHUB_TOKEN`; the `org.opencontainers.image.source`
label metadata-action emits links the GHCR package back to this repo.
* *GHCR package is private on first publish.* A package first created by a
`GITHUB_TOKEN` push is private, and the token cannot change that — so the
documented `docker pull` path needs a one-time manual step: after the first
release the owner flips the package to *Public* in its GHCR settings (or
consumers `docker login ghcr.io` with a `read:packages` token). This is called
out in the README, CONTRIBUTING, and 7.3 so the "pullable from GHCR" claim is
honest.
* *E2E stays in the gate.* A release is rare and the arm64 native build under
QEMU dominates the wall-clock anyway, so running the *full* suite (not just a
"CI already passed" assumption) is the honest reading of "any test failure
aborts before anything is published" and costs nothing that matters.
* *`latest` never points at a pre-release.* The `-rc`/`-beta` verification tags
must not become what `docker pull …:latest` fetches; only a final `vX.Y.Z`
advances `latest`.
* *A real dry run without spending a tag.* `workflow_dispatch` runs the same
gate and pushes to a throwaway `:dryrun` tag (no `latest`, no version tag) and
creates *no* Release — the way to prove the multi-arch build works before the
first real `v*` tag. It is only dispatchable once the file is on the default
branch (a GitHub constraint), so the practical sequence is: merge → dispatch a
`:dryrun` build to confirm the image builds on both arches → then tag
`v1.0.0-rc.1` for the end-to-end acceptance check.
* *Identity comes from the publish checkout.* Immediately after its checkout,
the `publish` job resolves the full commit with `git rev-parse HEAD` and passes
that value as `DRAW_BUILD_SHA`; this remains truthful when a dispatch supplies
an optional `ref`. Tag pushes pass `DRAW_BUILD_CHANNEL=stable`, while dispatch
dry runs pass `local`. The Dockerfile exposes both build arguments at runtime;
an ordinary local build defaults to channel `local` and an empty SHA. This
contract does not publish an `edge` image or claim that an identity consumer
exists.
* *A bounded, repository-specific inspector is the reusable publication
foundation.* The strict JSON and staged OCI graph core from #274 is integrated
by #276 behind `node scripts/inspect-oci-image.mjs --image
<ghcr.io/felixgeisler/draw:tag> [--expected-revision <sha>]`. The CLI either
checks the supplied revision or derives the revision from the index, and emits a
digest-pinned result only after the named index, digest-pinned index, amd64
manifest/config, and arm64 manifest/config validate sequentially; the core's
one-item plan is the sole authority for the next request and layers are never
fetched. The fixed GHCR boundary permits one fail-closed Bearer exchange for
the exact combined `WWW-Authenticate` value exposed by Fetch (without claiming
visibility of physical header-field cardinality), confines optional paired
Basic credentials to the exact token endpoint and Bearer credentials to the
registry origin, retries only the authenticated named restart, and uses one
resource-specific non-wildcard `Accept` value. Named/digest indexes, manifests,
tokens, and errors still reject every redirect. The sole exception is an
`amd64-config` or `arm64-config` digest-pinned blob GET: it may accept one empty
307 and manually follow one HTTPS Location on
`pkg-containers.githubusercontent.com` whose exact
`/ghcrblobs<positive-decimal>/blobs/<requested-digest>` path binds it to that
config. The complete nonempty signed query remains opaque and is passed through
without application-level query parsing, normalization, or reserialization. The
follow carries only octet-stream and
identity Accept headers--no Authorization, Cookie, or Referer--and rejects any
further redirect.
* *Transport evidence is bounded before interpretation.* Every registry,
challenge/error, token, redirect, and CDN response requests identity encoding,
rejects any Fetch-visible coding other than absent or exact `identity`, and
streams at most 1 MiB of bytes exposed by Fetch before strict parsing or OCI
validation. The 307 body must be exactly empty; the followed 200 config still
passes descriptor size, content type, digest, and optional Docker digest checks.
Six physical requests complete an unchallenged direct graph and eight complete
one with both config redirects. A challenge adds one failed named request and
one token request, so challenged success uses eight direct requests or at most
ten with both redirects. Registry and token allowances do not increase. Every
307 and CDN follow has its own 20-second fetch-and-stream deadline inside the
same non-resetting 90-second overall deadline. Requests remain sequential, stop
at the first failure, and SIGINT/SIGTERM abort the active operation. Exit 0 is
the sole JSON success; structured initial-name absence is exit 3;
usage/credential setup is exit 2; authentication, transport, timeout,
strict-JSON, and graph failures are exit 1. Output is one bounded sanitized line
where applicable and never includes credentials, tokens, capability queries,
complete capability URLs, challenge/error bodies, or ignored error details.
* *The test seam does not widen production policy.* Production always constructs
and validates canonical HTTPS `Request` objects before calling Node 22 global
`fetch`; it has no transport selector or capture facility. Deterministic tests
may inject a trusted Fetch-compatible adapter that maps those already-validated
requests to local HTTP and retains only in-memory, authorization-redacted and
capability-query-redacted evidence. This adapter can technically inspect,
alter, ignore, or replace a request and is not a security boundary. The runner
remains the single policy path, so future publication can call the same
expected-revision CLI without reimplementing registry or OCI rules.
* *The CDN exception is calibrated compatibility, not a provider contract.* Its
GitHub-owned host and path shape reflect GHCR's observed config delivery; any
status, origin, path-shape, or query-presence drift fails closed pending another
reviewed compatibility change. The client deliberately does not interpret the
provider's signed query, and the exception makes no CDN-availability promise.
* *Consistency is not provenance authenticity.* Digest, size, media, platform,
and revision agreement closes internal graph substitution after name
resolution, and descriptor-size plus digest validation detects substituted CDN
config bytes, but an authorized substitution before resolution remains
undetectable without a signature or independently trusted digest anchor. #276
accepts that residual risk and performs no registry mutation, publication, or
promotion.
* *The detached writer is least-privilege and commit-pinned.* The workflow
default remains `contents: read`; its only job has exactly `contents: read` and
`packages: write`, a 60-minute timeout, and non-cancelling per-SHA concurrency
`edge-publication-<event-head-sha>`. Checkout, Node 22 setup, QEMU, Buildx, GHCR
login, metadata, and build/push are the only action invocations and are pinned,
respectively, to
`actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683`,
`actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020`,
`docker/setup-qemu-action@c7c53464625b32c7a7e944ae62b3e17d2b600130`,
`docker/setup-buildx-action@8d2750c68a42422c14e847fe6c8ac0403b4cbd6f`,
`docker/login-action@c94ce9fb468520275223c153574b00df6fe4bcc9`,
`docker/metadata-action@c299e40c65443455700f0fdfc63efafe5b349051`,
and
`docker/build-push-action@10e90e3645eae34f1e60eeb005ba3a3d33f178e8`.
No dependency installation is needed for the repository inspector. Its two
invocations alone receive `OCI_REGISTRY_USERNAME`/`OCI_REGISTRY_PASSWORD` as
step-scoped environment bindings. The pinned login action separately receives
only `ghcr.io`, `github.actor`, and `GITHUB_TOKEN` through its `with` inputs;
build/push inherits that Docker authentication and receives no credential
environment or input directly.
* *Automation-policy first-write-wins, with a fail-closed state machine.* The
workflow derives one lowercase full-40-hex event SHA and one target,
`ghcr.io/felixgeisler/draw:sha-<full-SHA>`, then invokes #276's inspector in
expected-revision mode. Exit 0 must carry valid JSON: its verified index digest
is consumed and no build or package mutation occurs. Exit 3 alone is
an authoritative absence and enables QEMU/Buildx/login/metadata plus one push;
every other exit or malformed success output wedges the SHA without mutation.
The absent path builds exactly ADR-51's `linux/amd64,linux/arm64`, with
provenance disabled, `DRAW_BUILD_CHANNEL=edge`, `DRAW_BUILD_SHA=<full-SHA>`, and
that revision on the image index annotation and both platform config labels.
Afterward, one expected-revision inspection must return exit 0, valid JSON, and
an index digest exactly equal to the build action's top-level digest. Absence,
failure, malformed output, or mismatch wedges the SHA; automation performs no
delete, retry, replacement, or repair.
* *Exclusive automation is a policy, not registry immutability.* This workflow
is the only automated writer of workflow-managed `sha-<commit>` tags.
Non-cancelling per-SHA concurrency makes same-SHA automation runs converge while
distinct commits retain distinct tags, but observation and push are not atomic.
An administrator or compromised GHCR credential can write after absence was
observed and before build/push; the latter may overwrite that external write.
That race is accepted residual risk, not a claim of registry-enforced
immutability or atomic create-if-absent. Publication emits no `edge`, `latest`,
semver, `dryrun`, or other tag and no GitHub Release. A manually verified rollback reference is stably pinned as
`ghcr.io/felixgeisler/draw:sha-<full-40-hex-SHA>@sha256:<verified-index-digest>`.
This immutable publication supplies the edge identity permitted by ADR-70; it
does not add an application identity consumer.
* *Promotion reconciles current main rather than replaying the trigger.* The
separate `needs: publication` job repeats all five authorization predicates and
runs on exact GitHub-hosted `ubuntu-24.04`, with exact Bash on every shell step,
`contents: read` plus `packages: write`, and a 60-minute timeout. Job-level
non-cancelling `edge-promotion` concurrency implements GitHub's global one
running/one pending rule: a newer arrival may replace pending work but never
cancels the running job. Every admitted job therefore fetches current `main`
afresh instead of promoting its trigger SHA; reverse publication completion,
same-SHA reruns, replaced pending work, and later main advancement converge
whenever the current immutable source exists.
* *Authoritative history has an isolated, anonymous boundary.* Promotion's
non-persisting full-history checkout is only a source of workflow and inspector
scripts. Its immediate first Bash step requires the exact clean public origin
and rejects effective extra headers, credential helpers/stores, and fetch/push
URL rewrites before repository-controlled scripts or authenticated operations.
Under `env -i`, retaining only `PATH`, a new empty `HOME`, null global/system
Git configs, disabled prompting/askpass, and an explicitly empty template, it
initializes a fresh bare repository in one unique current-user-owned mode-0700
direct child of `RUNNER_TEMP`. It verifies that bare config, then fetches the
literal public HTTPS URL and exact `main` refspec with an explicitly empty
credential-helper chain, no named remote, no Git-config redirect, and no token
or credential fallback. Only that fetched ref selects the target and only that
bare object database--with alternates and replace refs rejected--may prove an
existing edge revision is a commit ancestor by `merge-base --is-ancestor`.
* *The temporary history lifecycle crosses steps without crossing the credential
boundary.* An initialization-only trap removes the area on failure or
interruption before its exact path and fetched target are handed off through
`GITHUB_OUTPUT`; successful initialization disarms that trap so ancestry can
reuse the bare repository. The ancestry step revalidates the output path,
ownership, exact mode, clean config, and unchanged fetched ref. The final
declared step runs `if: always()`, rejects an absent or unsafe path, removes the
area after no-op, failure, or success, and fails an available runner if cleanup
fails. Forced cancellation or runner termination may prevent that final step;
the fixed GitHub-hosted ephemeral runner is the accepted disposal boundary, and
the area contains only public Git objects/configuration, never credentials or
tokens.
* *Promotion is digest-pinned and fail-closed.* After history establishment,
the shared inspector checks `sha-<fresh-main>` in expected-revision mode. Exit
3 is a successful no-op for in-flight publication and every other nonzero or
malformed result fails without mutation. Existing `edge` absence permits first
promotion; valid presence must supply an ancestor/equal revision from isolated
history. Equal source/edge digests are a no-op. Otherwise one pinned Buildx
setup and GHCR login precede exactly one `imagetools create` from
`sha-<fresh-main>@sha256:<verified-digest>` to `edge`; an expected-revision
post-check must prove both source-digest equality and the fresh-main revision.
Inspector credentials exist only on inspector steps, login receives only its
three approved inputs, and history, Buildx, and imagetools receive no direct
credential. Source absence, invalid/unprovable/non-ancestor state, mutation or
post-check failure performs no delete, retry, rollback, replacement, or repair.
Promotion is the exclusive automated `edge` writer and emits no `latest`,
semver, `dryrun`, release tag, or GitHub Release. Operations, rollback
implementation, signatures, and trusted digest anchors remain outside this
decision.

*Rationale:*

* *Completes the release-and-inspection deferral without changing the app
runtime.* ADR-51 named "#192" as the excluded release automation; that workflow
still makes no application production-code change, and the version bump to
1.0.0 (the `package.json` files) remains a separate concern. #276 separately
adds the production inspector CLI and HTTP client: their boundary ends at
bounded, encoding-checked registry/token/Distribution responses and the strict
#274 graph core, including fail-closed authentication and error classification.
They do not alter the server/client runtime, publish an image, or mutate a
registry. Docker Hub, npm publishing, and changelog conventions beyond GitHub's
generated notes remain out of scope.
* *Separation of pipelines.* Tag triggering still exclusively owns release
artifacts; a pull request never builds or publishes, and an ordinary push can
reach only detached immutable-SHA publication and its digest-verified mutable
`edge` reconciliation after exact successful-main-CI authorization. `ci.yml`,
`release.yml`, and `docs.yml` remain unchanged. Promotion does not create or
discover a release and does not operate a deployment.
* *Verification.* Workflows are not executable in this CI, so (as with the
container contract) text-contract tests pin both workflow shapes. Release tests
retain the `v*`, full-test, semver/conditional-`latest`, two-platform, and GitHub
Release boundary. Edge tests pin the completed-run route, both jobs' five
independent authorization predicates, publication's event-head checkout and seven action
SHAs, promotion's fixed runner/Bash shell and four action SHAs, exact
permissions/concurrency, isolated anonymous public-main history and lifecycle,
Node/credential boundaries, absent-only publication, digest-only promotion,
and both post-checks. Pure state models cover reverse completion order,
same-SHA reruns, valid presence, authoritative absence, one-running/one-pending
replacement, main advancement, non-ancestor/unprovable state,
inspector/validation failure, post-check mismatch, no backward movement, and
the publication path's accepted non-atomic external-write race. Those tests use
no credential, live registry, Docker daemon, package mutation, or Actions
execution. The release image building on both architectures remains
proven by its separately controlled dispatch dry run.

== ADR-54: Phone support as an installable PWA — responsive adaptation, app-shell service worker, no native app

*Context:* 1.0.0 is used from an Android phone against the self-hosted container
(#191, ADR-51), but the client was built desktop-first — with no responsive
baseline at all: before #193 not one stylesheet carried a width-based media
query (every `@media` in the client was `prefers-reduced-motion`), and there was
no web app manifest and no service worker. The product's own one-card-up,
hide-the-mountain design suits a phone screen — the UI had to follow (#193).

*Decision:* Ship the phone experience as an *installable PWA*, not a native or
Capacitor app. Three parts: a responsive adaptation at phone widths that leaves
the card's visual identity untouched; a manifest with regular and maskable icons so
Android Chrome installs the app and launches it standalone; and a *minimal
app-shell service worker*, registered in production builds only.

*Rationale:*

* *PWA over native.* The deployment already serves the app over HTTP on the
LAN, so installability costs a manifest and a worker — no second build
pipeline, no signing keys, no store review, no divergent codebase. A native or
Capacitor shell buys push notifications and a store listing, neither of which a
single-user planner needs; it is a revisit-if-the-PWA-disappoints option, not a
1.0.0 requirement. The accepted cost: no push notifications, and iOS
install-to-home-screen is clunkier than Android's prompt — the owner's device is
Android.
* *Adaptation, not redesign.* The card face's own language — full-bleed art under
its legibility scrim, the category pill, the effort chip, the impact stars, the
holo shimmer on a drawn 5★ (ADR-33, which superseded ADR-31's literal TCG frame;
the vocabulary is listed in the glossary) — is the product's identity; the phone
pass re-flows layout (single column, thumb-reachable bottom tab bar, 44px minimum
touch targets, no horizontal page scroll) and changes none of it. It introduces
ONE width breakpoint, at 640px — the client's first, and deliberately its only
one: five stylesheets hang their phone rules off that same query rather than
growing a scale of thresholds. The tab bar is the one piece of *fixed* chrome the
phone layout adds, which makes its height a constraint for everything that floats
over the page: it claims a z-index band above page chrome and below the
fullscreen overlays, and a floating panel anchored to the viewport (the History
day-detail, ADR-45) has to subtract the bar's measured height — safe-area inset
included — from its own clamp, or its tail is painted over.
* *Service-worker scope discipline — the shell, and only the shell.* `/api` is
never intercepted: requests fall through to the network, so API data can never
be served stale by the worker. That is the hard rule of #193, and it is what
keeps the worker from becoming a correctness problem. The path test is
case-insensitive, because Express matches its mounts that way (#189) — `/API/…`
is API traffic too, and a case-sensitive test would have let its body through the
navigation branch. The content-hashed bundles under `/assets/` are deliberately
*not* precached either — the HTTP layer already serves them immutable (ADR-49),
and a worker copy would be a second cache to invalidate. Navigations are
network-first with the cached shell as an *offline fallback only*, so an online
user always gets the server's index.html and picks up a deploy on the next load;
only an `ok` *HTML* response is allowed to become that shell, so no stray
non-HTML navigation can replace it.
* *Installable, not offline-capable — and the docs say so.* The precached shell
is index.html, and index.html references the content-hashed bundles the worker
deliberately does not cache. An offline launch therefore renders only while the
browser's own (evictable) HTTP cache still holds those bundles: offline is
best-effort, not a promise. That trade-off is accepted rather than fixed —
precaching `/assets/` would buy a genuine offline shell at the cost of the second
cache to invalidate this ADR just refused, and offline-first data was out of
scope from the start. What the worker IS for is installability: Android Chrome
requires a manifest, a registered worker with a fetch handler, and a secure
context before it offers to install.
* *A documented update strategy, so nobody is stranded on a stale shell.*
`sw.js` sits outside `/assets/`, so the production server's header rule gives it
`no-cache` and the browser re-fetches it on navigation; any byte change installs
the new worker, `skipWaiting()` plus `clients.claim()` activate it immediately,
and the activate handler deletes the previous version's cache. The cache name is
bumped when the precached shell list — or what is allowed to become the shell —
changes shape.
* *Registered in production builds only.* The Vite dev server and the dev-mode
E2E suite stay worker-free, so a stale worker can never shadow live-reloaded
code. Registration is progressive enhancement — an unsupported browser or an
insecure origin leaves the app fully functional, just not installable.
* *Touch drag-and-drop needed no rework.* No ADR records the gesture; the
mechanism is in the code, and #193 verified it there: `TaskDnd.tsx` drives the
drag with pointer events and `setPointerCapture`, and `TaskDnd.css` puts
`touch-action: none` on the handle — which is exactly what a finger produces, so
touch support reduced to giving that handle a 44px target on phones. (The
reorder half of the gesture drops onto the gap zones between siblings, whose
stored `sort_order` is ADR-43.) No parallel touch code path, and desktop dragging
is byte-for-byte unchanged. Had that not been true, the existing "Move under…"
menu and keyboard paths were the fallback.
* *The manifest carries credentials, because the password gate covers it.* With
`DRAW_PASSWORD` set (ADR-50) the gate answers 401 for every path except
`/api/health` and the login route — including `/manifest.webmanifest`. Browsers
fetch a manifest *without* cookies by default, even same-origin, so a protected
instance would advertise no manifest and never offer installation; the link
therefore carries `crossorigin="use-credentials"`, which is inert when no gate is
configured. The worker script needs no such flag (a `register()` fetch is
same-origin-with-credentials already), and the worker never caches the 401 login
page because the navigation handler stores only `ok` bodies.
* *Verification.* A mobile-viewport spec (Pixel 7 emulation) walks the core
capture → draw → reveal → complete loop and asserts the document never scrolls
sideways on any main page — including `/assistant`, which has no tab to tap in
the AI-degraded suite and is therefore reached by URL. It measures the touch
targets the 640px rules actually change (the capture form's inputs, selects and
buttons; the drag handle in both axes), proves the bottom bar is *pinned* by
re-measuring after a scroll rather than at offset 0, repeats the
no-sideways-scroll invariant at 360px (the width the acceptance criterion names —
Pixel 7 is 412px), and drives BOTH halves of the touch gesture, reparent and
same-parent reorder, through CDP `Input.dispatchTouchEvent`. Real input matters
here: synthesised `PointerEvent`s never establish pointer capture, so a spec
built on them fails while the feature works. Everything the spec seeds is
removed in an `afterEach` with checked statuses — the suite shares one database,
and a leaked drawable task would change what later specs draw. PWA delivery is
asserted against the *production* server, since the manifest, icons and worker
only exist once vite has copied them into `client/dist`: the manifest declares
regular *and* maskable icons at 192 and 512 (asserted as purpose+size pairs) and
every one of them resolves, index.html carries the manifest link, the
`theme-color` and a `width=device-width` viewport, `sw.js` comes back
revalidating rather than immutable, and the activated worker holds a shell entry
but no `/api` and no `/assets/` entry in any cache — including after a navigation
to `/API/tasks`, which answers JSON and must not become the shell.

*Out of scope:* offline-first data sync, push notifications, and a
native/Capacitor app — all explicitly deferred past 1.0.0.

== ADR-55: TLS is delegated to Tailscale Serve, not a bundled reverse proxy — loopback-only port plus a one-hop TRUST_PROXY, and a request-derived Secure cookie

*Context:* ADR-54 ends on a requirement it cannot satisfy: Android Chrome offers
installation only given a manifest, a registered worker, *and a secure context*.
The container (ADR-51) serves plain HTTP, and neither a bare LAN IP nor an mDNS
`.local` name is a secure context — so on the very deployment the PWA was built
for, the worker never registers and the phone gets a bookmark instead of an app.
The same gap leaves the ADR-50 shared password crossing the LAN in clear. Both
the README and the deployment view said "put a reverse proxy in front" and
stopped there: no configuration was ever shipped, so the instruction was a
dangling pointer rather than a path.

*Decision:* Delegate TLS to *Tailscale Serve* running on the host, and ship the
recipe as documentation plus one behavioural change. `tailscale serve --bg 3001`
terminates TLS with a publicly-trusted certificate for the node's `*.ts.net`
name and proxies to `127.0.0.1:3001`. The compose file gains no service; the
sample documents a *pair* of changes — publish the container port on the host's
loopback only, and set `TRUST_PROXY: "1"`. The `draw_session` cookie's `Secure`
attribute is derived from `req.secure` rather than hardcoded.

*Rationale:*

* *Tailscale over a bundled Caddy/Traefik/nginx.* The alternative was a proxy
sidecar issuing its own certificate from an internal CA, which pushes a root
certificate onto every client — and Android has made user-installed CAs
progressively more hostile, which is precisely the audience this exists for. A
publicly-trusted `ts.net` certificate needs nothing installed on the phone, and
carries the app off-LAN as a side effect. It also adds *no* runtime dependency
and no compose service, so the "~6 runtime deps per package" and the
no-over-engineering constraint (arc42 §2) survive intact — this is the first
infrastructure decision in the 1.0.0 series that amends no guardrail at all,
unlike ADR-50 (auth) and ADR-51 (Docker). The accepted cost is a third-party
account and a client on every device; a self-hoster who refuses that keeps the
plain-HTTP LAN path, which is unchanged and still supported.
* *The two config changes are one decision, and the order matters.* Setting
`trust proxy` while the container is still reachable on the LAN is a downgrade,
not a hardening: any client could then forge `X-Forwarded-For` and choose its
own rate-limit bucket. Binding the published port to `127.0.0.1` first is what
makes the proxy the only possible peer and therefore makes trusting one hop
sound. They are documented together, adjacent, and each comment points at the
other, because splitting them is the failure mode.
* *The value is `1`, not the `loopback` preset — and this is a real trap.*
ADR-50 recommends `loopback` for a same-host proxy, which is right on bare
metal and wrong here: a published Docker port reaches the container from the
bridge gateway, so the peer inside is a `172.x` address and never `127.0.0.1`.
The `loopback` preset would therefore trust nothing, silently leaving `req.ip`
as the gateway for every client — collapsing per-IP throttling exactly as if
`TRUST_PROXY` had been left unset, and letting one attacker lock out every
user. Nothing fails loudly; the limiter just quietly stops discriminating.
* *`Secure` follows the request, never the configuration.* Hardcoding
`secure: true` would be correct for the Tailscale deployment and catastrophic
for the others: the plain-HTTP loopback and LAN paths are still supported, and
there the browser would discard the cookie on arrival, leaving the owner unable
to log into their own server with no error to read. `req.secure` reports
`X-Forwarded-Proto` only once `trust proxy` is configured — which is the same
condition as the terminating proxy existing — so the flag turns itself on in
exactly the topology that warrants it and stays off everywhere else. This is
the same derived-over-stored instinct as ADR-2, applied to a cookie attribute.
* *Verification.* An integration case pins both directions: over TLS the
`Set-Cookie` carries `Secure`, and over plain HTTP it does not — asserted on
the attribute rather than the whole header, so the other attributes stay free
to change. The container contract test pins the loopback-only port form and the
`TRUST_PROXY: "1"` value as *commented* guidance, so the LAN default is not
silently changed and the Tailscale recipe cannot rot out of the sample. The
end-to-end claim — that Chrome offers *Install app* rather than "Add to Home
screen" — is left to manual verification: it depends on a live tailnet and on
Chrome's own install heuristics, neither of which CI can host.

*Out of scope:* a bundled reverse-proxy profile, certificates for a
non-Tailscale LAN, and offline support — the worker still caches only the app
shell (ADR-54).

== ADR-56: Decomposition is offered wherever a task is met — split on any estimated subtask, break down on the drawn card, and the breakdown resolves the card

*Context:* Breaking work down is the app's central premise — nothing enters
the deck until it is small — yet the affordance reached one surface. `TaskRow`
renders only from the Tasks page, and within it Break down was scoped to roots
while Split (#108, the subtask-level equivalent under ADR-16's two-level cap)
was scoped to rows classifying *too-big*. Two dead ends followed. An open
subtask already under `max_draw_effort` offered nothing at all — and since
every *queued* row is a subtask by definition, this read as "queued tasks
cannot be broken down", which is not a rule the product has. And the drawn
card, the one moment you are actually looking at a task and judging it too
coarse, offered Start / Done / Not now / Edit / Delete and no way to
decompose.

*Decision:* Offer decomposition wherever the task is met. Split is gated on
open, non-archived, `parentId != null`, non-recurring, and *estimated* —
dropping the too-big test. The drawn card gains Break down, reusing
`SubtaskEditor` and `AiBreakdownPanel` rather than growing a second editor.
ADR-16 is untouched: no third level appears anywhere.

*Rationale:*

* *The too-big gate had no counterpart in the domain.* The split endpoint
never had one — `routes/tasks.ts` says outright that coupling it to a settings
value buys nothing — so the UI was inventing a restriction the server did not
believe in, and inventing it exactly where it hurt most. The conditions that
remain each mirror something the endpoint genuinely rejects (done/archived,
recurring), so the button no longer promises what the accept will refuse. Two
pre-existing instances of that mismatch are closed at the same time: an
archived root reached through the show-done list offered a Break down that
400s with `ARCHIVED_PARENT_ERROR`, and a too-big *recurring* subtask offered a
Split the endpoint rejects.
* *Requiring an estimate is a UI judgement, and the only one here.* The split
editor pre-fills a deterministic even split, which divides a *total*; with no
estimate there is nothing to divide and the pre-fill collapses to an empty
plan. An unestimated row is already in the triage strip asking for exactly the
thing that would unblock it, one inline action away. Because too-big implies
estimated, the new gate is a strict superset of the old one — nothing that
offered Split before stops offering it.
* *`minParts` exists because the arithmetic and the accept rule disagreed.*
`evenSplitPlan` yields `ceil(minutes / maxEffort)` parts, which is one for a
subtask under the limit, while `minRows` gates accept at two — so the editor
would have opened pre-filled with a single "(part 1/1)" row it would then
refuse to accept. The floor is a parameter defaulting to `1` rather than a
new behaviour, so the server mirror (`splitPlan` in `aiPostprocess.ts`) stays
exact for every other caller. The total-preserving invariant is unaffected: a
floor changes how many parts, never their sum.
* *Breaking the drawn card down RESOLVES it — this is the load-bearing part.*
A parent with children is a container and containers are never drawable, so
the breakdown pushes the card out of the deck. It therefore takes the same
#88 path an out-of-deck edit takes: the pointer is forfeit server-side and the
session holds the card on screen with the resolve hint until it is completed,
snoozed or deleted. Dealing a replacement would have made "break this down"
the re-roll button ADR-13/#88 spent a whole decision removing — fishing for a
comfortable card, one indirection away. The optimistic `hasOpenChildren` on
the session's copy is what surfaces the hint on the same render rather than on
the confirming refetch; the created rows are open by construction, so it is
not a guess.
* *The same two editors, not a third.* The Draw page hosts `SubtaskEditor` and
`AiBreakdownPanel` directly, keeping the AI cost gate, the degraded-mode
hiding and the accept semantics identical to the Tasks page. Re-breakdown
(#67) works there too, so the affordance remains after the card becomes a
container and reads as "add more steps" — the same meaning it carries on a
`TaskRow` parent that already has subtasks.
* *A done leaf still gets nothing, deliberately.* The checkbox is the reopen;
a breakdown offered as a second route to the same state would duplicate it
with a stranger gesture. Unchanged from #122/ADR-32.

*Out of scope:* three-level nesting (ADR-16 stands), decomposition from the
Goals page task section, and any change to the split endpoint's validation.

== ADR-57: Work mode is a sticky per-device deck scope — the existing category chips, remembered in localStorage, applied app-wide

*Context:* There was no way to say "I'm at work, show me work". The Draw page's
category chips were bare page state: they reset on reload, scoped only the next
draw, and the Tasks page never saw them. So household chores sat in the deck
during the work day, and the only remedy was re-picking a chip on every visit.
The vision (§1) points at "multiple decks for different contexts" but lists it
as undesigned.

*Decision:* Make the existing selection *sticky* and apply it across the app.
One category, stored in `localStorage` under `draw.deckScope`, resolved through
a pure module (`lib/deckScope.ts`) and shared by a small React context. The
Draw page's chips read and write it; the Tasks page narrows its tree, triage
strip, snoozed section and reparent targets to it, and quick-capture defaults
into it. No server change — `POST /api/draw` has always taken a category
filter.

*Rationale:*

* *A persistence layer on an existing control, not a new concept.* The
alternatives were a `contexts` table (named decks over sets of categories) and
an `is_work` flag on categories. Both invent a second grouping next to the one
that already exists and already works; the chips' only defect was amnesia.
Doing the small version keeps the door open — if one deck per category proves
too coarse, named contexts can be built on top — while a `contexts` table
built speculatively would have to be migrated away from if it were wrong.
* *Per device, and this is the interesting call.* The obvious home is the
`settings` table, next to `max_draw_effort`. That is wrong here: once the app
runs on a Pi with a phone and a desktop pointed at it, a server-side "current
mode" means switching on the phone silently switches the desktop mid-task. Per
device is both the behaviour people actually want and the one that does not
deepen the single-instance assumptions of *R6* — it is the first per-device
preference in the app, and it moves R6 slightly the right way rather than the
wrong one. The costs are accepted and
real: the scope is invisible to the MCP adapter (correct — an agent asking
"what should I do now?" should see the whole deck), it does not survive
clearing site data, and it is not in the backup.
* *A deleted category must not strand the app.* The stored id is resolved
against the live category list on every render, and an id that no longer
matches resolves to the whole deck. Without that, deleting a category from
Settings would leave an empty deck and an empty task list with no visible
cause — and no chip left on screen to click off. The mirror-image trap is
pruning too eagerly: an empty category list means "not fetched yet" on the
first render, not "no categories exist", so pruning against it would drop a
valid scope on every reload. Both directions are unit-tested.
* *The scope never retracts a face-up card.* Switching mode while a card is
revealed leaves it exactly where it is; the scope applies to the next draw.
The commitment invariant (§8.2) outranks the filter, and a card that could be
made to disappear by touching a chip would be the re-roll ADR-13 removed. This
costs nothing to implement — the standing card derives from the current-draw
pointer, which knows nothing about filters — but it had to be decided and
pinned, because "filter hides non-matching things" is the obvious reading.
* *Stats, streaks and XP stay whole-life.* Scoping them would let someone hide
a broken streak by switching modes, which makes the number mean nothing. The
scope is about what you are asked to do next, never about what you did.
* *An empty scoped page names its cause.* "Nothing here — capture something
above" in front of a full task list is the one way this feature can actively
mislead, and the scope survives reloads, so there is no natural moment where
the user is reminded they set it. Hence both the always-visible strip (which
renders nothing at all when unscoped, so the default app gains no chrome) and
a distinct empty-state message. The strip's ✕ is deliberately reachable from
every page, not only from the Draw page where the chips live.

*Out of scope:* named or multiple simultaneous contexts, multi-category
scopes, scoping by goal (the Draw page's goal select stays per-session), and
any server-side representation of the mode.

== ADR-58: Hall of Fame trophy variety — six designs derived from the goal id, never stored, plain modulo over a hash

*Context:* Every achieved goal hung the same gold cup (#181/ADR-46), so a
shelf of five wins read as one win, five times. #204 asks for design variants
"chosen deterministically per goal". The Hall of Fame has been redesigned
twice already (#168's cabinet, #181's spotlight), so the variants were chosen
from rendered candidates on a reproduction of the real shelf rather than
built speculatively; all five candidates were kept, joining the cup for a
six-design rotation: cup, chalice, star, laurel, obelisk, shield.

*Decision:* The design is *derived at render time from the goal's id* —
`trophyVariant(goal.id)` in `client/src/lib/trophyVariant.ts`, a plain
`id % 6` over an ordered list. No column, no setting, no API surface, no
randomness. Each variant is a committed static SVG in the classic cup's exact
technique: the same three-stop gold gradient, the same offset drop-shadow
group, the same shelf floor at `y=280` centred on `x=150`, so all six stand
on one surface at one scale under the existing spotlight CSS.

*Rationale:*

* *Derived, never stored — the ADR-2 pattern, again.* A stored `trophy_kind`
column would be one more thing to migrate, back up, and expose over the API,
buying nothing: the id is already a permanent fact about the goal, so the
derivation is stable forever and identical on every device. This is the same
shape as `trophyRarity` (#62), which the Trophy deck derives from
`(wasDrawn, impact)` — and like it, the pick costs one modulo per render.
* *Plain modulo over a hash, and that is a considered trade.* Goal ids are
assigned sequentially, so goals achieved near each other in time sit near
each other on the shelf — and `id % 6` guarantees any two ids closer than one
full rotation land on different designs. Two identical trophies can only
stand together once six goals apart in creation order. A hash would look
"more random" while silently allowing adjacent duplicates, which is the one
outcome that makes the feature pointless. The unit tests pin the guarantee,
not the arithmetic.
* *The list order is load-bearing, so it is documented as append-only.* The
mapping has no stored side, which means reordering or inserting mid-list
reshuffles every existing shelf. New designs go at the end; `cup` stays at
index 0, matching the empty-state ghost — which deliberately keeps the
classic cup, since it advertises the archetype, not a variant.
* *Existing shelves change appearance once, and that is accepted.* Goals
achieved before #204 all showed the cup; after it, they show their derived
design. The alternative — grandfathering old goals to the cup — would need
exactly the stored flag this decision refuses, to protect an aesthetic that
was never a promise. The E2E instead pins what IS promised: the pick never
changes across reloads (a trophy that re-rolled on refresh would make the
shelf feel like a slot machine).
* *The art is constrained so the shelf stays one composition.* Hard rules for
every variant, checked in review rather than code: the identical gold
gradient (unique ids per file, since inline SVGs share a DOM id namespace
when inlined elsewhere), accents only from the cup's own palette, the same
`translate(4 7)` shadow technique, silhouette-first detailing (fine
engraving vanishes at the rendered 122px), and the shared floor line — the
spotlight beam, pool and contact shadow in GoalShelf.css are positioned
around that floor and were not touched. ADR-46's name-only-at-rest reveal is
untouched too; only the `<img>` src varies.

*Out of scope:* user-selectable trophies, rarity-graded designs (the Hall of
Fame celebrates outcomes, not the algorithm's opinion of them), and variant
art for missed goals — a defeat stays a quiet row, not a different statue.

== ADR-59: The achievements heading counts keys, and chain cards wear tier pips — the collapse stops hiding the climb

*Context:* ADR-47 collapsed each chain to one evolving card, which was right
for the grid and wrong for the numbers around it. The heading counted
collapsed SLOTS with a monotonic per-chain "collected" flag, so "9/9
collected" could stand over a grid of face-down cards with 17 of 26 tiers
still locked — the owner read it as a bug, and as a metric it was one. And
nothing on a collapsed card said which rung of its chain it was: the depth
ADR-47 deliberately hid from the DOM was hidden from the user too.

*Decision:* The heading counts KEYS — unlocked over total, excluding keys
hidden by their own ADR-44 customization from both sides. Chain cards wear a
pip row: one dot per tier in ascending order — solid gold claimed, bright
unlocked-unclaimed, dim locked — derived in `collapseAchievementChains`
(`tierStates`) and passed to the card as display-only props. One-offs get no
pips: a single-tier row is noise pretending to be information.

*Rationale:* The key count is the number the collection actually asks about
("how much of this is mine"), it can still only rise on a claim (unlock rows
are append-only), and it is now pinned by an E2E in a state where slot- and
key-counts differ, so the old semantics cannot silently return. The pips are
NOT the rejected TCG level-star row (ADR-33): they encode chain progress in
the collection's own dim-gold idiom, sit under the name, and the earlier
`.trophy-stars`-stays-dead pin holds unchanged. Unlock, claim, XP, rarity and
the collapse selector are untouched — this is ADR-47's display layer growing
one honest signal, not a semantics change. Static paint; nothing to gate
behind reduced motion. The pip states are spoken as one text alternative
("chain level 2 of 5") rather than five unlabeled dots.

*Out of scope:* per-tier claim buttons on the collapsed card (the current
tier remains the only claim surface), and any server change — the payload
already shipped every tier.

== ADR-60: The catalog grows to 37 keys — two chains for the app's own mechanics, five event one-offs, all derived from existing logs

*Context:* 26 keys plateau fast: after the first week a normal user has the
level-1 tier of most chains and all three one-offs, and the grid goes quiet
(#223). The gap was thematic too — nothing rewarded the two behaviours the
product is actually about: trusting the deck, and finishing the steps that
breaking-down produces.

*Decision:* Eleven new keys, no new stored state (ADR-2). Two chains: *drawn*
(completions with `was_drawn AND NOT was_warmup` — the ADR-30 gambled sense
the ×1.5 and the trophy rarity already use) at 10/100/1000, and *steps*
(completions joined to `parent_id IS NOT NULL`) at 10/100/500. Five one-offs:
`holo_hunter` (a gambled 5★ completion — exactly the trophyRarity holo
condition), `momentum` (the ×1.25 condition completeTask already computes),
`well_rounded` (completions across three categories), `night_shift` (a
completion between 00:00 and 05:00 local), and `comeback` (completing the day
after a freeze-covered day, read from the streak fold's own `frozenDays`).

*Rationale:* Event-shaped conditions are judged from the completion's own
facts, not re-derived: `completeTask` hands `checkAchievements` a
`completion` payload (wasDrawn, wasWarmup, momentum, the stamped instant), so
display, XP and unlock can never disagree about what a completion was — and
R8's one-door rule holds, since the facts travel through the same call the
completion already makes. The steps and well-rounded conditions ride live
task joins, so undo and delete lower them — the accepted completions-chain
semantics, unchanged. `night_shift` reads the local clock and `comeback` the
local day (#219's rules: never UTC here). Art ships with every key — the
emoji fallback is a degraded state, not a plan — generated to the #124 house
conventions (300×420, dark tinted ground, radial glow, one bold motif above
the caption band, per-key gradient prefixes) and committed as static files
like every predecessor.

*Out of scope:* AI- or backup-gated achievements (paid-feature gating; new
`checkAchievements` call sites), rebalancing existing tiers or claim XP, and
retroactive unlocks — the new chains count from the logs as they stand, so a
long-time user may unlock several tiers on their next completion, which is a
feature.

== ADR-61: Boss battles — a goal's remaining work as an HP bar, derived twice over and never a judgement

*Context:* A goal with 400 minutes of open work was a number in a chip, and
the count-based progress bar (done/taskCount) treats a 5-minute errand and a
90-minute session as equal progress. The app's language is cards and rarity;
a goal deserves to be an opponent (#229).

*Decision:* Goals with estimated leaves render a *boss HP bar* on the Goals
page. Max HP is a new derived field on `GET /api/goals`
(`totalEffortMinutes`: the `remainingOpenEffortMinutes` leaf rule over open
AND done leaves), current HP is the remaining sum, damage is the difference.
The pure client combine lives in `lib/bossBar.ts`. *Enrage* is the
feasibility chip's own `infeasible` verdict wearing war paint — one verdict,
two costumes, never a second classifier. Goals without any estimated leaf
keep the count bar: no minutes, no HP to mean anything.

*Rationale:* Remaining ≤ total holds by construction (same leaves, same NULL
skips, archived leaves out of both — a split-in-place original was replaced,
not defeated), so the fraction cannot overflow; the lib still clamps for
mid-refetch payload skew. HP falls live through the existing `['goals']`
invalidation on task mutations — zero new plumbing. Effort-weighted progress
is honest in exactly the way the count bar was not, and it stays arithmetic
about WORK: no grading of choices (ADR-48), no judgement about which tasks
fell. The pulse animates only under no-preference; the enraged end-state
colors apply either way (#62 pattern). The downed state (all estimated leaves
done) dims the bar and hands off — the kill screen is the existing
goal-achieved overlay, not a second celebration.

*Out of scope:* boss art/avatars, damage numbers floating off completions,
and any change to the feasibility classifier itself.

== ADR-62: The XP shop — an append-only ledger, booster packs of card backs, and the purchase row as the freeze token

*Context:* XP was a pure score: levels its only meaning, claiming its only
decision (#230). Nothing in the economy looped back into the product's card
identity, and the pack-opening moment #224 built existed only for unlocks.

*Decision:* Migration v17 adds `xp_ledger(amount, reason, ref, created_at,
UNIQUE(reason, ref))` — the third stored XP source after completions and
claims (amending ADR-42 exactly as ADR-42 amended ADR-5): purchases are
negative rows, duplicate refunds and future payouts positive ones, and
`totalXp()` sums all three. Still no counter column anywhere. The shop
sells a *booster pack* (250 XP → two card-back pulls, rarity-weighted,
duplicates refund 75) and a *streak freeze* (500 XP, capped at the #58 bank).
Cosmetics live in settings (`owned_card_backs`, `equipped_card_back`);
the Draw page front face wears the equipped weave via a `data-back`
attribute whose CSS default — and unknown-key fallback — is the shipped
classic.

*Rationale:* The client mints a `ref` per purchase click and the ledger's
UNIQUE(reason, ref) turns any replay into a 409 — the claim endpoint's
double-click safety, generalised. Spending can lower the level (the level
chain's progress bar may regress — the undo precedent); unlocked
achievements never re-lock, because that table is append-only. The freeze
purchase deliberately writes NO streak_freezes row: the milestone table's
UNIQUE(milestone_day) holds one row per day, and a shop row there would also
make shouldEarnFreeze see "today already earned" and silently swallow a
real organic milestone landing on the purchase day. Instead the buy:freeze
LEDGER ROW IS THE TOKEN — earnedFreezeDays() derives it from the purchase's
local day, the fold already counts multiple earns per day, and the
same-day-organic-earn regression is pinned by an integration test. Pull odds
are a service fact pinned with an injected rng; the HTTP surface promises
only pack shape and balance arithmetic. A full bank refuses BEFORE the
charge — a refusal that costs XP is a bug, not a rule.

*Out of scope:* consumable items beyond the freeze, trading/duplicates
protection beyond the flat refund, and pack pity timers.

*Amendment (#263, schema v18):* the XP purchase model is retired. Historical
rows remain immutable history, but only `challenge` contributes to permanent
XP; `buy:freeze` remains solely a historical freeze-replay input. The shop GET
is transitional Gold + bank + settings-owned collection/equipment, with no XP
or costs. Every purchase POST reaching the route returns
`400 {"error":"shop purchases are unavailable"}` without RNG or writes. Pack
and direct-freeze controls are removed. The existing card-back settings and
equip/Draw behavior remain authoritative. Empty append-only `gold_ledger` and
immutable `pack_openings` establish the next contract without a producer.

== ADR-63: The dealer's daily challenge — hash of the local day, derived progress, a ledger row as the payout

*Context:* The deck deals work but never sets a stake (#231). A small daily
objective gives each day a shape and gives the #230 economy an income side
beyond claims.

*Decision:* One challenge per LOCAL day, picked by hashing the day string
over a fixed pool (complete 3, complete 2 drawn, complete 2 steps, finish
before noon, track 30 minutes) — derived, no storage, no config; the pool is
APPEND-ONLY, since reordering would retroactively rename every historical
day's challenge. Progress derives from the day's own rows via localDayBounds
(#219 rules; noon is parsed on the local clock, not start+12h, so DST days
stay honest). The payout is +50 XP as an xp_ledger row with
UNIQUE(reason='challenge', ref=day) — at most one per calendar day no matter
how many events re-evaluate it. Two callers land it, both through ONE
function (payChallengeIfDue): completeTask, and the timer-stop route — the
track challenge's satisfying event is a stop, not a completion. The R8
concern (a new event path skipping the check) has a single name to grep for.

*Rationale:* A GET never pays — the route ships a read-only snapshot and the
payout rides the mutating transaction that satisfied it, so the chip can
never show XP the ledger does not hold. The before-noon window is
[day-start, 12:00) EXCLUSIVE — pinned after the first integration run
failed on a seed at exactly noon. The E2E drives whatever objective the real
date names through the real API rather than pretending to choose one, and
sits out the 30-tracked-minutes day: 30 genuine minutes are nobody's E2E
budget, and the payout path is integration-tested.

*Out of scope:* challenge streaks/history, rerolls, difficulty tiers, and
pack rewards (the payout stays plain XP; what it buys is the shop's business).

*Amendment (#263):* `challenge` is now the only XP-ledger reason included by
`totalXp()`. The existing +50 XP producer is unchanged. `challenge` is reserved
as a future Gold-ledger reason, but v18 adds no Gold producer and does not copy
challenge payouts into Gold.

== ADR-64: The estimation hint becomes tap-to-apply and reaches the triage strip — and applying dismisses it

*Context:* The #55 hint whispered per-category bias in TaskForm but was
display-only, and the triage strip's inline estimate — where estimates are
typed with the LEAST reflection — had no hint at all (#232).

*Decision:* The hint gains a "use N min" button on both surfaces. Applying
merely TYPES the number: the field stays the authority, anything typed
afterwards wins, and nothing is ever auto-applied (ADR-48's spirit — inform,
never override). The strip's EstimateInput becomes a controlled input
carrying the same hint, aria-live semantics included (#103).

*Rationale:* The one non-obvious rule: APPLYING DISMISSES THE HINT.
Recomputing it off the just-applied value would scale the bias again and
chase its own tail ("use 42" → "use 60") — advice that never settles.
The dismissal keys on the applied value, so typing any other number re-arms
the coaching. estimateHint() itself is untouched: same preconditions, same
rounding, same silence when the suggestion equals the input.

*Out of scope:* auto-applying, per-task learning, and any change to the
bias math or its minimum sample.

== ADR-65: The weekly run report — a closed week folded client-side from the activity payload

*Context:* Stats answers "where did the time go" but never closes a week
(#233); the streak-and-XP loop had no weekly heartbeat.

*Decision:* A "This week" recap card at the top of Stats: completions,
minutes and XP with deltas against the previous seven days, the best day,
and the trophy rarities minted (the ADR-45 derivation over completed cards).
Folded in a pure client lib (`lib/weeklyReport.ts`) from the SAME activity
payload the History calendar fetches — no new API, no stored aggregates
(ADR-2). Weeks are LOCAL and Monday-first (the History calendar's
convention); the fold is pure date-string math over an injected "today",
so its tests stay green at any wall-clock hour and in any suite timezone
(#219's rules, applied preemptively). A week with no activity renders
nothing: a recap of nothing is noise, not encouragement.

*Rationale:* Client-side because every number is already in the activity
response — a `/api/report` endpoint would be a second aggregation to keep
honest. Deltas compare exactly the seven days before the week's Monday, not
a rolling window, so Monday morning's report compares a full closed week.

*Out of scope:* estimate-accuracy trends (the estimates panel below owns
those), history beyond one week-over-week comparison, and any server-side
aggregation or storage.

== ADR-66: Draw Wrapped — a year folded client-side, shipped as a local PNG

*Context:* A year of use produces nothing shareable (#234); self-hosters
love artifacts.

*Decision:* A "Your year" panel closing the Stats page, folding the
CALENDAR year from payloads the page already holds: activity days (cards,
hours, XP, holos), the gamification snapshot (achievements + full-history
frozen days), the achieved-goals list, and the rest-weekday setting. The
fold lives in `lib/wrapped.ts` — pure date-string math over an injected
"today" (#219 rules). "Deepest streak" replays the live streak's
semantics over the year: completion days count, recorded frozen days and
the configured rest weekdays bridge, nothing else does. The CURRENT
rest-weekday set applies to the whole year, because config history is not
recorded and pretending otherwise would be a second streak implementation.
The shareable is a 1080×1350 PNG drawn on a local canvas with the palette
inlined (canvas cannot read CSS variables, and Wrapped keeps the dark card
ground even if a theme ever changes the live tokens), saved via an
`<a download>` — no data leaves the machine, nothing is stored. The panel
opens from a one-line teaser (§8's hide-the-mountain rule) and the reveal
animates only under `prefers-reduced-motion: no-preference`.

*Out of scope:* month-by-month breakdowns, multi-year history, social
integrations, and any server-side aggregation.

== ADR-67: Outbound notifications — one post-commit fire-and-forget door

*Context:* A self-hosted Draw is invisible when closed (#235); unlocks and
felled goals deserve a phone ping without shipping a push service.

*Decision:* One `notify_url` setting, ntfy-compatible (plain-text POST with
Title/Tags headers). Empty means OFF, and the module makes ZERO network
calls. Every send goes through ONE function — `notify()` in
notifyService.ts — so a new event path has a single name to grep for (the
R8 rule, same as payChallengeIfDue). Callers are ROUTES, never services,
and they call it strictly AFTER the write transaction commits: a
notification about a rolled-back unlock would be a lie, and a slow webhook
must never hold a SQLite write lock. Delivery is fire-and-forget with a 3s
abort; failures log one warning and are swallowed — the app must feel
identical with a dead endpoint. Events: achievement unlocks (batched per
action, so a completion cascade is one ping, from the tasks, draw, goals
and claim routes), goal achieved, and daily challenge completed. The URL is
PRIVATE like the Claude API key — an ntfy URL embeds the topic, and knowing
the topic means posting to the user's phone — so it is excluded from
GET /api/settings and managed write-only via /api/notify (presence flag,
PUT/DELETE, and an awaited test send that reports honestly).

*Rationale:* The fetch implementation is injectable and the test route
sends through the same injectable, so the whole feature is tested without
ever opening a socket — including the load-bearing zero-calls-when-unset
assertion.

*Out of scope:* retries/queues, per-event toggles, payload templating, and
inbound webhooks (an automations API is its own issue if wanted).

== ADR-68: Command palette — server-side search that ignores work mode, a z-slot at 85, and 'd' that navigates instead of dealing

*Context:* Capture was fast, retrieval was not (#243): one search box in the
whole client (scoped to goal-less tasks inside the goal editor) and zero
global keyboard entry points.

*Decision:* One Ctrl+K palette mounted in the app shell, backed by a new
`GET /api/search` over task and goal titles, plus four global single keys
(n capture, d draw page, space timer toggle, ? shortcut sheet). Four calls
worth pinning:

* *Search runs server-side and ignores deck scope.* Work mode (ADR-57) is a
per-device display preference; the palette exists to find what the deck and
pages deliberately hide — done tasks, subtasks behind their roots, goals of
any status, other categories. Only `archived` stays invisible: it is the
soft-delete state, not work. Matching folds case AND diacritics by NFD
normalization in JS — SQLite's `LIKE` folds ASCII only and the repo
registers no `db.function` — so the route selects broadly and filters in
process (single-user DB), which also makes user-typed `%` and `_` literal
for free. No index, no FTS table, no schema change (ADR-2's derived-over-
stored spirit). Landing on a hidden row clears the scope: the scope yields
to the search, never the other way round.
* *`d` navigates to the deck; it never deals.* The issue text said "d draw",
but a draw is a commitment (#88) — a stray keypress must not gamble for the
user. `d` lands on the idle face-down deck, focused (programmatic focus
only, `tabIndex -1`); dealing stays one deliberate click. The same rule
shapes space: with no running timer and no current draw it is a no-op,
never a start of something random.
* *z-index 85.* Above the phone bottom nav (80) — a modal must cover the
page — and below the focus/victory overlays (90) and the achievement toast
(100): Ctrl+K must not paint over a running focus session, and unlocks
announce over everything. Documented in the index.css ladder comment.
* *One inertness rule, read off `inert`.* The single keys are dead while
typing (input/textarea/select/contenteditable), during IME composition, and
while any modal is open. "Any modal" is detected as the `inert` attribute
useModalFocus already puts on `#root` — every current and future dialog
opts in by construction, no overlay registry to maintain — and the
attribute is held by count, so stacked dialogs cannot strip each other's
inert. Space additionally yields to a focused button/link/`role=button`:
it is their native activation key, and stealing it would also cancel the
click via preventDefault. The chord is platform-split — Cmd+K on macOS,
where Ctrl+K is the native kill-to-end-of-line editing command, Ctrl+K
elsewhere; Shift and Alt disqualify (Firefox devtools, AltGr layouts). It
is exempt from the typing rule only, so the palette opens even from inside
the capture field, but it refuses to open under a foreign overlay (focus
session, victory — z 90 over the palette's 85): an invisible dialog must
never steal focus. Inside the open palette, keys pressed during IME
composition (Arrow/Enter/Escape picking, committing or cancelling a
candidate) belong to the IME, not the dialog. The decisions are pure
functions (`lib/keyScope`, `lib/paletteNav`) so the DOM-less client suite
pins them.

*Out of scope:* fuzzy ranking, search over descriptions/materials/notes,
custom keybindings, and scrolling to a goal on the Goals page (closed by
#246: goals now land with the same router-state scroll-and-flash as tasks).

== ADR-69: Design foundation — a token layer that renames instead of retunes, opacity-only row reveals, one SVG icon set

*Context:* The client had colour tokens and nothing else (#244): no spacing,
type, radius, elevation or motion scale — every stylesheet picked its own
literals. Task rows buried their own title under five always-visible labelled
buttons, and emoji served as the icon set, rendered with per-platform shapes
and widths. This is the floor for any later visual direction; it must change
structure without changing identity.

*Decision:* Four calls worth pinning:

* *Tokens rename, they do not retune.* The `:root` layer (`--space-*`,
`--text-*`+`--lh-*`, `--radius-*`, `--elev-*`, `--dur-*`, `--ease-standard`)
names the values the UI already uses — `--text-sm` is the app's real 13px,
not a rounded ideal — so adopting a token never changes computed output.
Genuinely bespoke values (the card face's 16px frame, the 7s holo drift, the
half-height progress pills, the calendar's tile-coupled 3px) become NAMED
file-local custom properties at the top of their own stylesheet instead of
fake scale rungs. A node-side vitest (`designTokens.test.ts`) keeps the five
migrated stylesheets free of bare duration/radius literals permanently, with
the custom-property declaration as the escape hatch. Tokens replace VALUES
only: motion stays inside its `prefers-reduced-motion: no-preference` blocks
(the #62/#123 idiom) — hoisting a declaration and zeroing a token under
`reduce` would flip the computed `0s` several specs assert.
* *Row actions reveal by opacity ONLY.* The secondary controls collapsed
into a `.row-actions` icon cluster: hidden at rest on hover-capable devices,
revealed by `.task-row:hover`/`:focus-within`, always visible under
`(hover: none)`. Never `display`/`visibility`/`pointer-events` hiding — the
buttons must keep their tab stops, geometry and clickability for keyboard
users and for Playwright, whose click hovers first. The two rarest actions
(Move under…, Delete) moved into a kebab popover (`.row-menu`) — a popover,
not a modal: no root inert, plain buttons, Esc returns focus to the trigger.
Titles that specs select by (`Edit`, `Promote to top-level`) survive
verbatim; accessible names stay the old labels.
* *One inline-SVG icon set* (`components/icons.tsx`): single 2px stroke,
`currentColor`, 24-box, sized by consumer CSS, every icon `aria-hidden` so
names never leak into links/buttons. Emoji stays only where it is content
(category emoji, achievement art, the TaskBadges chip vocabulary) — chrome
emoji is gone, brand included.
* *Daily-surface motion on the new tokens*, all behind `no-preference`:
route enter (one keyed wrapper in App.tsx around `<Routes>`, not seven
per-page `.content` roots), list entry for freshly captured rows (the
palette-flash classList idiom, never a prop through the tree), and a
delete-only row fade. Complete deliberately gets NO leave-fade: under
"show done" the row STAYS in the list, and a fade would strand a visible
row at opacity 0.

*Out of scope:* the visual direction itself (palette, felt/gilt), colour
tokens beyond the existing set, de-emojifying TaskBadges, and any spacing or
type normalization that would change computed output.

== ADR-70: Updates over the air — a default-on check, the version behind the gate, a trigger instead of the socket

*Context:* A self-hosted container on a Pi (#191, ADR-51) has no app store
and no update nag: releases land on GHCR (#192, ADR-53) and nothing tells
the owner. #247 wants Draw to notice a new release, say so, and offer a
one-tap apply — on an app whose deployment story is "a container that only
mounts `/data`" and whose only pre-auth endpoint is `/api/health` (ADR-50).

*Decision:* Three calls worth pinning:

* *The check is default-ON, and off means zero calls.* One GET per
`UPDATE_CHECK_INTERVAL_HOURS` (default 24) to the GitHub latest-release
endpoint, first ~60s after boot with jitter, never in the boot path. A
self-hosted app that never phones home about updates rots silently; the
counterweight is scope and a real off-switch — the request carries nothing
but the `Accept` header (no token, no telemetry), and both the
`update_check_enabled` setting and `UPDATE_CHECK_INTERVAL_HOURS=0` mean
zero outbound calls and zero timers, the #235 rule, gating even the user's
own "Check now". Unlike `BACKUP_INTERVAL_HOURS`, garbage in the env knob
falls back to the default rather than to disabled: a typo silently turning
a default-on feature off would be a setting that lies (the
`warmup_every_hours` lesson). Comparison is a pure semver module — numeric
fields, prereleases offered only to prerelease runners, unparseable tags
fail closed — and the running version is `server/package.json`, read once
(the root package.json and the MCP banner literal are not sources of
truth; a test pins the choice). The authenticated status also reports flat
build-identity fields: `buildChannel` trims `DRAW_BUILD_CHANNEL` but accepts
only exact lower-case `stable`, `edge`, or `local` (otherwise `local`), and
`buildSha` trims `DRAW_BUILD_SHA` but accepts only a full 40-character ASCII
hex SHA, normalized to lower case (otherwise `null`). `buildIdentity` is
`<channel>:<sha>` when valid and `<channel>:version-<server package version>`
otherwise. These fields do not change release checking: authenticated Settings
keeps `Draw <package version>` as the running version and separately displays
`<channel> · <full SHA>`, or `<channel> · package <version> (SHA unavailable)`
when no SHA was shipped. No other client surface consumes the identity. First
sighting of a new version pays ONE notification through the #235 door, deduped
in a settings row so restarts
never re-send. Forced checks are throttled server-side (one outbound GET
per 30s window, cache served inside it) so a hammered button cannot burn
GitHub's unauthenticated rate budget, and a failed re-check retains the
last successful sighting — a blip must not un-light the banner for a day.
* *The version sits behind the password gate.* `/api/health` stays exactly
`{ok, time}`: version and update state ride the authed `GET /api/update`.
Liveness is public infrastructure; "which exact build is this" is
reconnaissance, and the post-restart readiness probe needs only health.
* *Applying is a trigger, not the socket.* Draw never mounts `docker.sock`
— a compromise of the app must not be root on the host. "Update now" is
one POST to a user-configured trigger URL (Watchtower `http-api-update`,
label-scoped, polling off — deployment view 7.5), `Bearer` token attached
only there and never on the check request, managed write-only like
`notify_url` (presence flag on read, excluded from `GET /api/settings`).
No trigger configured -> `409` plus guidance, not a broken button. No
auto-apply: the check may run daily, but a human taps the button. After
apply the client polls `GET /api/update` (3s, 5-minute budget) and reloads
once the canonical `buildIdentity` differs from the identity at apply time,
including when the package version is unchanged. A versioned, exact-key
sessionStorage union records either the changed channel/full SHA or the
channel/package fallback; authenticated Settings removes every present value
on its single read and displays a valid, successfully consumed notice once.
Malformed, legacy, or inaccessible storage is silent, and a failed poll tick
during the container swap is never a reason to reload. A trigger that ANSWERS
non-2xx is remembered as
`lastApplyError` and stops the poll with an error line; a dropped or
aborted socket stays warn-only, because that is exactly what a successful
swap of the very container looks like.

Mutable-edge promotion is independent of this semver/GitHub-Release discovery
and trigger contract: moving `edge` neither opts a deployment in, applies an
update, nor operates a deployment. ADR-70's application behavior therefore does
not consume the mutable tag.

*Out of scope:* auto-apply on a schedule, build-identity consumption outside
authenticated Settings, edge image publication/promotion behavior, rollback
automation (pin the previous tag + restore a backup, 7.5), and bare-npm
self-restart — there the check and banner work, the button stays hidden.

== ADR-71: Card-table identity — felt ground, brass accent, serif on the card face only

*Context:* The app's chrome was neutral charcoal-and-blue while its reward
layer already spoke another language: a lit dark-gold trophy cabinet, brass
plaques, rarity sheens, booster packs (#181, #156, #230). #255 commits the
whole app to that language — direction B of the pitched mockups: the deck
becomes a card table, so the reward layer stops looking bolted on. Built on
the #244 token layer, so most of the reskin is one `:root` retune.

*Decision:* Five calls worth pinning:

* *The casino line is the operative constraint.* The sheen comment in
index.css — "a glint you notice when you look, not a casino" — governs the
whole identity: the deal's gilt sweep runs ONCE per fresh deal (a restored
card is not an arrival and stays quiet), the hover tilt is ≤5° and releases
fully at rest, nothing loops on any interactive element, and every new
motion sits inside its `prefers-reduced-motion: no-preference` block
(ADR-69's gating idiom, unchanged). The tilt transforms `.draw-face.back`,
composed onto its own `rotateY(180deg)` — never `.draw-card`, whose settled
pure-flip matrix the holo specs byte-pin.
* *Tokens retuned in place; the NAMES and the RATIOS are the contract.* The
#244 token names survive (`--bg`, `--accent`, …) with felt/brass values, and
a permanent sibling gate (`tokenContrast.test.ts`) computes WCAG ratios from
the actual `index.css` values with `lib/cardVisuals`' own contrast helpers:
text/bg ≥ 7:1, dim/bg ≥ 4.5:1, panel variants likewise, primary-button
ink on `--accent` ≥ 4.5:1, and — the brass being TEXT itself on the active
nav mark and the odds fine print — `--accent` as a foreground on both
grounds ≥ 4.5:1. The ink rule forced the one behavioural colour change:
`--accent-ink` is DARK on brass (white on the old blue was a standing 3.2:1
AA failure). The classic card-back weave, previously three private copies
(deck, locked achievement, unlock toast; the shop swatch reuses the deck's),
is one `--card-back-classic` property — the #124 sheen-hoist pattern.
* *Serif lives on the card face title ONLY.* Georgia stack on
`.draw-face.back h2`, nowhere else — not the card's own description, not the
page H1s, not the uppercase letterspaced stage action row (also this-row-
only). One serif is a signature; two is a font mess. E2E pins both halves.
* *Category colour is data, never chrome.* Pills keep the raw category fill
and the computed `pillInk` verdict on every surface and every palette (the
mockup's uniform brass pills were a sketch); `DARK_INK` stays `#12141a`
byte-for-byte, never re-derived from a retuned `--bg`. Likewise the seeded
and default category colours (`#4f8cff` et al.) are user data and survive
the retune untouched.
* *The reward layer was the reference, not the target.* The trophy
cabinet's gold, the rarity sheen ladder and the trophy pile keep their
values byte-identical except what flows in through shared tokens — repainting
the shipped identities (#181, ADR-42) in brass would erase the very layer the
table was tuned to match. The Wrapped share card keeps its inlined charcoal
palette by its own #234 decision (deliberately frozen against theme drift).
The favicon, by contrast, IS chrome — the browser-tab card mark followed the
retune (brass frame and glow, felt weave) rather than staying blue-era.

*Out of scope:* a light theme, per-surface accent theming, the command
palette adopting the accent (its selection stays `--bg-hover` on purpose —
a utility surface, not a stage), and any card geometry change (300x420 and
the 5/7 achievement ratio stand).
