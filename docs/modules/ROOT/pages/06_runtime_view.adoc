= 6. Runtime View

== 6.1 Drawing a card

....
User          Client (DrawPage)        Server (drawService)
 │ click card      │                        │
 │────────────────►│ POST /api/draw         │
 │                 │───────────────────────►│ select drawable candidates
 │                 │  (shuffle animation)   │ weight = impact²/effort
 │                 │                        │   × urgency × staleness × cooldown
 │                 │                        │ roulette pick, set last_drawn_at
 │                 │                        │ persist current_draw_task_id
 │                 │◄───────────────────────│ {task, poolSize, probability}
 │ card flips      │ + achievement check    │
....

Empty pool returns
`{task: null, reason: 'no_ready_tasks' | 'all_too_big' | 'all_outside_window'}` —
the UI turns `all_too_big` into a "break something down" call to action, while
`all_outside_window` (every remaining candidate is outside its availability
window, ADR-20) says "scheduled for later": those cards return on their own.

The pick is persisted as the *current draw* (ADR-13). The DrawPage DERIVES
the standing card from `GET /api/draw/current` continuously (#110, ADR-29
amendment): a reload restores it — revealed, no shuffle, the same pattern as
the TimerBar (6.4) — and a pointer cleared by a completion, snooze, or
delete on another surface (TimerBar, Tasks page, MCP, a second tab)
dismisses the card on the query's next refetch without a second ✓ Done.
The endpoint validates the task is still
drawable (open leaf, estimated, within `max_draw_effort`, not snoozed/blocked,
not held back behind a sequential sibling, inside its availability window) and
lazily clears a pointer that went stale, e.g. because the card was edited out
of the deck.

A revealed card offers no re-draw (#88): the draw is a commitment — re-rolling
would mean fishing for a comfortable card, which defeats the
anti-procrastination purpose. The card leaves the screen only by being
resolved: completed, snoozed/blocked ("Not now", ADR-17), or deleted. Editing
the card out of the deck (the "this card was a mistake" case) also resolves it
— the lazy restore validation clears the persisted pointer on the next check,
while the session keeps the card on screen with a resolve hint until it is
resolved on-page, so the edit never turns into a hidden re-roll (#110).
Changing the category/goal filter while a card is revealed applies to the next
draw only.

== 6.2 Completing a task (single transaction)

....
PATCH /api/tasks/:id {status: 'done'}
  ├─ reject 409 if open subtasks exist
  ├─ drawn := task is the persisted current draw, or last_drawn_at within 6h
  └─ transaction:
       insert completions row (xp = effort × impact/3, ×1.5 if drawn)
       recurring? push due_date forward : set status done
       clear current draw if it was this task
       check achievements → response {task, xpAwarded, newAchievements, levelUp}
....

The client fires confetti, updates the trophy deck, and toasts new achievements
from this single response.

== 6.3 AI backward planning (with materials)

....
User picks materials → POST /api/ai/estimate
                        └─ count_tokens on assembled request → {inputTokens, estimatedUsd}
User confirms        → POST /api/ai/plan-goal {goalId, materialIds, userNotes?}
                        ├─ 503 if no API key; 400 if > 180K input tokens
                        ├─ blocks: [materials (PDFs as document blocks,
                        │           cache_control on last), goal context + instructions]
                        ├─ messages.parse(model=claude-opus-4-8, adaptive thinking,
                        │                 output_config.format = zod schema)
                        └─ {outcomeAnalysis, tasks[{title, effort, impact, phase}]}
User reviews/edits/deselects → accepted tasks created via POST /api/tasks
....

Nothing is written to the database without explicit user confirmation.

=== Variant: generating tasks from materials (transcription mode)

....
User picks materials,
writes an instruction → POST /api/ai/estimate {goalId, materialIds, instruction}
                         └─ counts the generate-tasks prompt shape (transcription
                            system prompt + generateTasksContext), not plan-goal's
User confirms         → POST /api/ai/generate-tasks {goalId, materialIds, instruction}
                         └─ deterministic post-processing (ADR-14):
                            points→impact quintiles, split-don't-clamp

User reviews 40+ rows  → summary header to spot-check against the material;
(edit/deselect)          part rows coupled to their exercise's checkbox
User commits           → POST /api/tasks            (one umbrella parent, no estimate)
                       → POST /api/tasks/:id/subtasks (ONE transactional batch of leaves,
                         │                            provenance in description)
                         └─ batch failed? DELETE the parent (cascade) — no
                            half-imported state (ADR-16)
....

== 6.4 Timer invariant

`POST /api/tasks/:id/timer/start` closes any running entry and opens a new one in
one transaction — at most one `time_entries` row with `ended_at IS NULL` exists.
The TimerBar restores itself after reload from `GET /api/timer/current`.

== 6.5 Focus mode (derived view)

"▶ Start now" on the revealed card starts the timer (6.4) and drops into a
fullscreen focus overlay: task title, a countdown sized to the effort
estimate, ✓ Done and ■ Stop in-face. The overlay is never persisted —
DrawPage derives it per render from the two facts above: current draw
present AND running timer on that task AND not explicitly exited (Escape)
→ focus; otherwise the revealed card or the idle deck (ADR-29). A reload
mid-focus therefore restores straight into the overlay from the same two
GETs that already restore the card (6.1) and the TimerBar (6.4); a timer
stopped or moved to another task meanwhile degrades to the plain revealed
card. The countdown is display only: past zero it flips to a visually
distinct overtime count-up — nothing is auto-stopped or auto-completed.
Escape exits the view only; the timer keeps running in the TimerBar, and
the in-face actions are the DrawPage's own (✓ Done = the completion PATCH,
■ Stop = the timer stop) — no duplicated controls, no new endpoints, and
focus sessions are ordinary `time_entries` in the Stats page's
estimates-vs-tracked block.
