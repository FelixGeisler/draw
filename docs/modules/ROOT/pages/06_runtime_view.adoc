= 6. Runtime View

== 6.1 Drawing a card

[plantuml,runtime-draw,svg]
....
@startuml
skinparam shadowing false
skinparam maxMessageSize 150
skinparam sequenceMessageAlign left
autonumber

actor User
participant "DrawPage" as UI
participant "routes/draw.ts" as Route
participant "drawService" as Draw
database "SQLite" as DB

== Draw — the gamble ==
User -> UI : click the deck
UI -> Route : POST /api/draw {categoryId?, goalId?}
Route -> Draw : drawTask(filters)
Draw -> DB : candidates: open leaf, estimated, <= max_draw_effort, not blocked/snoozed, not held back behind a sequential sibling (#23)
DB --> Draw : rows
Draw -> Draw : availability-window filter (#33, local wall clock)
Draw -> Draw : recurrence filter (#205): a recurring task sleeps until its due_date, its next occurrence
alt pool empty
  Draw -> DB : clear current draw
  Draw --> Route : {task: null, reason: no_ready_tasks | all_too_big | all_outside_window | all_awaiting_next_occurrence}
else candidates present
  Draw -> Draw : weight = impact²/effort × urgency × staleness × cooldown × siblingDamping(1/√k)
  Draw -> Draw : roulette pick
  Draw -> DB : stamp last_drawn_at; persist current_draw = id; drop any warm-up marker (ADR-13)
  Draw --> Route : {task, poolSize, probability}
end
Route -> Route : checkAchievements({drew: true}) — only when a card was actually dealt
Route --> UI : {task, poolSize, probability, newAchievements}
UI --> User : shuffle, then the card flips — no re-draw (#88): the draw is a commitment

== Restore / dismiss — the derived card (#110) ==
UI -> Route : GET /api/draw/current (on mount, every 60s, on window focus)
Route -> Draw : currentDraw()
Draw -> DB : read pointer + task row
Draw -> Draw : isRestorable()? — the same predicate as the pool
alt still drawable
  Draw --> Route : {task, warmup?}
else stale (resolved elsewhere: TimerBar, Tasks page, MCP, a 2nd tab)
  Draw -> DB : clear the pointer lazily
  Draw --> Route : null
end
Route --> UI : the standing card, or null
UI --> User : a reload restores the revealed card (no shuffle); a pointer cleared elsewhere dismisses it
@enduml
....

Empty pool returns
`{task: null, reason: 'no_ready_tasks' | 'all_too_big' | 'all_outside_window' | 'all_awaiting_next_occurrence'}` —
the UI turns `all_too_big` into a "break something down" call to action, while
`all_outside_window` (every remaining candidate is outside its availability
window, ADR-20) and `all_awaiting_next_occurrence` (every remaining candidate
is a recurring task already done this cycle, ADR-6 amendment) say "scheduled
for later": those cards return on their own.
Every call to action links to the Tasks page, where capture, the estimate
input and the break-down control all live since the Capture merge (ADR-40) —
each named action exists where the link lands.

The pick is persisted as the *current draw* (ADR-13). The DrawPage DERIVES
the standing card from `GET /api/draw/current` continuously (#110, ADR-29
amendment): a reload restores it — revealed, no shuffle, the same pattern as
the TimerBar (6.4) — and a pointer cleared by a completion, snooze, or
delete on another surface (TimerBar, Tasks page, MCP, a second tab)
dismisses the card on the query's next refetch without a second ✓ Done.
The endpoint validates the task is still
drawable (open leaf, estimated, within `max_draw_effort`, not snoozed/blocked,
not held back behind a sequential sibling, inside its availability window) and
lazily clears a pointer that went stale, e.g. because the card was edited out
of the deck.

A revealed card offers no re-draw (#88): the draw is a commitment — re-rolling
would mean fishing for a comfortable card, which defeats the
anti-procrastination purpose. The card leaves the screen only by being
resolved: completed, snoozed/blocked ("Not now", ADR-17), or deleted. Editing
the card out of the deck (the "this card was a mistake" case) also resolves it
— the lazy restore validation clears the persisted pointer on the next check,
while the session keeps the card on screen with a resolve hint until it is
resolved on-page, so the edit never turns into a hidden re-roll (#110).
Changing the category/goal filter while a card is revealed applies to the next
draw only.

The *warm-up deal* (`POST /api/draw/warmup`, #57, ADR-30) is the "I can't
start" escape hatch on the IDLE deck: it deterministically deals the
smallest eligible card from the same pool (no weights, no probability),
rate-limited to one per `warmup_every_hours`. It is not a re-roll — the
endpoint answers 409 while a valid current draw exists, and the dealt card
is the same commitment as a drawn one, marker and badge surviving reloads
via `GET /api/draw/current`.

There is deliberately no "deal me a day" batch of face-up cards (ADR-39
removed the daily hand, #147): a strip of dealt cards is a to-do list, and
showing the pile is the overwhelm the one-card draw exists to prevent. The
"enough for today" finish line is the daily goal (`daily_goal_completions`),
which counts completions without ever previewing tasks.

== 6.2 Completing a task (single transaction)

[plantuml,runtime-completion,svg]
....
@startuml
skinparam shadowing false
skinparam maxMessageSize 130
skinparam sequenceMessageAlign left
autonumber

participant "Client (card, TimerBar,\nTasks page) or MCP client" as UI
participant "routes/tasks.ts" as Route
participant "gamificationService\ncompleteTask()" as Gam
database "SQLite" as DB

UI -> Route : ✓ Done — PATCH /api/tasks/:id {status: 'done'}
Route -> DB : load the task row
alt open subtasks exist
  Route --> UI : 409 "complete all subtasks first"
else
  Route -> Route : zeroEffort := hasNonArchivedSubtask(id)
  note right of Route
    #111 / ADR-32: a parent whose subtasks
    already paid the effort XP completes at
    effort 0 — the floor lifts it to a symbolic
    1 XP. It is never in the deck, so wasDrawn
    is forced false with it.
  end note
  Route -> Route : drawn := is the current draw, or last_drawn_at < 6h — but never the card's own warm-up stamp (ADR-30): handed out, not gambled
  group transaction
    Route -> Gam : completeTask(task, drawn, {effortMinutes: 0}?)
    Gam -> Gam : multiplier (ADR-30): warm-up? in window ×1.25 / late ×1.0, never ×1.5 — else min(drawn ×1.5 × momentum ×1.25, ×1.5)
    Gam -> DB : INSERT completions (xp = max(1, round(round(effort × impact/3) × multiplier)), was_drawn, was_warmup)
    Gam -> DB : close this task's running time_entry (ADR-12)
    alt recurring
      Gam -> DB : due_date = completion's LOCAL day + recur_every_days, clear snooze/block — the task stays open, asleep until that next occurrence (#205)
    else normal
      Gam -> DB : status = 'done', completed_at, clear snooze/block
    end
    Gam -> DB : clearCurrentDraw() — drops the pointer + warm-up marker if it was this card
    Gam -> DB : freeze-token earn on a 7th/14th/… day — INSERT OR IGNORE, idempotent (ADR-28)
    Gam -> Gam : checkAchievements()
    Gam --> Route : {xpAwarded, bonus, newAchievements, recurring, levelUp}
    Route -> Gam : maybeAutoCompleteParent(parent_id) → completeTask(parent, false, {effortMinutes: 0})
    note right of Route
      #111 / ADR-32: breakdown all-done
      (>= 1 done, 0 open, archived ignored)
      and the parent open + non-recurring?
      Then it completes through completeTask()
      in the SAME transaction — effort 0.
    end note
  end
  Route --> UI : {task, xpAwarded, bonus, newAchievements, levelUp, parentCompletion?}
end
UI -> UI : confetti, XP/level bar, trophy deck, achievement toasts — all from this one response
@enduml
....

The client fires confetti, updates the trophy deck, and toasts new achievements
from this single response.

XP, levels, streaks and the trophy deck are never stored counters — they are
derived from the `completions` log on every read (ADR-2, ADR-5), which is why
reopening a task simply deletes its latest completion row.

=== Atomic pack opening and replay (#266)

[plantuml,runtime-pack-opening,svg]
....
@startuml
skinparam shadowing false
skinparam maxMessageSize 130
skinparam sequenceMessageAlign left
autonumber

actor Client
participant "routes/shop.ts" as Route
participant "shopService.ts" as Shop
participant "packCatalog.ts" as Catalog
database "SQLite" as DB

Client -> Route : POST /api/shop/buy {item, payment, ref}
Route -> Route : exact shape/field validation; canonical ref := trim(ref)
Route -> Shop : buyPack(payment, canonical ref, app-composed Math.random)
Shop -> DB : BEGIN IMMEDIATE; lookup ref
alt same ref and same payment
  Shop -> DB : derive fresh Gold/Tickets/Secret/Freeze/ownership snapshot
  Shop --> Client : 200 persisted opening + fresh shop + replayed:true\n(no RNG, write, repair or current-funds check)
else same ref, different payment
  Shop --> Client : 409 exact error; ROLLBACK, no RNG/write
else fresh but insufficient selected payment
  Shop --> Client : 400 exact Gold/Ticket error; ROLLBACK, no RNG/write
else fresh and funded
  Shop -> DB : read derived Gold/Tickets, ordered rarity history, Freeze bank
  Shop -> Catalog : sample 1 rarity; sample 2 back; sample 3 effective bonus
  Shop -> DB : INSERT immutable opening (AUTOINCREMENT order)
  Shop -> DB : settings grant if new; -100 Gold if Gold payment;
  Shop -> DB : duplicate refund and/or +50 Pouch where applicable
  Shop -> DB : derive post-opening shop snapshot
  Shop -> DB : COMMIT
  Shop --> Client : 200 persisted opening + shop + replayed:false
end
@enduml
....

The immediate writer lock serializes distinct refs, so concurrent requests
cannot overspend the same 100 Gold or one Ticket and later orders use the
predecessor's Secret result. The transaction object and prepared statements
are created against the current live handle per request because ADR-26 import
can replace and reopen it. Any sample or persistence failure rolls every fact
back. GET `/api/shop` is the same derived snapshot without transaction, RNG or
write.

A validated current first/retry/resume response replaces `['shop']` and separately
snapshots `opening` into a mount-local modal session keyed by `ref` and
`openingOrder`. Normal motion advances only on explicit background reveal, then an
effective bonus reveal when present; Skip completes without celebration and Close
or Escape discards only that session. The final explicit card reveal celebrates
once through the shared reduced-motion-aware gateway. The dialog is portalled
outside the inert app root, traps focus, announces only facts already exposed, and
restores the initiating control or the stable Shop heading. Reduced motion starts
at the same complete one-card/optional-second-card content with no reveal controls,
animation, timer or confetti. Failures and ordinary reloads never create a reveal,
and reveal progress is not stored or reconstructed from the later shop snapshot.

Nothing is written to the database without explicit user confirmation: the
estimate is a read-only price tag, the plan is a proposal, and only the tasks
the user keeps become rows.

== 6.4 Timer invariant

`POST /api/tasks/:id/timer/start` closes any running entry and opens a new one in
one transaction — at most one `time_entries` row with `ended_at IS NULL` exists.
The TimerBar restores itself after reload from `GET /api/timer/current`.

== 6.5 Focus mode (derived view)

"▶ Start now" on the revealed card starts the timer (6.4) and drops into a
fullscreen focus overlay: task title, a countdown sized to the effort
estimate, ✓ Done and ■ Stop in-face. The overlay is never persisted —
DrawPage derives it per render from the two facts above: current draw
present AND running timer on that task AND not explicitly exited (Escape)
→ focus; otherwise the revealed card or the idle deck (ADR-29). A reload
mid-focus therefore restores straight into the overlay from the same two
GETs that already restore the card (6.1) and the TimerBar (6.4); a timer
stopped or moved to another task meanwhile degrades to the plain revealed
card. The countdown is display only: past zero it flips to a visually
distinct overtime count-up — nothing is auto-stopped or auto-completed.
Escape exits the view only; the timer keeps running in the TimerBar, and
the in-face actions are the DrawPage's own (✓ Done = the completion PATCH,
■ Stop = the timer stop) — no duplicated controls, no new endpoints, and
focus sessions are ordinary `time_entries` in the Stats page's
estimates-vs-tracked block.

== 6.6 Breaking the drawn card down (#209)

"🔨 Break down" on the revealed card opens the same `SubtaskEditor` /
`AiBreakdownPanel` pair the Tasks page hosts, and accepting posts the ordinary
`POST /api/tasks/:id/subtasks` — no new endpoint, no second editor. What is
specific to this surface is the aftermath: the parent now has children, so it
is a *container* and containers are never drawable (6.1). The card has left
the deck, and the server clears the current-draw pointer lazily on the next
`GET /api/draw/current` exactly as it does after an edit that pushes the card
out.

It therefore takes the #88 hold rather than vanishing or being replaced: the
session stamps `heldSince`, the card stands on screen carrying the
out-of-the-deck hint, and it leaves only by being completed, snoozed or
deleted. No replacement card is dealt — a breakdown that redealt would be the
re-roll ADR-13 removed, reached by another name (ADR-56). A reload at this
point finds the pointer already gone and shows the idle deck, since the hold
is session-local by construction.
