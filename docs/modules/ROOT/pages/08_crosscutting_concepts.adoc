= 8. Cross-cutting Concepts

== 8.1 Derived state over stored state

Anything that can drift is computed at read time: drawability (SQL predicate),
"snoozed" (`blocked` or `deferred_until` still ahead — an expired snooze
re-enters the deck with no write, ADR-17), "held back" (an EARLIER open sibling
by stored `sort_order` under a `sequential` parent — completing the step in
front, OR dragging this one ahead of it, frees the next one with no write to
the freed row, ADR-18/ADR-43), "scheduled" (the calendar has the card for now and gives it
back with no write: outside the task's availability window on the local wall
clock, which re-admits it when the window opens, ADR-20 — or, on a RECURRING
task, its due date still ahead, that date being its next occurrence, which
re-admits it on the user's local day it names, ADR-6 amendment/#205),
"in progress" (running time entry
exists), Gold/XP/level/streak (v18 derives unclamped Gold from completion and
achievement owner columns plus `gold_ledger`; permanent XP is exactly
`SUM(completions.xp_awarded) + SUM(achievements.claim_xp) +
SUM(xp_ledger.amount WHERE reason='challenge')`, so retained legacy shop rows
are inert — ADR-5/ADR-42/ADR-62; Golden Tickets are pack Ticket earns minus
Ticket-paid openings, and Secret chance is the ordered opening-rarity suffix;
the streak's rest days and freeze consumption are re-derived on every read
from the rest-weekday setting, milestone earns, historical `buy:freeze` facts,
and effective pack Freeze openings read in `opening_order` — ADR-28), and the
displayed effort of a broken-down
task (`remainingEffortMinutes` — SUM over its OPEN subtasks' estimates at query
time, and NULL while any non-archived subtask exists but none are open: with
a breakdown the subtasks own the estimate, ADR-32; the stored estimate stays
what the user typed and keeps feeding edit forms and the revives-as-leaf path,
but never the parent's XP or drawability while a breakdown exists; the
one-level sum is exact for every database because the API
rejects new nested breakdowns, ADR-16, and the v7 startup migration
re-parented any pre-guard nesting to the root, ADR-24). The parent's own
status is lifecycle-derived from the same facts (ADR-32): the last subtask
closing completes it through `completeTask()` at a symbolic 1 XP, and an
open subtask arriving under a done parent reopens it, deleting its latest
completion row (ADR-5). Goal feasibility
(#60) is the same rule at goal scope: `GET /api/goals` derives
`remainingOpenEffortMinutes` (SUM over the goal's open *leaf* tasks — a
broken-down parent counts through its open subtasks, which inherit the goal
link, never its own estimate on top) and `trackedMinutes14d` (stats
`MINUTES_EXPR`, so a running entry counts up to now), and the pure client
module `lib/feasibility.ts` classifies on-track/tight/infeasible from
required vs. actual pace; days to the target date count on the LOCAL wall
clock to the end of the target day — a target date is a human-facing calendar
day like the ADR-21 activity buckets, not a UTC instant. No feasibility
snapshot is ever persisted. Split-in-place (#108) introduces no new derived
state either: the archived original of a split falls out of every predicate
above — the draw pool, the Tasks page child list, the effort rollups, the
sequential hold-back and the parent-completion gate — through the existing
`status` conditions alone, with no write beyond the one status flip.
Only facts are stored
(tasks, entries, completions, the append-only `draws` log, unlocked
achievements and their one-time claim, each subtask's `sort_order`, and the
optional achievement DISPLAY overrides — the user's chosen sibling POSITION and
a renamed/hidden achievement are stored facts like `resolved_at`,
ADR-38/ADR-43/ADR-44, not derivables, so they stay within this principle;
"held back" is still DERIVED from `sort_order`, never stored as a flag). Achievement CHAINS (#156, ADR-42)
derive each level's progress from these logs — draws (non-warmup only, ADR-30),
completions, streak, level, achieved goals, tracked hours — against one shared
threshold table that also drives the unlock, so a full progress bar is always a
real unlock. Claiming an unlocked achievement pays rarity-scaled XP and Gold
once (idempotent by one guarded owner update); the 5-tier rarity ladder and
both payout maps (Gold 5/10/25/50/100 from common through secret-rare) live in
`shared/achievementTiers.ts`, imported by the server and client so they cannot
drift.
Achievement DISPLAY metadata is user-customizable (#177, ADR-44): the
`achievement_customizations` side table (keyed by achievement key, so it covers
LOCKED keys too) holds an optional renamed title, a rewritten description, and a
`hidden` curation flag; `gamificationState()` ships `title`/`description` =
`COALESCE(custom, default)` plus `hidden`/`customized`. These are DISPLAY-ONLY
stored FACTS — a chosen label/visibility has no predicate to derive it from, so
they sit with `resolved_at`/`sort_order` inside ADR-2 — and touch nothing about
unlock, claim, XP, rarity or the shared key set: a hidden achievement still
unlocks and is still claimable (in the Stats "Hidden" section). The unlock toast
and every other reader pick up the custom copy for free, reading the same
`/api/gamification` fields.

=== Gold producer consistency (#264)

A completion stamps `gold_awarded = max(1, Math.round(final xp_awarded / 10))`
beside final XP in the same `completions` insert; reopen/delete remove that
owner through the existing lifecycle, and legacy rows remain zero. An
achievement claim stamps `claimed_at`, tier XP, and tier Gold together; a
pre-v18 claimed row keeps `claim_gold = NULL` and its XP-only wording. A daily
challenge stamps same-day, same-ref `+50` XP and `+20` Gold ledger rows in the
triggering completion or timer-stop transaction. XP-only days are immutable
legacy paid days; both rows mean paid; Gold-only is an invariant failure on a
payout attempt and is displayed as inconsistent, never repaired. The derived
Gold total is never clamped, so owner removal may expose a negative value.

Producer responses carry owner-local Gold only: completion results (including
nested parent completions) carry completion Gold, claims carry claim Gold, and
the challenge read model reports advertised versus actual Gold separately.
The header, trophy pile, History cards, achievement cards, and challenge chip
render server truth. Weekly/Wrapped summaries, MCP schemas/catalog, and shop
purchase availability do not change; HTTP passthroughs naturally carry the
additive fields. Completion-capable task writes, claims, and timer stop
invalidate both `['gamification']` and the independent `['shop']` snapshot
(with `['challenge']` where already required); no client computes or copies a
Gold total between caches.

=== Pure pack calculations (#265)

The stable registry is, in order: `classic`; common `ember`, `tide`,
`midnight`, `parchment`, `graphite`; rare `meadow`, `royal`, `sakura`,
`circuit`, `frost`; ultra-rare `aurum`, `aurora`, `obsidian`; secret-rare
`prism`. Their names are respectively Classic weave, Ember lattice, Tide
glass, Midnight stars, Aged parchment, Graphite weave, Meadow braid, Royal
filigree, Sakura glass, Neon circuit, Frost lattice, Aurum crest, Aurora silk,
Obsidian gold and Prism foil. Classic remains the always-owned common fallback,
not one of the 5/5/3/1 pullable entries.

Pack math is derived state over explicit arguments. Ordered outcomes are
consumed oldest-to-newest and produce
`min(500 + 50 * trailingNonSecretCount, 1500)` basis points; a Secret resets
the trailing count even when duplicate. One finite `[0,1)` sample selects the
Secret interval and then the non-Secret 45:32:18 ratio; a second sample selects
`floor(sample * tierSize)` in registry order. Duplicate Gold by tier is
10/20/40/100. Bonus intervals are `[0,.05)` Freeze, `[.05,.10)` Pouch,
`[.10,.12)` Ticket and `[.12,1)` none, except bank 2 resolves the first interval
directly to Pouch. Inputs are never clamped, coerced or implicitly generated:
invalid values throw, and the pure module reads no request, database or clock.
#266 introduces production randomness, payment, persistence and effects without
changing those pure rules.

=== Atomic Gold pack facts and derivation (#266)

`GET /api/shop` derives exactly Gold, Golden Tickets, the 100-Gold pack cost,
next Secret chance, the cap-2 Freeze bank, fixed-order ownership flags, and
equipment. Gold is still the unclamped sum of its three owner classes. Tickets
are `count(effective_bonus='ticket') - count(payment='ticket')`; chance consumes
rarities in ascending immutable `opening_order`; and pack Freeze timestamps are
converted through `localDate` after reading those rows in that same order.
There are no mutable balance, chance, Ticket, or Freeze counters.

A buy validates the plain three-key JSON body before any replay lookup. Its
canonical, case-sensitive identity is `trim(ref)`. A new request creates one
`db.transaction(fn).immediate()` against the current live handle. Replay or
conflict lookup precedes current-resource checks; a matching payment maps the
persisted row and returns a fresh snapshot without RNG, write, or repair, while
a changed payment is 409. Fresh Gold/Ticket insufficiency is a no-RNG 400.
Only a funded fresh opening consumes three app-composed finite `[0,1)` samples
in rarity/back/bonus order. Opening, optional settings grant, Gold charge,
duplicate refund, and Pouch effect then commit together or all roll back.

`pack_openings` is the immutable opening fact. Refund and `bonusGold` amounts
are reconstructed from its duplicate/rarity/effective-bonus values and the
stable catalog. Gold payments add exactly `-100, reason='buy:pack'`; Ticket
payments add no Gold row. Duplicate and Pouch effects add their own same-ref
rows under `refund:duplicate` and `bonus:pouch`. New ownership preserves
unknown string entries and never changes equipment. No effect changes XP.
SQLite's immediate lock makes concurrent payment validation, order allocation,
and predecessor-based chance one serialized operation.

== 8.2 The weight formula

....
weight = impact² / max(effort, 5)          leverage per minute
       × urgency(due_date)                 ×1 → ×4 over last 7 days, ×5 overdue
       × staleness(base date)              up to ×2 over 30 days; base = created,
                                           last completion (recurring), or the
                                           snooze wake time (ADR-17)
       × 0.15 if drawn within cooldown     variety across successive draws
       ÷ sqrt(pool siblings)               sibling damping (ADR-25): a k-leaf
                                           breakdown competes like ~√k cards;
                                           k counts siblings in the pool
....

Household chores work without ratings: no goal → neutral impact 3, and staleness
makes neglected chores progressively louder. Sibling damping keeps a 40-leaf
import (#29) from drowning them: measured at 58% of the probability mass on
day 0 (and rising with staleness), damped to ~18% — methodology and numbers in
`server/scripts/sim-issue30.ts`, guarded by `test/unit/draw-weights.test.ts`.

The *warm-up draw* (#57, ADR-30) deliberately bypasses this whole formula: one
deal per `warmup_every_hours` on the idle deck picks the minimum-effort
eligible card deterministically (tie-break most stale — the same staleness
anchor — then lowest id), with the cooldown applied as exclusion instead of
the ×0.15 dampener. Gamification keeps it honest: completed inside its
`max(effort, 15)`-minute window it pays ×1.25 (never the drawn ×1.5 — it was
handed out, not gambled), completing another card within 30 minutes of a
warm-up completion pays momentum ×1.25 — every combined multiplier is capped
at ×1.5, so warm-ups can never out-earn playing the deck.

=== The commitment invariant

One rule spans the draw (#88) and the warm-up (ADR-30): *a card in play
cannot be replaced, only resolved.* At most one current draw exists;
`POST /api/draw/warmup` answers 409 while one is standing; there is no
"Draw again". Every way out of a card is a real resolution — complete,
snooze/block, edit out of the deck, or delete — because the alternative is
fishing for a comfortable card, which is the choice paralysis the app
exists to remove. The same rule is why there is no multi-card day preview
at all (ADR-39): one card face-up hides the mountain; a dealt strip would
show it.

== 8.3 Error handling

- Server: consistent `{error: string}` bodies with proper status codes (404, 409 for
  domain conflicts, 503 for unconfigured AI).
- Client: typed `ApiError` from a single fetch wrapper; TanStack Query retry once.
- AI: SDK's typed exception classes mapped most-specific-first
  (`AuthenticationError` → friendly key hint, `RateLimitError` → 429,
  `APIConnectionError` → offline hint).

== 8.4 AI usage rules

Server-side only. `claude-opus-4-8` with adaptive thinking and structured outputs
(`beta.messages.parse` + `betaZodOutputFormat`; impact as literal union 1|2|3|4|5
because numeric min/max is unsupported). Materials precede instructions in the prompt
with a `cache_control` breakpoint on the last material block (prompt caching). Token
counting gates every call (estimate endpoint + 180K hard limit); the estimate
mirrors the exact prompt shape of the call it gates — a goal estimate carrying an
`instruction` counts the generate-tasks context under the transcription system
prompt, not plan-goal's (`estimateMode` in `aiService.ts`). No `temperature`,
`budget_tokens`, or assistant prefill — all rejected by this model family.

Goal PDFs upload once to the Anthropic Files API and are referenced by `file_id`
thereafter, instead of re-sending base64 on every call (xref:09_architecture_decisions.adoc[ADR-35],
#92). The id is a cache of Anthropic-side state, not identity: it is lazily filled on
first AI use (`materials.anthropic_file_id`, migration v11), cleared and re-uploaded
once when Anthropic rejects it (a stale id after a key swap or a restored backup), and
falls back to base64 whenever an upload cannot be made — so no AI feature breaks on the
upgrade path, and degraded mode without a key is unchanged. The `file_id` document
source is a beta surface, so these four calls use `client.beta.messages.*` with the
`files-api-2025-04-14` header, sent only when a request actually references an id. `.txt`/`.md`
materials stay inline as text blocks. `count_tokens` resolves the referenced file and
counts its real tokens, so the estimate and the 180K guard stay honest.

== 8.5 Security

- API key only in `server/.env` (gitignored), never in the browser.
- Upload filenames sanitized; stored under server-generated names; download/delete
  paths resolved and verified against the files directory (no traversal).
- Upload restricted to PDF/txt/md, 50 MB cap.
- Localhost by default: `npm run dev` is pinned to `127.0.0.1` — an ambient
  `HOST` export cannot move it — and only the production entry (`prod.ts`)
  honors the `HOST` env var (`server/src/config.ts`, default `127.0.0.1`).
  Setting `HOST` is the explicit opt-in for the self-hosted deployment
  (#189, ADR-49).
- Access protection (#190, xref:09_architecture_decisions.adoc[ADR-50]): the
  optional `DRAW_PASSWORD` gate — production entry only, off by default —
  puts every `/api` route and static asset behind a shared secret, presented
  either as a 30-day HMAC-signed `HttpOnly` session cookie (server-rendered
  login page, `server/src/loginPage.ts`) or as the `x-draw-password` header
  (MCP adapter, scripts). Password comparisons are constant-time
  (`timingSafeEqual` over SHA-256 digests, `server/src/auth.ts`); failed
  presentations are rate-limited per client IP (5 per 15 minutes, then 429),
  keyed on the de-proxied `req.ip` (set `TRUST_PROXY` behind a reverse proxy).
  Loopback clients (the in-process assistant, a same-host MCP adapter) present
  the real secret from inside the trust boundary and skip the limiter; an
  expired or tampered cookie is never counted as a failed attempt.
  `GET /api/health` stays credential-free for healthchecks. Threat model:
  protects the settings-DB API key and task data against casual LAN access;
  plain HTTP means it does NOT resist an on-path attacker — TLS is a reverse
  proxy's job, out of scope for Draw itself.
- Model-written SVG (card art, ADR-22) is treated as untrusted input:
  allowlist-re-serialized by `svgSanitizer.ts` before storage, and rendered
  only as an `<img>` data URI — never `dangerouslySetInnerHTML`.

== 8.6 Time handling

Timestamps stored as ISO 8601 UTC strings. Date-only values (due dates) are
compared as strings, which makes their format load-bearing — the write paths
reject anything that is not a real `YYYY-MM-DD` day, because an unpadded
`2026-7-4` sorts after `2026-07-26`. Date-range *arithmetic* happens in UTC
(`addDays` in `services/localDay.ts`) — local-timezone `Date` round-trips
caused an off-by-one-day bug
(see xref:11_risks_and_technical_debt.adoc[section 11]). Which *day* an
instant belongs to is the user-local question, and it has exactly one answer
in the codebase (`localDate`, same file): streak days (SQLite
`date(..., 'localtime')`), the History calendar's buckets (`localDayOf`,
ADR-21) and the recurrence schedule's next occurrence (ADR-6 amendment) all
read it the same way, with the UTC offset injectable so unit tests can pin
midnight-boundary behavior on any machine. The server suite runs pinned to
`TZ=Europe/Berlin`: on a UTC runner every local-vs-UTC day bug is invisible.

Three levels, all mandatory per PR (enforced by CI):

AI degraded mode).

== 8.8 Database migrations

`PRAGMA user_version` switch in `db.ts`: fresh databases execute `schema.sql`
(always the current schema); existing databases run incremental `ALTER TABLE`
steps. No migration framework. Version 18 adds the two Gold owner columns, the
append-only `gold_ledger`, immutable `pack_openings`, and the XP-ledger reason
index in one transaction; `user_version=18` is the last statement, so any DDL
failure leaves a v17 database unchanged. Backup import (section 8.9) runs this
same migration against its staged copy before any live swap.

== 8.9 Backup and restore

`GET /api/backup/export` streams one zip: an `app.db` snapshot taken with
`VACUUM INTO` (safe under WAL — the live file is never copied raw), all
material files, and a manifest (ADR-26). The Claude API key is stripped from
the snapshot only — backups never contain it; the live DB keeps it.

`POST /api/backup/import` **replaces everything** — tasks, goals, materials,
settings, gamification history, the current draw. There is no merge and no
partial restore. Safety nets, both inside `DATA_DIR`:

- the previous database is kept as `app.db.bak` (overwritten on the next import),
- the previous material files as `files.bak`.

Every rejected import (foreign zip, corrupt or newer-than-v18 database,
unsafe paths) is a `400` with the live data untouched. Versions through v18
are accepted; v17-or-older snapshots migrate in staging. The staged database
must then match the complete runtime v18 contract: both owner columns, exact
Gold/opening definitions and CHECK/unique/AUTOINCREMENT rules, all six
immutable triggers (definition and rollback-only behavior), and the
XP-ledger reason index. Only that validated file reaches the atomic swap. A
round trip therefore preserves append-only rows, opening order and
`sqlite_sequence`, not merely table names. #266 relies on that unchanged
whole-database format: refs/payments/rarities/bonuses/timestamps, applicable
Gold effects, ownership and equipment reproduce the exact derived shop and
same-ref replay after restore, and the next API opening receives an order above
the restored maximum. The Settings page gates restore behind an explicit
warning plus typing `REPLACE`.

A restored `app.db` carries each material's `anthropic_file_id` (section 8.4),
which is Anthropic-side state that does not travel with the archive — on another
machine or account it is dangling. This needs no special handling here: the id
is treated as a cache everywhere (xref:09_architecture_decisions.adoc[ADR-35]),
so the first AI call after a cross-account restore is rejected, drops the id and
re-uploads the PDF (which the archive does carry) transparently.

*Scheduled backups* (#194, xref:09_architecture_decisions.adoc[ADR-52]) reuse
that same export. When `BACKUP_INTERVAL_HOURS` is set (production entry only, off
by default), an in-process timer writes one archive per tick into
`DATA_DIR/backups/` and prunes to the newest `BACKUP_RETENTION` (default 7). The
archives are ordinary exports, so *restoring a scheduled backup is just an
import* — no separate restore path. The destination is a sibling of `files/`, not
under it, which is the entire recursion guard: the export globs `files/` and the
DB only, so an archive can never contain `backups/` (no archive-inside-archive
growth). A failed scheduled run is logged and swallowed — it never crashes the
server. The timer is started next to `startServer`, never inside `createApp()`
(which runs per integration test), and is `unref`'d and stoppable so no test or
shutdown leaks it.
