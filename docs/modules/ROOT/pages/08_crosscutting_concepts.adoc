= 8. Cross-cutting Concepts

== 8.1 Derived state over stored state

Anything that can drift is computed at read time: drawability (SQL predicate),
"snoozed" (`blocked` or `deferred_until` still ahead — an expired snooze
re-enters the deck with no write, ADR-17), "held back" (an EARLIER open sibling
by stored `sort_order` under a `sequential` parent — completing the step in
front, OR dragging this one ahead of it, frees the next one with no write to
the freed row, ADR-18/ADR-43), "scheduled" (outside the task's availability window on
the local wall clock — the window opening re-admits the card with no write,
ADR-20), "in progress" (running time entry
exists), XP/level/streak (aggregates over `completions` PLUS claimed-achievement
payouts — since #156 XP has TWO stored sources,
`SUM(completions.xp_awarded) + SUM(achievements.claim_xp)`, both honest event
logs so no counter drifts, ADR-42; the streak's rest
days and freeze consumption are re-derived on every read from the rest-weekday
setting and the append-only `streak_freezes` earn log — ADR-28), and the
displayed effort of a broken-down
task (`remainingEffortMinutes` — SUM over its OPEN subtasks' estimates at query
time, and NULL while any non-archived subtask exists but none are open: with
a breakdown the subtasks own the estimate, ADR-32; the stored estimate stays
what the user typed and keeps feeding edit forms and the revives-as-leaf path,
but never the parent's XP or drawability while a breakdown exists; the
one-level sum is exact for every database because the API
rejects new nested breakdowns, ADR-16, and the v7 startup migration
re-parented any pre-guard nesting to the root, ADR-24). The parent's own
status is lifecycle-derived from the same facts (ADR-32): the last subtask
closing completes it through `completeTask()` at a symbolic 1 XP, and an
open subtask arriving under a done parent reopens it, deleting its latest
completion row (ADR-5). Goal feasibility
(#60) is the same rule at goal scope: `GET /api/goals` derives
`remainingOpenEffortMinutes` (SUM over the goal's open *leaf* tasks — a
broken-down parent counts through its open subtasks, which inherit the goal
link, never its own estimate on top) and `trackedMinutes14d` (stats
`MINUTES_EXPR`, so a running entry counts up to now), and the pure client
module `lib/feasibility.ts` classifies on-track/tight/infeasible from
required vs. actual pace; days to the target date count on the LOCAL wall
clock to the end of the target day — a target date is a human-facing calendar
day like the ADR-21 activity buckets, not a UTC instant. No feasibility
snapshot is ever persisted. Split-in-place (#108) introduces no new derived
state either: the archived original of a split falls out of every predicate
above — the draw pool, the Tasks page child list, the effort rollups, the
sequential hold-back and the parent-completion gate — through the existing
`status` conditions alone, with no write beyond the one status flip.
Only facts are stored
(tasks, entries, completions, the append-only `draws` log, unlocked
achievements and their one-time claim, each subtask's `sort_order`, and the
optional achievement DISPLAY overrides — the user's chosen sibling POSITION and
a renamed/hidden achievement are stored facts like `resolved_at`,
ADR-38/ADR-43/ADR-44, not derivables, so they stay within this principle;
"held back" is still DERIVED from `sort_order`, never stored as a flag). Achievement CHAINS (#156, ADR-42)
derive each level's progress from these logs — draws (non-warmup only, ADR-30),
completions, streak, level, achieved goals, tracked hours — against one shared
threshold table that also drives the unlock, so a full progress bar is always a
real unlock. Claiming an unlocked achievement pays rarity-scaled XP once
(idempotent by the achievements primary key); the 5-tier rarity ladder
(common → secret-rare) lives in `shared/achievementTiers.ts`, imported by the
server (claim price) and the client (styling) so the two cannot drift.
Achievement DISPLAY metadata is user-customizable (#177, ADR-44): the
`achievement_customizations` side table (keyed by achievement key, so it covers
LOCKED keys too) holds an optional renamed title, a rewritten description, and a
`hidden` curation flag; `gamificationState()` ships `title`/`description` =
`COALESCE(custom, default)` plus `hidden`/`customized`. These are DISPLAY-ONLY
stored FACTS — a chosen label/visibility has no predicate to derive it from, so
they sit with `resolved_at`/`sort_order` inside ADR-2 — and touch nothing about
unlock, claim, XP, rarity or the shared key set: a hidden achievement still
unlocks and is still claimable (in the Stats "Hidden" section). The unlock toast
and every other reader pick up the custom copy for free, reading the same
`/api/gamification` fields.

== 8.2 The weight formula

....
weight = impact² / max(effort, 5)          leverage per minute
       × urgency(due_date)                 ×1 → ×4 over last 7 days, ×5 overdue
       × staleness(base date)              up to ×2 over 30 days; base = created,
                                           last completion (recurring), or the
                                           snooze wake time (ADR-17)
       × 0.15 if drawn within cooldown     variety across successive draws
       ÷ sqrt(pool siblings)               sibling damping (ADR-25): a k-leaf
                                           breakdown competes like ~√k cards;
                                           k counts siblings in the pool
....

Household chores work without ratings: no goal → neutral impact 3, and staleness
makes neglected chores progressively louder. Sibling damping keeps a 40-leaf
import (#29) from drowning them: measured at 58% of the probability mass on
day 0 (and rising with staleness), damped to ~18% — methodology and numbers in
`server/scripts/sim-issue30.ts`, guarded by `test/unit/draw-weights.test.ts`.

The *warm-up draw* (#57, ADR-30) deliberately bypasses this whole formula: one
deal per `warmup_every_hours` on the idle deck picks the minimum-effort
eligible card deterministically (tie-break most stale — the same staleness
anchor — then lowest id), with the cooldown applied as exclusion instead of
the ×0.15 dampener. Gamification keeps it honest: completed inside its
`max(effort, 15)`-minute window it pays ×1.25 (never the drawn ×1.5 — it was
handed out, not gambled), completing another card within 30 minutes of a
warm-up completion pays momentum ×1.25 — every combined multiplier is capped
at ×1.5, so warm-ups can never out-earn playing the deck.

=== The commitment invariant

One rule spans the draw (#88) and the warm-up (ADR-30): *a card in play
cannot be replaced, only resolved.* At most one current draw exists;
`POST /api/draw/warmup` answers 409 while one is standing; there is no
"Draw again". Every way out of a card is a real resolution — complete,
snooze/block, edit out of the deck, or delete — because the alternative is
fishing for a comfortable card, which is the choice paralysis the app
exists to remove. The same rule is why there is no multi-card day preview
at all (ADR-39): one card face-up hides the mountain; a dealt strip would
show it.

== 8.3 Error handling

- Server: consistent `{error: string}` bodies with proper status codes (404, 409 for
  domain conflicts, 503 for unconfigured AI).
- Client: typed `ApiError` from a single fetch wrapper; TanStack Query retry once.
- AI: SDK's typed exception classes mapped most-specific-first
  (`AuthenticationError` → friendly key hint, `RateLimitError` → 429,
  `APIConnectionError` → offline hint).

== 8.4 AI usage rules

Server-side only. `claude-opus-4-8` with adaptive thinking and structured outputs
(`beta.messages.parse` + `betaZodOutputFormat`; impact as literal union 1|2|3|4|5
because numeric min/max is unsupported). Materials precede instructions in the prompt
with a `cache_control` breakpoint on the last material block (prompt caching). Token
counting gates every call (estimate endpoint + 180K hard limit); the estimate
mirrors the exact prompt shape of the call it gates — a goal estimate carrying an
`instruction` counts the generate-tasks context under the transcription system
prompt, not plan-goal's (`estimateMode` in `aiService.ts`). No `temperature`,
`budget_tokens`, or assistant prefill — all rejected by this model family.

Goal PDFs upload once to the Anthropic Files API and are referenced by `file_id`
thereafter, instead of re-sending base64 on every call (xref:09_architecture_decisions.adoc[ADR-35],
#92). The id is a cache of Anthropic-side state, not identity: it is lazily filled on
first AI use (`materials.anthropic_file_id`, migration v11), cleared and re-uploaded
once when Anthropic rejects it (a stale id after a key swap or a restored backup), and
falls back to base64 whenever an upload cannot be made — so no AI feature breaks on the
upgrade path, and degraded mode without a key is unchanged. The `file_id` document
source is a beta surface, so these four calls use `client.beta.messages.*` with the
`files-api-2025-04-14` header, sent only when a request actually references an id. `.txt`/`.md`
materials stay inline as text blocks. `count_tokens` resolves the referenced file and
counts its real tokens, so the estimate and the 180K guard stay honest.

== 8.5 Security

- API key only in `server/.env` (gitignored), never in the browser.
- Upload filenames sanitized; stored under server-generated names; download/delete
  paths resolved and verified against the files directory (no traversal).
- Upload restricted to PDF/txt/md, 50 MB cap.
- Localhost only, enforced: the API server binds explicitly to `127.0.0.1`
  (`server/src/server.ts`), so it is not reachable from the local network.
  No auth by design (single local user).
- Model-written SVG (card art, ADR-22) is treated as untrusted input:
  allowlist-re-serialized by `svgSanitizer.ts` before storage, and rendered
  only as an `<img>` data URI — never `dangerouslySetInnerHTML`.

== 8.6 Time handling

Timestamps stored as ISO 8601 UTC strings. Date-only values (due dates) are
compared as strings. Date-range arithmetic happens in UTC (`addDays` in
`routes/stats.ts`) — local-timezone `Date` round-trips caused an off-by-one-day bug
(see xref:11_risks_and_technical_debt.adoc[section 11]). Streak days use SQLite
`date(..., 'localtime')` because a "day" is a user-local concept; the History
calendar's day buckets follow the same rule (`localDayOf` in `activityService`,
ADR-21), with the UTC offset injectable so unit tests can pin midnight-boundary
behavior on any machine.

== 8.7 Testing strategy

Three levels, all mandatory per PR (enforced by CI):

[cols="1,1,3",options="header"]
|===
|Level |Tooling |Scope

|Unit
|Vitest
|Pure logic: `urgencyFactor`/`stalenessFactor`/`weight`, `levelFromXp`, `classifyTask`

|Integration
|Vitest + Supertest
|Full REST API against `createApp()` with a real temp SQLite database per test file (`DATA_DIR` env, forked pool)

|End-to-end
|Playwright
|User journeys in a real browser: capture → triage/breakdown → draw → complete → timer → stats (the planning steps all on the single Tasks page, ADR-40); own ports (`API_PORT`/`VITE_PORT`) + throwaway DB, so a live dev server is undisturbed
|===

Design rules: tests never touch `server/data/`; journey E2E tests run serially
without retries (shared DB state); integration tests encode the domain invariants
(breakdown 409, one running timer, recurrence reset, XP-farming protection,
AI degraded mode).

== 8.8 Database migrations

`PRAGMA user_version` switch in `db.ts`: fresh databases execute `schema.sql`
(always the current schema); existing databases run incremental `ALTER TABLE`
steps. No migration framework. Backup import (section 8.9) reuses the same
`migrate()` after swapping in a restored database, so backups from older app
versions are migrated forward exactly like an old database on boot.

== 8.9 Backup and restore

`GET /api/backup/export` streams one zip: an `app.db` snapshot taken with
`VACUUM INTO` (safe under WAL — the live file is never copied raw), all
material files, and a manifest (ADR-26). The Claude API key is stripped from
the snapshot only — backups never contain it; the live DB keeps it.

`POST /api/backup/import` **replaces everything** — tasks, goals, materials,
settings, gamification history, the current draw. There is no merge and no
partial restore. Safety nets, both inside `DATA_DIR`:

- the previous database is kept as `app.db.bak` (overwritten on the next import),
- the previous material files as `files.bak`.

Every rejected import (foreign zip, corrupt or newer-versioned database,
unsafe paths) is a `400` with the live data untouched: validation runs
against staged temp copies before anything is swapped. The Settings page
gates the restore behind an explicit warning plus typing `REPLACE`.

A restored `app.db` carries each material's `anthropic_file_id` (section 8.4),
which is Anthropic-side state that does not travel with the archive — on another
machine or account it is dangling. This needs no special handling here: the id
is treated as a cache everywhere (xref:09_architecture_decisions.adoc[ADR-35]),
so the first AI call after a cross-account restore is rejected, drops the id and
re-uploads the PDF (which the archive does carry) transparently.
