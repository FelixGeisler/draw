= 8. Cross-cutting Concepts

== 8.1 Derived state over stored state

Anything that can drift is computed at read time: drawability (SQL predicate),
"snoozed" (`blocked` or `deferred_until` still ahead — an expired snooze
re-enters the deck with no write, ADR-17), "held back" (an older open sibling
under a `sequential` parent — completing the step in front frees the next one
with no write, ADR-18), "scheduled" (outside the task's availability window on
the local wall clock — the window opening re-admits the card with no write,
ADR-20), "in progress" (running time entry
exists), XP/level/streak (aggregates over `completions`; the streak's rest
days and freeze consumption are re-derived on every read from the rest-weekday
setting and the append-only `streak_freezes` earn log — ADR-28), weekly grade
(aggregation over `time_entries`), and the displayed effort of a broken-down
task (`remainingEffortMinutes` — SUM over its OPEN subtasks' estimates at query
time; the stored estimate stays what the user typed and keeps feeding XP and
edit forms; the one-level sum is exact for every database because the API
rejects new nested breakdowns, ADR-16, and the v7 startup migration
re-parented any pre-guard nesting to the root, ADR-24). Goal feasibility
(#60) is the same rule at goal scope: `GET /api/goals` derives
`remainingOpenEffortMinutes` (SUM over the goal's open *leaf* tasks — a
broken-down parent counts through its open subtasks, which inherit the goal
link, never its own estimate on top) and `trackedMinutes14d` (stats
`MINUTES_EXPR`, so a running entry counts up to now), and the pure client
module `lib/feasibility.ts` classifies on-track/tight/infeasible from
required vs. actual pace; days to the target date count on the LOCAL wall
clock to the end of the target day — a target date is a human-facing calendar
day like the ADR-21 activity buckets, not a UTC instant. No feasibility
snapshot is ever persisted. Only facts are stored
(tasks, entries, completions, unlocked achievements).

== 8.2 The weight formula

....
weight = impact² / max(effort, 5)          leverage per minute
       × urgency(due_date)                 ×1 → ×4 over last 7 days, ×5 overdue
       × staleness(base date)              up to ×2 over 30 days; base = created,
                                           last completion (recurring), or the
                                           snooze wake time (ADR-17)
       × 0.15 if drawn within cooldown     variety across successive draws
       ÷ sqrt(pool siblings)               sibling damping (ADR-25): a k-leaf
                                           breakdown competes like ~√k cards;
                                           k counts siblings in the pool
....

Household chores work without ratings: no goal → neutral impact 3, and staleness
makes neglected chores progressively louder. Sibling damping keeps a 40-leaf
import (#29) from drowning them: measured at 58% of the probability mass on
day 0 (and rising with staleness), damped to ~18% — methodology and numbers in
`server/scripts/sim-issue30.ts`, guarded by `test/unit/draw-weights.test.ts`.

== 8.3 Error handling

- Server: consistent `{error: string}` bodies with proper status codes (404, 409 for
  domain conflicts, 503 for unconfigured AI).
- Client: typed `ApiError` from a single fetch wrapper; TanStack Query retry once.
- AI: SDK's typed exception classes mapped most-specific-first
  (`AuthenticationError` → friendly key hint, `RateLimitError` → 429,
  `APIConnectionError` → offline hint).

== 8.4 AI usage rules

Server-side only. `claude-opus-4-8` with adaptive thinking and structured outputs
(`messages.parse` + `zodOutputFormat`; impact as literal union 1|2|3|4|5 because
numeric min/max is unsupported). Materials precede instructions in the prompt with a
`cache_control` breakpoint on the last material block (prompt caching). Token
counting gates every call (estimate endpoint + 180K hard limit); the estimate
mirrors the exact prompt shape of the call it gates — a goal estimate carrying an
`instruction` counts the generate-tasks context under the transcription system
prompt, not plan-goal's (`estimateMode` in `aiService.ts`). No `temperature`,
`budget_tokens`, or assistant prefill — all rejected by this model family.

== 8.5 Security

- API key only in `server/.env` (gitignored), never in the browser.
- Upload filenames sanitized; stored under server-generated names; download/delete
  paths resolved and verified against the files directory (no traversal).
- Upload restricted to PDF/txt/md, 50 MB cap.
- Localhost only, enforced: the API server binds explicitly to `127.0.0.1`
  (`server/src/server.ts`), so it is not reachable from the local network.
  No auth by design (single local user).
- Model-written SVG (card art, ADR-22) is treated as untrusted input:
  allowlist-re-serialized by `svgSanitizer.ts` before storage, and rendered
  only as an `<img>` data URI — never `dangerouslySetInnerHTML`.

== 8.6 Time handling

Timestamps stored as ISO 8601 UTC strings. Date-only values (due dates) are
compared as strings. Date-range arithmetic happens in UTC (`addDays` in
`routes/stats.ts`) — local-timezone `Date` round-trips caused an off-by-one-day bug
(see xref:11_risks_and_technical_debt.adoc[section 11]). Streak days use SQLite
`date(..., 'localtime')` because a "day" is a user-local concept; the history
skyline's day buckets follow the same rule (`localDayOf` in `activityService`,
ADR-21), with the UTC offset injectable so unit tests can pin midnight-boundary
behavior on any machine.

== 8.7 Testing strategy

Three levels, all mandatory per PR (enforced by CI):

[cols="1,1,3",options="header"]
|===
|Level |Tooling |Scope

|Unit
|Vitest
|Pure logic: `urgencyFactor`/`stalenessFactor`/`weight`, `levelFromXp`, `classifyTask`

|Integration
|Vitest + Supertest
|Full REST API against `createApp()` with a real temp SQLite database per test file (`DATA_DIR` env, forked pool)

|End-to-end
|Playwright
|User journeys in a real browser: capture → breakdown → draw → complete → timer → stats; own ports (`API_PORT`/`VITE_PORT`) + throwaway DB, so a live dev server is undisturbed
|===

Design rules: tests never touch `server/data/`; journey E2E tests run serially
without retries (shared DB state); integration tests encode the domain invariants
(breakdown 409, one running timer, recurrence reset, XP-farming protection,
AI degraded mode).

== 8.8 Database migrations

`PRAGMA user_version` switch in `db.ts`: fresh databases execute `schema.sql`
(always the current schema); existing databases run incremental `ALTER TABLE`
steps. No migration framework. Backup import (section 8.9) reuses the same
`migrate()` after swapping in a restored database, so backups from older app
versions are migrated forward exactly like an old database on boot.

== 8.9 Backup and restore

`GET /api/backup/export` streams one zip: an `app.db` snapshot taken with
`VACUUM INTO` (safe under WAL — the live file is never copied raw), all
material files, and a manifest (ADR-26). The Claude API key is stripped from
the snapshot only — backups never contain it; the live DB keeps it.

`POST /api/backup/import` **replaces everything** — tasks, goals, materials,
settings, gamification history, the current draw. There is no merge and no
partial restore. Safety nets, both inside `DATA_DIR`:

- the previous database is kept as `app.db.bak` (overwritten on the next import),
- the previous material files as `files.bak`.

Every rejected import (foreign zip, corrupt or newer-versioned database,
unsafe paths) is a `400` with the live data untouched: validation runs
against staged temp copies before anything is swapped. The Settings page
gates the restore behind an explicit warning plus typing `REPLACE`.
