= 1. Introduction and Goals

== 1.1 Requirements Overview

*Draw* is a web application that helps its user overcome two concrete
productivity problems. It currently runs as a local, single-user deployment
(xref:02_architecture_constraints.adoc[section 2]) — a property of the present
setup, not of the product itself (see <<vision>>):

1. *Difficulty getting started.* Big, vague tasks create decision paralysis.
   Draw forces every task above a configurable effort threshold (default 30 minutes)
   to be broken into small, concrete steps before it can be worked on, and offers a
   _card draw_: a weighted random pick that removes the "what should I do now?"
   decision entirely.
2. *Time spent on low-leverage work.* When studying for an exam it is tempting to
   perfect the introduction chapter instead of practicing past exam questions. Draw
   attaches an _impact_ rating (1–5★) to goal-linked tasks, biases the draw toward
   high-impact work, and tracks where time actually goes — the Stats page breaks
   the tracked minutes down by impact level so the pattern is visible.

Main features:

[cols="1,2",options="header"]
|===
|Feature |Purpose

|Capture-first task page + forced breakdown
|Quick capture on top of the Tasks page; tasks > 30 min cannot enter the deck — a triage strip surfaces them with the split/estimate controls in place (ADR-40)

|Weighted card draw
|Random pick weighted by impact² / effort × urgency × staleness

|Goals + backward planning
|Derive tasks from what is actually measured (e.g. the exam)

|Time tracking + stats
|Minutes tracked by impact level, category, and goal; estimate-vs-actual accuracy

|Gamification
|XP, levels, streaks, achievements, trophy deck

|AI assistance (optional)
|Claude API breaks down tasks and plans backward from goals, using uploaded materials (lecture PDFs, past exams) as context
|===

[#vision]
=== Vision

The long-term direction is to use Draw beyond a single local machine: on
several devices, on mobile, and possibly with multiple decks for different
contexts (e.g. different workplaces). None of this is designed yet — there is
no architecture and no schedule behind it. This subsection states direction,
not design: constraints and scope statements elsewhere
(xref:02_architecture_constraints.adoc[section 2],
xref:03_context_and_scope.adoc[section 3]) describe the current deployment and
point here, so that future multi-device features read as roadmap rather than
constraint violations.

== 1.2 Quality Goals

[cols="1,2,3",options="header"]
|===
|Priority |Quality goal |Motivation

|1
|*Zero-friction local operation*
|One command (`npm run dev`), no accounts. Local-_first_, not local-forever:
core features never depend on a cloud service — a property that must survive
any future step toward the <<vision>>

|2
|*Graceful AI degradation*
|Everything must work without an API key; AI is purely additive

|3
|*Data integrity*
|Time entries and completions are the basis of stats and XP — atomic writes, one source of truth, derived values never stored

|4
|*Cost transparency*
|Every AI call shows a token/cost estimate and requires explicit confirmation

|5
|*Responsiveness*
|Draw and completion feedback (confetti, XP) must feel instant
|===
